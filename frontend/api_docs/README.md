что убрано. Записи сверху вниз, новые — в начало.

## 2026-09-03 — Витрина: чат по заявке (шаг 3 плана)

Покупатель, оформивший заявку, и владелец/сотрудник теперь могут переписываться прямо
по заявке — уточнить размер, адрес, детали до того, как заявка вообще принята.

### Доступ покупателя — по `access_token`, не по логину

`POST /api/storefront/{slug}/requests` (уже существовал) теперь возвращает дополнительное
поле **`access_token`** — непредсказуемая строка, единственный способ покупателя вернуться
к своей заявке и чату без аккаунта. **Показывается один раз**, в момент создания — сервер
больше нигде его не отдаёт (owner-side ответы токен не содержат). Фронт должен сохранить
его в `localStorage` сразу после получения.

### Публичные эндпоинты (без авторизации, токен — query-параметр `?token=`)

- **`GET /api/storefront/requests/chat?token=<access_token>`** → список сообщений,
  старые сначала.
- **`POST /api/storefront/requests/chat?token=<access_token>`** → `{ text: string }`,
  `201`, отправляет сообщение от покупателя.
- **`WS /api/storefront/requests/chat/ws?token=<access_token>`** → push новых сообщений
  в реальном времени (тот же принцип, что и WS-канал уведомлений — открыть при входе на
  страницу заявки, переподключаться при разрыве, **не заменяет** REST для истории,
  только ускоряет доставку новых). Невалидный токен — сервер закрывает соединение.
  Формат события:
  ```ts
  { id: number, request_id: number, author: "customer" | "staff", text: string }
  ```
- Неверный/несуществующий токен на REST-эндпоинтах → `404`.

### Эндпоинты для владельца/сотрудника (авторизация, `Permission.ORDERS_VIEW`/`ORDERS_MANAGE`)

- **`GET /api/storefront/requests/{request_id}/chat`** → список сообщений заявки.
- **`POST /api/storefront/requests/{request_id}/chat`** → `{ text: string }`, `201`,
  отправляет сообщение от сотрудника.

Формат `StorefrontMessageResponse` (общий для всех вариантов чтения):
```ts
{ id: number, request_id: number, author: "customer" | "staff", text: string, created_at: string | null }
```

Новое сообщение от покупателя автоматически создаёт in-app + Telegram-уведомление
владельцу/менеджерам (тот же механизм, что и остальные уведомления, `kind: "storefront_message"`,
уже приходит через существующий `WS /api/notifications/ws`) — на панели управления
можно ничего специально не опрашивать, обычный колокольчик уже сработает.

### Что нужно сделать на фронте

1. После создания заявки — сохранить `access_token` из ответа в `localStorage`.
2. Экран заявки покупателя (доступен по сохранённому токену) — история сообщений +
   поле отправки, открыть WS при входе.
3. В панели владельца, на карточке заявки (`GET /api/storefront/requests/{id}`, уже
   существовал) — добавить блок переписки: история + отправка через новые эндпоинты.

## 2026-09-03 — Витрина: заявка от покупателя (шаг 2 плана)

Покупатель на публичной витрине теперь может оформить заявку (корзина → отправка) без
регистрации/входа. **Это НЕ мгновенный заказ** — заявка становится настоящим заказом
(`Order`) только после того, как владелец её примет и укажет склад и дату готовности.
Так фильтруются случайные/пустые заявки, и решается вопрос «покупателю всё равно, с
какого склада» — выбор склада остаётся за владельцем при обработке.

### 1. Публичный эндпоинт (без авторизации): оформить заявку

**`POST /api/storefront/{slug}/requests`** → `201`, `StorefrontRequestResponse`

```ts
// запрос
{
  customer_name: string,       // обязательно
  customer_phone?: string,     // опционально — российский формат, любой ввод нормализуется
  note?: string,                // до 1000 символов — пожелания/уточнения
  items: { product_id: number, quantity: string, variant_id?: number }[],  // корзина, quantity > 0
}
// ответ (201)
{
  id: number,
  customer_name: string,
  customer_phone: string,
  note: string,
  status: "new",
  lines: { product_id: number, quantity: string, variant_id: number | null }[],
}
```

Rate limit `20/hour` на IP. `404` — витрина выключена/не существует (тот же смысл, что и
у каталога). `400` — среди `items` есть товар без `show_on_storefront` (уже пропал с витрины
или ошибка на фронте — не должно происходить при нормальном сценарии из каталога).
Заявка **не резервирует остаток** и не проверяет его на этом шаге — только фиксирует
намерение купить.

### 2. Владелец: список входящих заявок и обработка

**`GET /api/storefront/requests/new`** (требует авторизации, `Permission.ORDERS_VIEW`) →
список `StorefrontRequestResponse` — заявки в статусе `new`, старые сначала. Предлагается
отдельный экран/вкладка «Заявки с витрины», не смешивать со списком обычных заказов.

**`POST /api/storefront/requests/{id}/accept`** (`Permission.ORDERS_MANAGE`):
```ts
{ warehouse_id: number, due_date: string /* YYYY-MM-DD */, prepayment?: string }
```
→ `200`, обычный `OrderResponse` (`source: "storefront"`) — заявка становится заказом:
резервируется остаток на указанном складе, товары получают текущую розничную цену
(не ту, что была в момент заявки — цена могла измениться), заявка помечается `accepted`.
Клиент находится по телефону заявки среди существующих в CRM либо создаётся новый
(если телефон не указан — клиент создаётся по имени без телефона).
`400` — недостаточно остатка на складе, или заявка уже обработана повторно.

**`POST /api/storefront/requests/{id}/reject`** (`Permission.ORDERS_MANAGE`) → `200`,
`StorefrontRequestResponse` со `status: "rejected"`. Без тела запроса.

**`GET /api/storefront/requests/{id}`** — карточка одной заявки (любого статуса), для
экрана истории/деталей.

### Что нужно сделать на фронте

1. На публичной странице витрины — корзина с количеством для каждого товара, форма
   оформления (имя обязательно, телефон и комментарий опционально), отправка на
   `POST /api/storefront/{slug}/requests`.
2. В панели владельца — новый экран/вкладка «Заявки с витрины» со списком новых заявок;
   у каждой — кнопки «Принять» (форма: склад + дата готовности + опционально предоплата)
   и «Отклонить».
3. После приёма заявка исчезает из списка новых (сервер отдаёт только `status=new`
   через `list/new`) — обновлять список после accept/reject.

## 2026-09-03 — Витрина: фильтр по складу (`?warehouse_id=`)

**Эндпоинт:** `GET /api/storefront/{slug}` (см. запись ниже про сам эндпоинт)

Добавлен опциональный query-параметр `warehouse_id: number`. Смысл — владелец с несколькими
точками/складами может поделиться с конкретным клиентом ссылкой на ассортимент ОДНОЙ точки:
`<домен>/store/{slug}?warehouse_id=<id>`.

**Список товаров не меняется** от этого параметра — витрина остаётся общим каталогом всех
товаров с `show_on_storefront: true` независимо от склада. Меняется только `in_stock`:
без параметра — наличие суммарно по всем складам магазина (как было); с параметром — наличие
именно на этом складе (товар, которого нет на выбранном складе, но есть на другом, всё равно
в списке, просто с `in_stock: false`).

Несуществующий/чужой `warehouse_id` не даёт ошибку — тихо игнорируется, как если бы параметра
не было (осознанно: иначе перебором можно было бы угадывать чужие id складов).

**Что нужно сделать на фронте:** в панели владельца, на экране склада — кнопка/ссылка «Поделиться
витриной склада», формирующая `<домен>/store/{slug}?warehouse_id=<id>` (id склада уже есть в
существующих данных `GET /api/inventory/warehouses`, ничего нового запрашивать не нужно). На
самой публичной странице — просто прочитать `warehouse_id` из query-string и передать его тем
же именем в запрос к API.

## 2026-09-03 — Публичная витрина-каталог: первый шаг (без заявки, без чата)

Первая часть будущей витрины для конечных покупателей (см. README §5.2). Пока только
**просмотр каталога без авторизации** — оформление заявки и чат будут отдельными шагами
позже, здесь их ещё нет.

**Новый публичный эндпоинт (без авторизации):** `GET /api/storefront/{slug}`

`{slug}` — тот же `shop_slug`, что отдаёт `POST /api/auth/register` при регистрации
(и теперь виден в `GET/PATCH /api/auth/shop` как поле `slug`).

Query-параметры (все опциональные): `query` (поиск по названию), `limit` (по умолчанию 50,
максимум 200), `offset`, `category_id`.

Ответ `200`:
```ts
{
  shop_name: string,
  products: {
    id: number,
    name: string,
    retail_price: string,
    photo: string,          // URL картинки или "" — своей заглушки нет, решать на фронте
    category_id: number | null,
    in_stock: boolean,      // ТОЛЬКО факт наличия — точных остатков в штуках здесь нет и не будет
  }[],
  categories: { id: number, name: string, parent_id: number | null }[],
  total: number,
}
```
**Намеренно нет в ответе:** `purchase_price`, `margin`, `sku`, `barcode`, точного количества
на складе — покупателю это не нужно и не должно быть видно.

**`404`** в двух случаях, неразличимых снаружи (чтобы не палить, существует ли магазин с таким
slug, но витрина просто выключена): slug не существует, либо у магазина витрина выключена.

**Товар не появляется на витрине сам по себе.** Нужны оба условия разом:
1. У магазина включена витрина целиком — новое поле `storefront_enabled` в
   `GET/PATCH /api/auth/shop` (`TenantResponse`/`UpdateShopRequest`), по умолчанию `false`.
2. У конкретного товара включён показ — новое поле `show_on_storefront` в
   `POST/PATCH /api/products` и в `ProductResponse`, по умолчанию `false`.

И то, и другое — сознательно выключено по умолчанию: включение витрины на уже заполненном
каталоге не должно тихо «рассекретить» всё разом.

**Что нужно сделать на фронте:**
1. В настройках магазина — тумблер «Публичная витрина» (`storefront_enabled` через
   `PATCH /api/auth/shop`), рядом можно показать готовую ссылку `<домен>/{slug}` для шапки
   Instagram (после того, как появится сама публичная страница на фронте).
2. В форме товара — чекбокс «Показывать на витрине» (`show_on_storefront`). Обе формы
   (создание/редактирование) уже принимают поле, `ProductResponse` уже его отдаёт.
3. Публичная страница каталога по `slug` (сама вёрстка и роут `/store/{slug}` или подобный —
   на усмотрение фронта) — тонкий read-only список карточек, без входа в систему.
4. Заявка/корзина/чат — не в этой части, будут отдельным API позже.

## 2026-09-03 — `GET /api/products`: серверная фильтрация/сортировка/остаток (breaking по query-параметрам)

**Эндпоинт:** `GET /api/products`

**Зачем:** сортировка по остатку (`stock_desc`) и фильтр «только в наличии» считались на клиенте — при большом каталоге это лишняя нагрузка и просто не масштабируется (страница отдаёт только 50 товаров за раз, а на клиенте фильтровался только этот кусок). Теперь то же самое считает сервер по всему каталогу.

**Query-параметры (все опциональные, `extra=forbid` — опечатка в имени вернёт `422`):**
```
query: str = ""              // как раньше — теперь ищет и по name, и по sku, и по barcode одним полем
limit: int = 50 (max 200)
offset: int = 0
category_id: int | null
sort: str = "name"           // те же значения, что и раньше: name, price_asc, price_desc,
                              // margin_desc, created_desc, created_asc — плюс новое: stock_desc
in_stock_only: bool = false  // НОВОЕ — остаток > 0
warehouse_id: int | null     // НОВОЕ — для in_stock_only/stock_desc: остаток на конкретном складе;
                              // не передан — остаток суммируется по всем складам магазина
```

**Не breaking по смыслу** (значения `sort` и семантика `query` не изменились), но **параметры теперь строго валидируются** Pydantic-схемой — если раньше на сервере лежал незнакомый query-параметр, он тихо игнорировался, теперь любой параметр не из списка выше вернёт `422`. Неизвестное значение `sort` теперь возвращает `400` с понятным `detail`, а не тихо откатывается на сортировку по имени, как раньше.

**Что нужно сделать на фронте:** в `ProductsPage.tsx` перенести клиентский `useMemo`-фильтр (`inStockOnly`, `sortMode === 'stock_desc'`, `stockFor()`) на серверные параметры — передавать `in_stock_only`/`sort=stock_desc`/`warehouse_id` в запрос `GET /api/products` вместо пост-обработки уже полученной страницы. Это даст корректный результат по всему каталогу, а не только по 50 загруженным товарам.

## 2026-09-02 — WebSocket-канал уведомлений (push вместо опроса)

**Новый эндпоинт:** `WS /api/notifications/ws?token=<access_token>`

Раньше единственный способ узнать о новом уведомлении — периодически дёргать `GET /api/notifications`. Теперь можно открыть WebSocket-соединение и получать события в реальном времени, без опроса.

**Авторизация:** токен передаётся query-параметром `?token=`, не заголовком `Authorization` — браузер не может выставить кастомный заголовок при открытии WebSocket-хендшейка. Тот же access_token, что и для обычных запросов. Невалидный/просроченный токен — сервер закрывает соединение (хендшейк не проходит).

**Формат события** (JSON, приходит на каждое новое уведомление пользователя):
```ts
{
  id: number,
  kind: "task_assigned" | "task_done" | "debt_due_soon" | "debt_overdue" | "low_stock",
  text: string,
  link: string,          // относительный путь для перехода по клику
  entity_id: number | null,
}
```

**Что нужно сделать на фронте:**
1. Открыть WS-соединение при входе в приложение (после получения access_token), переподключаться при разрыве.
2. На каждое событие — обновить счётчик непрочитанных и, если нужно, показать всплывающее уведомление; полный список/пометка прочитанным по-прежнему через существующие REST-эндпоинты (`GET/POST /api/notifications/...`) — WS ничего в них не меняет.
3. **WS не гарантирует доставку пропущенного** — если соединение было разорвано (телефон уснул, потеря сети), при реконнекте нужно один раз дёрнуть `GET /api/notifications`, чтобы досчитать то, что пропущено. WS — это ускорение, не замена REST.
4. Новый `kind: "low_stock"` — раньше в системе не было такого уведомления (см. следующую запись).

**Инфраструктура (если сами поднимаете dev через `npm run dev`, не через Docker):** ничего делать не нужно — `vite.config.ts` уже настроен на проксирование WS.

## 2026-09-02 — Приёмка товара теперь обновляет закупочную цену

**Эндпоинт:** `POST /api/inventory/receive`

**Изменено поведение (не меняет форму запроса/ответа, но меняет побочный эффект):**
Раньше поле `cost` в строке приёмки использовалось только для расчёта суммы долга поставщику — карточка товара (`Product.purchase_price`) не менялась вообще, даже если приняли по другой цене. Теперь после успешной приёмки закупочная цена товара становится равна цене последней приёмки (по строкам этого же документа с `cost`, если товар встречается в нескольких строках — побеждает последняя по порядку). Строки без `cost` цену не трогают.

**Почему:** без этого маржа/прибыль в аналитике тихо считалась по устаревшей закупочной цене, пока владелец не заходил в карточку товара и не поправлял её вручную.

**Что нужно сделать на фронте:** если где-то в UI кешируется/показывается `purchase_price` товара сразу после приёмки (не перезапрашивая карточку с сервера) — стоит перезапросить товар после успешной приёмки, чтобы не показать устаревшую цену.

## 2026-09-02 — CRM: клиент как центр (задачи↔клиент, лента событий, сводка)

Три связанных изменения одной темой — раньше, чтобы понять «что там с этим клиентом»,
нужно было отдельно открывать Продажи, Заказы, Долги и Задачи. Теперь всё это можно
собрать в одном месте на карточке клиента.

### 1. Задачи можно привязать к клиенту (новое поле, не breaking)

**Эндпоинты:** `POST /api/tasks`, `PATCH /api/tasks/{id}`, ответ `TaskResponse`.

- `TaskCreateRequest` и `TaskUpdateRequest` — новое опциональное поле `client_id: number | null`.
- `TaskResponse` — новое поле `client_id: number | null`.
- Если передать `client_id` несуществующего/чужого клиента — `404`.
- В `PATCH` работает обычная PATCH-семантика: поле шлётся, только если его нужно менять; `client_id: null` явно снимает привязку.

**Что можно сделать на фронте:** добавить выбор клиента в форму создания/редактирования задачи (не обязательно — старое поведение без `client_id` работает как раньше).

### 2. Новый эндпоинт: единая лента событий клиента

**`GET /api/counterparties/clients/{id}/timeline`** → `ClientTimelineEventResponse[]`

Продажи, заказы, долги (выдача/погашения/продления сроков) и задачи клиента одним
списком, отсортированным по дате (новые сверху). Формат события:

```ts
{
  type: "sale" | "order_created" | "debt_issued" | "debt_repaid" | "debt_extended" | "task",
  occurred_at: string,   // ISO datetime
  entity_id: number,     // id продажи/заказа/долга/задачи — для перехода на карточку
  title: string,         // готовый человекочитаемый текст, форматировать на фронте не нужно
  amount: string | null, // сумма, если применимо
  status: string | null, // order.status / task.status, если применимо
}
```

Пустой список — валидный ответ (клиент без событий), не ошибка. Несуществующий/чужой
клиент — `404`.

### 3. Новый эндпоинт: карточка клиента со сводкой

**`GET /api/counterparties/clients/{id}`** → `ClientSummaryResponse` (раньше такого
эндпоинта не было вообще — только список/поиск через `GET /api/counterparties/clients`)

```ts
{
  client: ClientResponse,        // те же поля, что и в списке
  debt_balance: string,          // суммарный непогашенный долг клиента
  active_orders_count: number,   // заказы в статусах new/in_progress/ready
  open_tasks_count: number,      // задачи клиента не в статусе done
}
```

Список/поиск (`GET /api/counterparties/clients`) не изменился — по-прежнему возвращает
`ClientResponse[]` без сводки, чтобы не утяжелять список большим количеством запросов.

## 2026-09-02 — единый формат непредвиденных ошибок (500)

**Затрагивает:** любой эндпоинт.

**Изменено (не breaking для штатных ошибок, но меняет edge case):**
- Раньше непредвиденная серверная ошибка (баг в коде, обрыв БД и т.п. — не бизнес-ошибка вроде «недостаточно остатка») могла отдать разный формат тела ответа в зависимости от режима сервера. Теперь **всегда** `500` с телом `{"detail": "Внутренняя ошибка сервера"}`, единообразно.
- Обычные ожидаемые ошибки (400/403/404/409 с понятным `detail`, например «Недостаточно остатка», «Товар не найден») не изменились — это касается только неожиданных сбоев, которых по-хорошему не должно быть видно.

**Что нужно сделать на фронте:** ничего обязательного — если где-то есть отдельная обработка сетевого/500-сценария, можно опираться на то, что `detail` теперь всегда предсказуемая строка, а не HTML/трейсбек.

## 2026-09-02 — офлайн-синхронизация продаж в долг

**Эндпоинт:** `POST /api/sync/sales`

**Добавлено (не breaking, обратно совместимо):**
- `OfflineSaleRequest` — новое опциональное поле `debt_due_date: string | null` (формат `YYYY-MM-DD`). То же поле, что уже принимает обычный `POST /api/sales` при `payment_method: "credit"`.

**Контекст:** раньше продажа с оплатой «в долг» не могла попасть в офлайн-очередь — контракт синка не принимал `debt_due_date`, и при отправке такой продажи сервер возвращал ошибку («Для продажи в долг нужно указать срок «Долг до»») вместо применения. Долг — самый частый способ оплаты в регионе, так что это был реальный пробел для офлайн-сценария на рынке без интернета.

**Что нужно сделать на фронте:**
1. Разрешить постановку продажи в долг (`payment_method: 'credit'`) в офлайн-очередь (IndexedDB) — сейчас, вероятно, такая продажа не ставится в очередь вообще или падает при отсутствии сети.
2. При отправке синка передавать `debt_due_date` и `client_id` — оба обязательны для продажи в долг (как и в онлайн-режиме).

Backend полностью готов и протестирован: создание долга, идемпотентность при повторной отправке той же офлайн-пачки (`client_op_id`) не задваивает ни продажу, ни долг.
