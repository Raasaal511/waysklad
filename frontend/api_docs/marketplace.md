# Общий каталог платформы (маркетплейс всех магазинов)

Новый публичный эндпоинт — единый каталог товаров **сразу всех** магазинов
платформы с включённой витриной, отдельно от каталога одного магазина
(`GET /api/storefront/{slug}`, см. `README.md` и `storefront_extras.md`).
Анонимный доступ, без авторизации — как и обычная витрина.

---

## `GET /api/marketplace/products`

Возвращает страницу товаров из всех магазинов, у которых включена витрина
(`storefront_enabled: true`). Rate limit: 300 запросов/минуту на IP — как у
витрины одного магазина (поднят в сессии 30, см. `README.md`).

### Query-параметры

Все необязательны.

```ts
{
  query?: string,          // поиск по названию/артикулу/штрихкоду, ILIKE
  category?: string,       // точное совпадение названия категории (см. ниже)
  price_min?: string,      // например "500"
  price_max?: string,
  in_stock_only?: boolean,
  variant_size?: string,   // точное совпадение, например "M" или "42"
  variant_color?: string,  // точное совпадение, например "Красный"
  shop_slug?: string,      // ограничить каталог одним магазином
  sort?: "name" | "price_asc" | "price_desc" | "created_desc",  // по умолчанию "name"
  limit?: number,          // по умолчанию 50, максимум 50
  offset?: number,         // по умолчанию 0
  min_rating?: number,     // 1..5 — новое (2026-09-16), «от N звёзд»
}
```

**`min_rating`** (новое, 2026-09-16) — тот же смысл, что у одиночной
витрины (см. `storefront_extras.md`, п.8): товар проходит фильтр, если его
`average_rating` больше или равен указанному значению, только по видимым
отзывам. Товар без единого отзыва не проходит фильтр даже при
`min_rating=1` — считается кросс-tenant, каждый товар видит только свои
собственные отзывы (изоляция та же, что у `sold_count`/`average_rating` в
ответе, см. выше).

**`category`** — не `category_id`, как в каталоге одного магазина, а
**название** категории строкой. У разных магазинов нет общего справочника
категорий (каждая категория привязана к своему tenant), поэтому кросс-
магазинный фильтр матчит по точному совпадению названия строкой (например,
`category=Обувь` найдёт товары из категории «Обувь» у любого магазина,
у которого такая категория есть — это разные записи в БД с разными id,
но одинаковым названием). Если понадобится общий справочник категорий
платформы — это отдельная доработка, сейчас его нет.

**`shop_slug`** — тот же slug, что в URL одиночной витрины
(`/storefront/{slug}`). Полезно, если хотите переиспользовать общий
каталог как основу для страницы одного магазина, либо дать пользователю
ссылку «показать все товары этого продавца» из общей выдачи. Неизвестный
слаг или слаг магазина с выключенной витриной — просто пустой результат
(`total: 0`), не ошибка.

**Неизвестное значение `sort`** → `400` с понятным `detail`, как и в
каталоге одного магазина.

### Формат ответа — `200`

```ts
{
  products: {
    id: number,
    name: string,
    retail_price: string,
    photo: string,
    category_name: string | null,
    in_stock: boolean,
    min_order_qty: string | null,
    order_step_qty: string | null,
    shop_slug: string,
    shop_name: string,
    sold_count: string,       // новое (2026-09-16) — см. ниже
    average_rating: number,   // новое (2026-09-16)
    reviews_count: number,    // новое (2026-09-16)
  }[],
  total: number,
}
```

Та же публично безопасная модель, что в каталоге одного магазина (без
закупочной цены, без маржи, без точного остатка — только `in_stock`), плюс
два новых поля `shop_slug`/`shop_name`, чтобы на общей странице маркетплейса
можно было показать, из какого магазина товар, и дать ссылку на его витрину
(`/storefront/{shop_slug}`) или отфильтровать через `?shop_slug=`.

**`sold_count`/`average_rating`/`reviews_count` (добавлены 2026-09-16)** —
догнали расхождение с одиночной витриной (см. `storefront_sold_count.md` и
`reviews.md`, где эти поля появились раньше). Считаются кросс-tenant: каждый
товар видит только свои продажи/отзывы, значения у разных магазинов не
пересекаются. Товар без продаж/отзывов — `sold_count: "0"`,
`average_rating: 0.0`, `reviews_count: 0` (не `null`, не отсутствие полей).
Только видимые (не скрытые владельцем) отзывы входят в агрегат — как и на
одиночной витрине.

Пустой каталог (нет ни одного магазина с включённой витриной, либо
`shop_slug` не найден) — это `200` с `{"products": [], "total": 0}`, не
`404`.

### Наличие (`in_stock`)

Считается только по складам, которые владелец магазина отметил видимыми на
витрине (`Warehouse.show_on_storefront`, см. `storefront_extras.md`, п.6) —
как и в одиночной витрине. У магазина без ни одного видимого склада все его
товары в общем каталоге присутствуют, но `in_stock` всегда `false`.

### Пагинация

`limit`/`offset` — как везде в API, `total` — количество товаров,
подходящих под текущие фильтры **по всем магазинам сразу** (не на
магазин). Максимальный `limit` — 50, как в одиночной витрине.

### Пример

```
GET /api/marketplace/products?query=кроссовки&price_min=1000&price_max=5000&in_stock_only=true&sort=price_asc&limit=20
```

### На фронте

1. Отдельная страница/раздел «Маркетплейс» или «Открытая лавка» — плитка
   товаров разных магазинов вперемешку (сортировка/фильтры как в обычном
   каталоге одного магазина).
2. На каждой карточке товара — название магазина (`shop_name`), ссылка на
   `shop_slug` ведёт на страницу этого магазина (либо на существующую
   одиночную витрину `/store/{shop_slug}`, либо на этот же общий каталог с
   `?shop_slug=...`, если отдельной страницы магазина не будет).
3. Категории и размеры/цвета для построения фильтров этот эндпоинт **не
   отдаёт списком** (в отличие от одиночной витрины, где есть
   `available_sizes`/`available_colors`/`categories` с счётчиками) — в эту
   задачу это не входило. Если понадобится — фронту стоит запросить это
   отдельной доработкой.
4. У эндпоинта нет своей карточки товара (`GET .../products/{id}`) — только
   список. Для перехода на детальную страницу товара используйте уже
   существующий `GET /api/storefront/{shop_slug}/products/{id}` (см.
   `storefront_extras.md`, п.1), передав туда `shop_slug` и `id` из строки
   общего каталога.
5. Заявку/заказ по товару из общего каталога оформляем так же, как с
   одиночной витрины — `POST /api/storefront/{shop_slug}/requests` (общий
   каталог сам заявки не создаёт, это чисто витрина списка).
6. Бейдж рейтинга (`average_rating`/`reviews_count`) и «Продано: N»
   (`sold_count`) на карточке товара в общей ленте — тот же паттерн, что уже
   должен быть на карточке одиночной витрины (`storefront_sold_count.md`,
   `reviews.md`): скрывать бейдж при `reviews_count == 0` / `sold_count == "0"`,
   не показывать «0 отзывов»/«Продано: 0».
