# Витрина: карточка товара, сортировка, статус заявки, спам-защита

Пять доработок публичной витрины поверх уже описанного в `README.md`
(каталог, заявка, чат). Ничего не ломает существующие контракты — только
новые эндпоинты и новые опциональные поля.

---

## 1. Карточка одного товара

**`GET /api/storefront/{slug}/products/{product_id}`** → `200`,
`StorefrontProductPageResponse`, или `404` (товар скрыт/не существует/
принадлежит другому магазину/витрина выключена — все случаи неразличимы
снаружи).

```ts
{
  shop_name: string,
  product: {
    id: number,
    name: string,
    retail_price: string,
    photo: string,
    category_id: number | null,
    in_stock: boolean,
    sku: string,
    variants: { id: number, size: string, color: string }[],
  },
}
```

Та же урезанная модель, что и в списке каталога (без закупочной цены/маржи/
точного остатка), плюс `sku` и `variants` — для полноты карточки и для
шеринга конкретного товара (например, ссылка на кроссовки нужного размера
в WhatsApp).

**На фронте:** отдельный роут `/store/{slug}/products/{id}`, ссылка на него
с каждой карточки в списке каталога.

---

## 2. Сортировка каталога

**`GET /api/storefront/{slug}`** — новый опциональный query-параметр
`sort`, по умолчанию `"name"`. Допустимые значения:

- `name` — по названию (по умолчанию, как раньше)
- `price_asc` / `price_desc` — по розничной цене
- `created_desc` — новинки сначала

Неизвестное значение → `400` с понятным `detail`, не 500 и не тихий откат
на дефолт.

**Специально не отдаётся:** сортировка по марже/остатку — это внутренние
данные, покупателю их видеть незачем.

**На фронте:** селект сортировки над списком каталога, значение — прямо в
query `?sort=price_asc`.

---

## 3. Категории со счётчиком товаров

**`GET /api/storefront/{slug}`** — поле `categories` в ответе теперь несёт
дополнительное поле `product_count`:

```ts
categories: { id: number, name: string, parent_id: number | null, product_count: number }[]
```

Список **уже отфильтрован** — отдаются только категории, где есть хотя бы
один товар с `show_on_storefront: true` (пустые категории не засоряют
навигацию). Число — только видимые на витрине товары этой категории, не
весь каталог магазина.

**На фронте:** навигация вида «Обувь (12)» вместо плоского списка названий.

---

## 4. Статус своей заявки по токену

**`GET /api/storefront/requests/status?token=<access_token>`** → `200`,
или `404` (неверный/несуществующий токен).

```ts
{
  status: "new" | "accepted" | "rejected",
  order: {
    due_date: string,       // YYYY-MM-DD
    total: string,
    prepayment: string,
    to_pay: string,
    status: "new" | "in_progress" | "ready" | "issued" | "cancelled",
  } | null,   // заполнено только когда status === "accepted"
}
```

Тот же `access_token`, что уже используется для чата (`localStorage`,
получен один раз при создании заявки) — отдельного токена заводить не
пришлось.

**На фронте:** на странице заявки покупателя — блок «Статус заявки» рядом
с чатом; после `accepted` показать дату готовности и сумму к доплате.

---

## 5. Защита от спама заявками

Не новый эндпоинт — изменение поведения `POST /api/storefront/{slug}/requests`.

Если у покупателя (по указанному телефону) уже есть **5 необработанных**
(`status: "new"`) заявок в этом магазине — новая заявка отклоняется:

```json
{"detail": "У вас уже есть необработанные заявки — дождитесь ответа магазина"}
```
`400`.

Действует только когда телефон указан — анонимные заявки (без телефона) не
ограничены этим лимитом (нечем идентифицировать одного и того же
отправителя). Лимит — per-магазин, не глобальный: тот же телефон свободно
пишет в другой магазин.

**На фронте:** показать `detail` из ответа как есть — сообщение уже готово
для показа пользователю, ничего дополнительно формулировать не нужно.

## 6. Список складов в каталоге + видимость склада на витрине (2026-09-04)

**`GET /api/storefront/{slug}`** — новое поле `warehouses` в ответе:

```ts
warehouses: { id: number, name: string, address: string }[]
```

Только склады, которые владелец явно отметил видимыми на витрине (новое
поле `Warehouse.show_on_storefront`, по умолчанию `false` — как и у товара).
Если владелец ничего не включил, `warehouses` — пустой массив.

**⚠️ Breaking для уже работающих витрин:** у магазинов, где витрина уже
была включена ДО этой доработки (сессии 23-25), все существующие склады
после миграции получают `show_on_storefront=false` по умолчанию — значит
все товары такого магазина внезапно покажут `in_stock: false`, и
`warehouses` станет пустым, пока владелец не зайдёт в настройки каждого
склада и явно не включит витрину. На момент этой сессии в проде таких
магазинов не было (только тестовые dev-аккаунты), но при следующем реальном
деплое с уже существующими пилотными магазинами это надо учесть — либо
предупредить владельцев, либо (лучше) сделать одноразовый backfill-скрипт
«включить show_on_storefront на всех складах тенантов с storefront_enabled=true»
перед вкаткой в прод.

**Важно про `in_stock` и уже существующий `?warehouse_id=`:** теперь
считается только по видимым складам. Товар, у которого остаток есть только
на скрытом складе, отдаётся как `in_stock: false` — покупателю не показывают
наличие там, куда его не пускают физически. `?warehouse_id=` с id скрытого
склада тихо игнорируется (как и раньше с несуществующим/чужим).

**Как владелец включает склад:** `PUT /api/inventory/warehouses/{id}` (уже
существующий эндпоинт настроек склада) — новое поле в теле запроса:

```ts
{ name: string, address?: string, show_on_storefront?: boolean }
```

Ответ (`WarehouseResponse`) тоже получил это поле.

**На фронте:** это НЕ отдельный раздел «Склады» с навигацией — специально
не стали делать так по итогам обсуждения (покупателю физически всё равно,
с какого склада товар, продавец сам решает логистику после заявки). Что
нужно на фронте:
1. Настройки склада (форма редактирования склада у владельца) — чекбокс
   «Показывать на витрине».
2. Общий каталог — как есть, ничего не меняется по умолчанию (весь
   ассортимент магазина, наличие суммируется по видимым складам).
3. Если хотите использовать `warehouses` из ответа — например, лёгкий
   фильтр-переключатель наличия по конкретной точке (не отдельная
   страница) для магазинов с несколькими адресами. Опционально, можно не
   делать вовсе, если у пилотных магазинов один склад.

## 7. Мин. количество и шаг заказа на витрине (2026-09-04)

Новые поля товара — настраиваются владельцем в форме товара, как цена или
единица измерения. Оба опциональны, `null` по умолчанию = без ограничения
(как сейчас).

**`POST /api/products`** и **`PUT /api/products/{id}`** — новые поля в теле:

```ts
{ storefront_min_qty?: string | null, storefront_step_qty?: string | null }
```

`ProductResponse` (ответ создания/обновления/списка товаров владельцу)
получил эти же два поля под теми же именами.

**На публичной витрине названия другие** — `GET /api/storefront/{slug}` и
`GET /api/storefront/{slug}/products/{id}`:

```ts
{ min_order_qty: string | null, order_step_qty: string | null }
```

**Как считается валидное количество:** `quantity >= min_order_qty` (если
задан) и `(quantity - min_order_qty) % order_step_qty == 0` (если задан шаг
— кратность отсчитывается от минимума, не от нуля: минимум 15 и шаг 10
значит 15, 25, 35...). Если задан только шаг без минимума — кратность от
нуля. Проверяется **только** при создании заявки с витрины
(`POST /api/storefront/{slug}/requests`) — обычная продажа/заказ через
основной интерфейс магазина эти поля не знают и не ограничены ими.

Нарушение → `400` с готовым текстом, можно показывать как есть:
```json
{"detail": "«Мука оптом»: минимальное количество для заказа — 10"}
{"detail": "«Мука оптом»: количество должно кратно увеличиваться на 10"}
```

**На фронте:**
1. Форма товара (у владельца) — два опциональных числовых поля рядом с
   ценой/единицей измерения: «Мин. количество для заказа», «Шаг заказа».
2. Карточка товара на витрине (список и детальная) — если `min_order_qty`
   задан, поле количества в заявке должно стартовать с этого значения, а
   не с 1; если задан `order_step_qty` — кнопки +/- должны прыгать этим
   шагом, а не на 1. Не обязательно валидировать на фронте заранее — сервер
   всё равно проверит и вернёт понятный `detail`, но лучше не давать ввести
   заведомо невалидное количество.

## 8. Фильтры каталога «как в Wildberries» (2026-09-04)

**`GET /api/storefront/{slug}`** — новые опциональные query-параметры,
комбинируются с уже существующими (`query`, `category_id`, `sort`,
`warehouse_id`):

```ts
{
  min_price?: string,     // например "500"
  max_price?: string,
  in_stock_only?: boolean,
  variant_size?: string,  // точное совпадение, например "M" или "42"
  variant_color?: string, // точное совпадение, например "Красный"
}
```

`in_stock_only=true` — как обычный `in_stock`, учитывает только видимые на
витрине склады (см. п.6 выше). `variant_size`/`variant_color` — товар
попадает в выдачу, если у него есть **хотя бы один** вариант с этим точным
значением (не текстовый поиск, точное совпадение — значения берутся из
нового списка `available_sizes`/`available_colors`, см. ниже).

**Новые поля в ответе каталога** — список доступных значений для построения
самого фильтра (без этого фронту не из чего строить чипсы/селект):

```ts
{
  available_sizes: string[],   // например ["S", "M", "42", "43"]
  available_colors: string[],  // например ["Белый", "Красный", "Синий"]
}
```

Список — только среди товаров, видимых на витрине прямо сейчас (пустых
значений size/color нет — у товара без вариантов туда ничего не попадает).
Список **не зависит от остальных активных фильтров** (не сужается, если
уже выбрана категория/цена) — иначе фильтры «прыгали» бы при каждом клике;
если понадобится обратное поведение (фасетный подсчёт, как на WB — «Красный
(3)» с числом внутри текущей выборки), это отдельная доработка, не в этой
пачке.

**На фронте:**
1. Панель фильтров над/рядом с каталогом — слайдер или два поля «от-до» для
   цены, чекбокс «Только в наличии», чипсы/селект для размера и цвета
   (данные — из `available_sizes`/`available_colors`).
2. Все параметры комбинируются в одном запросе `GET /{slug}?min_price=500&
   in_stock_only=true&variant_size=M` — не нужно делать отдельные запросы на
   каждый фильтр.
3. Раз это то же самое место, где уже есть сортировка и поиск — панель
   фильтров логично встраивать в тот же контрол, а не как отдельный экран.

---

## Не в этой пачке — сделать на чистом фронтенде

**Избранное** — по решению явно НЕ backend-функциональность: список
избранных товаров хранится в `localStorage` браузера покупателя, backend
ничего не знает про избранное и не участвует. Ничего добавлять в API не
нужно — фронт сам решает, как хранить и показывать список.
