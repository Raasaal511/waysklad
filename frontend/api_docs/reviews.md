# Отзывы и рейтинг товара — v2 (промпт B3)

Продолжение первой итерации отзывов (раздел «v1» ниже в этом же файле, не
удалён — контракт только расширен, ничего не сломано). Новое: исправлена
уникальность отзыва (был баг — заявка с несколькими товарами позволяла
оценить только один), несколько фото в отзыве, фиксированные теги, голоса
«полезно/не полезно», серверные фильтры/сортировка/агрегаты публичного
списка, проверка «можно ли оставить отзыв», список для модерации по всему
магазину. Фронтенд не менялся — весь этот раздел про новый бэкенд-контракт.

---

## 1. Исправлен баг уникальности

Раньше `reviews.storefront_request_id` был `unique` — из заявки с
несколькими товарами можно было оценить только ПЕРВЫЙ. Теперь уникальность
по паре `(storefront_request_id, product_id)`: один отзыв на товар в рамках
заявки, но заявка с 3 товарами допускает по отзыву на каждый. Ошибка `400`
при повторе — как раньше, просто теперь смотрит на пару, а не только на
заявку.

## 2. Несколько фото

`POST /api/reviews` и весь вывод отзыва получили `photos: string[]` (до 5).
Старое поле `photo` осталось для совместимости:

- Если в ответе есть `photos`, `photo` = `photos[0]` (или `""`, если пусто).
- Старые отзывы, заведённые только через `photo` (до этой итерации),
  автоматически отдают `photos: [photo]`.
- Можно продолжать слать только `photo` в `POST /api/reviews` (без `photos`)
  — сработает как раньше, просто `photos` в ответе будет `[photo]`.

### `POST /api/reviews/photos` — загрузить фото для отзыва

Требует `Authorization: Bearer <customer JWT>`. `multipart/form-data`, поле
`file`. Те же ограничения, что у фото товара (jpg/jpeg/png/webp, до 5 МБ,
пережимается в WebP). Rate limit `30/час` на покупателя (плюс общий лимит по
IP на роутере).

Ответ `201`: `{ "url": "/uploads/<file>.webp" }`.

Загруженный URL нужно передать в `POST /api/reviews` в массиве `photos` —
**каждый URL должен быть загружен этим же покупателем**, иначе `POST
/api/reviews` вернёт `400`. Подставить чужой/произвольный URL нельзя.

**Техдолг, сознательно не сделано в этой итерации**: неиспользованные
загрузки (покупатель загрузил фото, но так и не отправил отзыв) не
удаляются никаким фоновым механизмом — такого механизма очистки в проекте
ещё нет. Файлы остаются на диске и в таблице `review_uploads` бессрочно.
Не критично для запуска (место дешёвое, объём небольшой), но при росте
стоит добавить периодическую очистку `review_uploads` старше суток без
соответствующего `reviews.photos`.

## 3. Теги

Фиксированный список (владелец их не редактирует, это не пользовательский
текст, а закрытый набор чипов-фильтров):

```ts
type ReviewTagCode =
  | "fast_delivery"   // «Быстрая доставка»
  | "good_packaging"  // «Хорошая упаковка»
  | "fast_reply"      // «Быстрый ответ»
  | "good_quality"    // «Хорошее качество»
  | "no_defects"      // «Отсутствие брака»
  | "as_described"    // «Соответствует описанию»
  | "good_price"      // «Хорошая цена»
  | "polite_seller";  // «Вежливый продавец»
```

### `GET /api/reviews/tags` → `{ code, label }[]`

Без авторизации, статичный список из 8 элементов, порядок как выше.

`POST /api/reviews` принимает `tags: string[]` (0-5 элементов, только коды
из списка выше — незнакомый код или больше 5 штук отдаёт `400`). В ответе
отзыва — `tags: { code, label }[]`, не просто массив кодов (фронту не нужно
самому резолвить label).

**Хранение** (решение и обоснование): `tags` — колонка `JSONB` прямо в
`reviews` (как и `photos`), НЕ отдельная таблица с внешним ключом на
справочник. Причина: справочник тегов фиксирован в коде (`app/domain/reviews/tags.py`),
не таблица в БД — заводить `review_tags`/`review_tag_links` добавило бы
join ради данных, которые и так умещаются в 8 известных строк. `JSONB`
поддерживает `@>` (фильтр по тегу) и `jsonb_array_elements_text` (счётчик
по тегам в публичном списке) — то же самое, что уже понадобилось для
`photos`, единообразно.

## 4. Голоса «полезно / не полезно»

### `PUT /api/reviews/{review_id}/vote` — поставить/снять голос

Требует `Authorization: Bearer <customer JWT>`. Тело: `{ "value": 1 | -1 | 0 }`
(`1` — полезно, `-1` — не полезно, `0` — снять свой голос). Один голос на
покупателя на отзыв — повторный вызов с другим `value` просто переписывает
голос (не копится история).

```json
// ответ 200
{ "likes": 12, "dislikes": 1, "my_vote": 1 }
```

Ошибки:
- `401` — без токена.
- `400` — голос за свой собственный отзыв.
- `404` — отзыв не существует или скрыт модерацией (скрытый отзыв
  недоступен для голосования, как и для публичного просмотра).

Каждый отзыв в ответах (и публичном списке, и панели владельца) теперь
несёт:

```ts
{
  likes: number;
  dislikes: number;
  my_vote: 0 | 1 | -1;  // 0 — без голоса ИЛИ без токена в запросе
}
```

**Токен в публичном списке — опциональный.** `GET
.../products/{id}/reviews` с `Authorization` заполняет `my_vote` для
текущего покупателя; без заголовка (или с истёкшим/невалидным токеном)
эндпоинт не падает `401` — просто у всех отзывов `my_vote: 0`.

## 5. Публичный список — фильтры, сортировка, агрегаты

### `GET /api/storefront/{slug}/products/{product_id}/reviews`

Без обязательной авторизации (см. п.4 про опциональный токен). Новые
query-параметры:

| Параметр | Тип | По умолчанию | Значения |
|---|---|---|---|
| `sort` | string | `date_desc` | `date_desc`, `date_asc`, `rating_desc`, `rating_asc`, `useful` (по `likes - dislikes`) |
| `rating` | int | — | `1`..`5`, точная оценка |
| `with_photos` | bool | `false` | только отзывы с фото |
| `tag` | string | — | код тега из `GET /api/reviews/tags` |
| `limit` | int | `10` | максимум `50` |
| `offset` | int | `0` | — |

Новый ответ (старые поля `reviews`/`average_rating`/`reviews_count`
остались, остальное — новое):

```ts
interface ProductReviewsResponseV2 {
  reviews: ReviewResponseV2[];
  total: number;               // с учётом ТЕКУЩИХ фильтров (rating/with_photos/tag)
  average_rating: number;      // БЕЗ фильтров — по всем видимым отзывам товара
  reviews_count: number;       // БЕЗ фильтров
  rating_distribution: { "5": number; "4": number; "3": number; "2": number; "1": number };  // без фильтров
  with_photos_count: number;   // без фильтров
  tags: { code: string; label: string; count: number }[];  // без фильтров, только count > 0, по убыванию
  photos: { url: string; review_id: number }[];  // последние 30 фото товара — лента «Фото покупателей»
}

interface ReviewResponseV2 {
  id: number;
  product_id: number;
  rating: number;
  text: string;
  author_name: string;
  photo: string;      // устаревшее, см. п.2
  photos: string[];
  tags: { code: string; label: string }[];
  likes: number;
  dislikes: number;
  my_vote: 0 | 1 | -1;
  created_at: string | null;
  is_hidden: boolean | null;  // null у покупателя, true/false у владельца
}
```

**Важно про агрегаты**: `average_rating`, `reviews_count`,
`rating_distribution`, `with_photos_count`, `tags`, `photos` — ВСЕГДА по
полному набору видимых отзывов товара, независимо от `rating`/`with_photos`/`tag`
в запросе. Меняется только `reviews`/`total`. Так гистограмма по звёздам и
чипы тегов остаются стабильным «снимком» товара, по которому можно
переключать фильтр, а не подстраиваются под уже применённый фильтр.

Все агрегаты считаются SQL-агрегатами на стороне БД (не загрузкой всех
отзывов в память) — важно для товаров с сотнями отзывов.

## 6. Можно ли оставить отзыв

### `GET /api/storefront/{slug}/products/{product_id}/reviews/eligibility`

Требует `Authorization: Bearer <customer JWT>`.

```ts
interface ReviewEligibilityResponse {
  can_review: boolean;
  request_id: number | null;   // заявка, которую передать в POST /api/reviews, если can_review
  reason: "ok" | "no_purchase" | "already_reviewed";
}
```

- `no_purchase` — нет ни одной `accepted`-заявки этого покупателя в этом
  магазине с этим товаром.
- `already_reviewed` — есть покупка(и), но на КАЖДУЮ уже оставлен отзыв.
- `ok` — можно оставить, `request_id` — самая свежая подходящая заявка
  (передать её в `POST /api/reviews`).

Это заменяет прежний обходной путь с фронта («дёрнуть
`GET /api/storefront/requests/my` и проверить локально») — теперь есть
прямой ответ одним запросом.

## 7. Владелец

### `GET /api/reviews/product/{product_id}` — изменился формат ответа

Было: `list[ReviewResponse]`. Стало:

```ts
interface OwnerProductReviewsResponse {
  reviews: ReviewResponseV2[];  // is_hidden всегда true/false, likes/dislikes заполнены, my_vote всегда 0 (владелец не голосует)
}
```

**Breaking для фронта, если он уже использовал этот эндпоинт**: раньше
корнем ответа был массив, теперь объект с полем `reviews`. Остальные поля
внутри каждого отзыва — только дополнены.

### `GET /api/reviews?status=all|visible|hidden&limit&offset` — новый эндпоинт

Требует `ORDERS_VIEW`. Все отзывы магазина (по ВСЕМ товарам, не одного) —
для отдельного экрана модерации, без захода в карточку каждого товара.

```ts
interface AllReviewsForOwnerResponse {
  reviews: (ReviewResponseV2 & { product_name: string | null })[];
  total: number;  // с учётом status, для пагинации
}
```

`status` по умолчанию `all`. `limit` по умолчанию `20`, максимум `100`.
`product_name` — название товара, к которому относится отзыв (для строки в
таблице модерации, без похода за каждым товаром отдельно).

## Что нужно сделать на фронте

1. **Форма отзыва**: до показа — дёрнуть `GET .../reviews/eligibility`,
   показывать форму только при `can_review: true`, передавать её
   `request_id` в `POST /api/reviews`. Загрузка фото — сначала `POST
   /api/reviews/photos` для каждого файла (до 5), собрать `url` в массив,
   отправить в `photos` вместе с самим отзывом.
2. **Теги при создании отзыва**: чипы из `GET /api/reviews/tags`,
   мультивыбор до 5.
3. **Карточка отзыва**: 👍/👎 с counters (`likes`/`dislikes`), подсветка
   активной кнопки по `my_vote`; клик по своей же кнопке с тем же значением
   — снять голос (`PUT .../vote { value: 0 }`), либо просто использовать
   `value: 0` явно.
4. **Блок отзывов на карточке товара**: гистограмма по `rating_distribution`,
   чипы тегов с `count` (сортировка уже с бэка), переключатель «Только с
   фото» (`with_photos_count`), лента «Фото покупателей» из `photos` (клик
   по фото — открыть отзыв `review_id`), сортировка `sort` в выпадающем
   списке («Сначала новые» / «Сначала старые» / «Сначала высокая оценка» /
   «Сначала низкая оценка» / «Сначала полезные»).
5. **Панель владельца**: обновить парсинг `GET /api/reviews/product/{id}`
   под новый формат (`{ reviews: [...] }`, не голый массив) — см. breaking
   change в п.7 выше. Добавить отдельный экран/вкладку «Все отзывы» на
   `GET /api/reviews?status=...` с фильтром по статусу и названием товара в
   каждой строке.

## Не реализовано в этой итерации (сознательно)

- Автоматическая очистка неиспользованных `review_uploads` — см. техдолг в
  п.2.
- Ответ владельца на отзыв — по-прежнему не в этой итерации (перенесено из
  v1).
- Похожие товары / карусель рекомендаций рядом с отзывами — отдельный
  промпт (B4), не пересекается с этим доменом.

# Отзывы и рейтинг товара — v1 (исходная версия)

Новый домен: покупатель, купивший товар через витрину (заявка принята
владельцем), может оставить отзыв с оценкой 1-5, текстом и опциональным фото.
Рейтинг агрегируется на карточке товара и в каталоге. Владелец модерирует
(скрыть/вернуть), ответ владельца на отзыв — не в этой итерации.

**Этот раздел описывает исходный контракт (до промпта B3). Актуальные
изменения — в разделе «v2» выше: исправленная уникальность, несколько
фото, теги, голоса, фильтры публичного списка, проверка возможности
отзыва, список для модерации.**

---

## Кто может оставить отзыв

Только авторизованный покупатель (см. `customer_auth.md`), у которого есть
своя заявка (`StorefrontRequest`) в статусе `accepted`, содержащая этот товар.
Один отзыв на одну заявку — повторно по той же заявке отправить нельзя (400).
Анонимные отзывы невозможны — нет отдельного access_token флоу, как у чата.

**Уточнение из v2**: «один отзыв на заявку» на самом деле было багом —
правильно «один отзыв на пару (заявка, товар)», исправлено в v2 п.1.

## Эндпоинты

### `POST /api/reviews` — оставить отзыв

Требует `Authorization: Bearer <customer JWT>`.

```json
{
  "storefront_request_id": 123,
  "product_id": 45,
  "rating": 5,
  "text": "Очень доволен покупкой",
  "photo": ""
}
```

- `rating` — целое 1..5, обязательно.
- `text` — до 2000 символов, можно пустым, если есть `photo`.
- `photo` — URL/путь загруженного файла (используйте существующий upload-флоу
  для фото, как у товаров), необязателен.

Ответ `201`:
```json
{
  "id": 1, "product_id": 45, "rating": 5, "text": "Очень доволен покупкой",
  "author_name": "Ахмед", "photo": "", "created_at": "2026-09-16T12:00:00+00:00",
  "is_hidden": null
}
```
`is_hidden` всегда `null` в этом ответе и в публичном списке — покупателю не
показываем состояние модерации (см. ниже, отдельно для владельца).

Ошибки:
- `401` — не авторизован.
- `403` — заявка не в статусе `accepted` (ещё новая/отклонена).
- `404` — заявка не найдена или принадлежит другому покупателю.
- `400` — товара не было в составе этой заявки, ИЛИ отзыв по заявке уже есть.

### `GET /api/storefront/{slug}/products/{product_id}/reviews` — публичный список

Без авторизации. Возвращает только видимые (не скрытые владельцем) отзывы.

```json
{
  "reviews": [
    {
      "id": 1, "product_id": 45, "rating": 5, "text": "Очень доволен покупкой",
      "author_name": "Ахмед", "photo": "", "created_at": "2026-09-16T12:00:00+00:00",
      "is_hidden": null
    }
  ],
  "average_rating": 5.0,
  "reviews_count": 1
}
```

Товар без отзывов — `reviews: []`, `average_rating: 0.0`, `reviews_count: 0`.

### `GET /api/reviews/product/{product_id}` — для владельца (панель управления)

Требует роль с правом `ORDERS_VIEW` (owner/manager и т.п.). Возвращает ВСЕ
отзывы товара, включая скрытые — `is_hidden` здесь `true`/`false` (не `null`).

### `POST /api/reviews/{review_id}/hide` и `/unhide` — модерация

Требует `ORDERS_MANAGE`. Скрывает/возвращает отзыв — не удаление, история
сохраняется. Скрытый отзыв пропадает из публичного списка и из агрегата
рейтинга (среднее и счётчик пересчитываются без него).

## Рейтинг на карточках каталога и товара

Существующие ответы получили два новых поля — считаются только по видимым
(не скрытым) отзывам:

- `GET /api/storefront/{slug}` (каталог) — у каждого товара в `products[]`
  теперь есть `average_rating: float` и `reviews_count: int`.
- `GET /api/storefront/{slug}/products/{id}` (карточка) — те же два поля
  внутри `product`.

Товар без отзывов — `average_rating: 0.0`, `reviews_count: 0` (не `null`,
не отсутствие полей).

## Что нужно сделать на фронте (v1, см. актуальный список в v2 выше)

1. **Карточка товара на витрине**: блок отзывов — список из
   `GET .../reviews`, средний рейтинг звёздами, число отзывов. Форма отправки
   отзыва видна только покупателю, у которого для этого товара есть
   `accepted`-заявка без отзыва — самый простой способ узнать это: дёрнуть
   `GET /api/storefront/requests/my` (уже существует, см. `customer_auth.md`)
   и проверить на фронте локально, нет отдельного эндпоинта
   «доступен ли мне отзыв на этот товар».
2. **Каталог**: бейдж рейтинга (звезда + число) на карточке товара в сетке —
   рядом с `sold_count` (см. `storefront_sold_count.md`), скрывать при
   `reviews_count == 0`, как и `sold_count == 0`.
3. **Панель владельца**: список отзывов по товару (например, вкладка в
   карточке товара в админке) с кнопкой скрыть/вернуть каждого отзыва.
4. Дизайн — звёзды 1-5, стандартный паттерн, оформить в цветах ВайСклада (см.
   оговорку в `customer_auth.md` про wikkeo — не копировать визуал 1-в-1).

## Не реализовано в этой итерации (сознательно, v1)

- Ответ владельца на отзыв.
- Фото в отзыве не проходит отдельную валидацию/модерацию на бэке — тот же
  upload-флоу, что у остальных изображений, ответственность за контент на
  покупателе.
- Агрегат рейтинга по магазину в целом (страница `/store/{slug}`, не только
  по товару) — не сделано, можно добавить позже как `avg` по всем товарам
  tenant'а без новой сущности. **(Сделано отдельно в промпте B2 — см.
  `product_page_v2.md`.)**
- Фильтр каталога «от N звёзд» — не сделано (было предложение из
