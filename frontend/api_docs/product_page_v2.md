# Карточка товара витрины v2 (B1): варианты, наличие, гарантия, просмотры

Первая часть бэкенда под новую карточку товара витрины «как на wikkeo» (см.
`docs/PRODUCT_PAGE_PROMPTS.md`, промпт B1). Правая колонка (магазин, FAQ,
минимальная сумма заказа), отзывы v2 и похожие товары — в следующих частях
(B2/B3/B4), здесь их ещё нет. Фронтенд не менялся.

**Эндпоинт:** `GET /api/storefront/{slug}/products/{product_id}` — контракт
не сломан, только добавлены поля. `GET /api/storefront/{slug}` (каталог) не
менялся вообще, кроме `PATCH /api/auth/shop` — см. п.6.

---

## 1. Название варианта

`ProductVariant` получил поле `name` (в панели владельца — подсказка
«например, Aurum. Если пусто — цвет · размер»). На витрине у каждого
варианта теперь два поля:

```ts
{
  name: string,          // как задал владелец, может быть ""
  display_name: string,  // готовая строка для показа — см. правило ниже
}
```

`display_name`:
1. `name`, если не пустой (обрезка пробелов) — например, `"Aurum"`.
2. Иначе `"color · size"` — только непустые части через ` · `. Например,
   цвет "Красный" + размер "M" → `"Красный · M"`; только цвет → `"Красный"`.
3. Иначе (нет ни имени, ни цвета, ни размера) — `"Вариант N"`, где `N` —
   порядковый номер варианта в списке товара (с 1).

Владелец: `POST/PUT /api/products` и `.../variants/*` принимают/отдают
`name` в объекте варианта — то же место, что `size`/`color`.

## 2. Наличие по вариантам и уровень запаса

Раньше `in_stock` считался только по товару целиком — вариант без остатка
выглядел доступным. Теперь у каждого варианта есть собственное наличие, и у
товара с вариантами тоже появился более информативный статус:

```ts
{
  in_stock: boolean,               // не изменился по смыслу — уже был
  stock_level: "out" | "low" | "in",
  stock_qty: string | null,        // см. ниже про настройку магазина
  variants: {
    // ...
    in_stock: boolean,             // НОВОЕ — наличие именно этого варианта
    stock_level: "out" | "low" | "in",
    stock_qty: string | null,
  }[],
}
```

`stock_level` (и у товара, и у каждого варианта):
- `"out"` — остаток `<= 0`.
- `"low"` — остаток `> 0` и `<= min_stock` (если у товара задан `min_stock >
  0`), иначе порог `<= 3` (владелец не настраивал порог — используется
  разумное значение по умолчанию).
- `"in"` — остаток выше порога.

Остаток считается только по складам, у которых включён показ на витрине
(`Warehouse.show_on_storefront`) — как и раньше у `in_stock`. **Уточнение
поведения:** до этого промпта `in_stock` карточки товара (не каталога!) не
учитывал видимость складов вообще — это было расхождение с каталогом,
исправлено попутно: теперь оба эндпоинта считают наличие одинаково.

`stock_qty: string | null` — точный остаток. Заполнен **только** если у
магазина включена новая настройка (см. п.6), иначе всегда `null` — и у
товара, и у всех вариантов. Остаток скрытых от витрины складов никогда не
попадает ни в `stock_qty`, ни в наличие, даже если настройка включена.

**Известное ограничение (сознательно не сделано в B1):** `GET
/api/storefront/{slug}` (каталог) с фильтрами `?in_stock_only=true` и
`?variant_size=/?variant_color=` продолжают работать независимо друг от
друга — `in_stock_only` фильтрует по остатку **товара целиком** (сумма по
всем вариантам), а не по остатку именно того варианта, что подошёл под
`variant_size`/`variant_color`. Пример: товар «Платье» с размерами S (нет в
наличии) и M (в наличии) — фильтр `variant_size=S&in_stock_only=true` всё
равно покажет товар в списке, хотя нужного размера нет. На карточке товара
(этот документ) наличие каждого варианта уже показано honestly — ограничение
касается только списка/каталога. Точечный fix потребовал бы соединять
фильтр вариантов с остатком внутри одного SQL-условия — отложено, не было
явно приоритетным в промпте.

## 3. Категория и единица измерения

```ts
{
  category: {
    id: number,
    name: string,
    parent: { id: number, name: string } | null,
  } | null,          // null — у товара не выбрана категория
  unit_code: string,  // "pcs", "kg", "l", "m", ...
  unit_label: string, // "шт", "кг", "л", "м", "упаковка", ...
}
```

`unit_label` — человекочитаемое название из существующего справочника единиц
(тот же, что уже используется в панели владельца), не новый список.

## 4. Гарантия

Новое поле товара `warranty_text` (`Text`, до 5000 символов, по умолчанию
`""`) — тот же характер поля, что `description`. Принимается/отдаётся в
`POST/PUT /api/products` (панель владельца) как обычное текстовое поле.

На витрине: `product.warranty_text` — **только в карточке одного товара**,
в каталоге (`GET /api/storefront/{slug}`, список) поля нет — список
специально остаётся лёгким.

---

## 5. Просмотры товара

### `POST /api/storefront/{slug}/products/{product_id}/view` → `204`

Без авторизации, без тела запроса. Вызывать один раз при открытии карточки
товара (см. `useEffect` + `ref`-защита от двойного вызова в StrictMode —
шаблон уже описан в `F1` серии фронтенд-промптов).

- Rate limit `120/минуту` на IP.
- Дедупликация: повторный вызов с того же IP по тому же товару **в течение
  30 минут** не увеличивает счётчик просмотров (тихо отвечает `204` в любом
  случае — фронту не нужно различать «засчитано»/«уже считали»).
- `404` — товар не существует, скрыт (`show_on_storefront: false`) или
  витрина магазина выключена/не существует. Те же случаи, что у самой
  карточки товара.

В ответе карточки:

```ts
{ views_90d: number }  // сумма просмотров за последние 90 дней (включая сегодня)
```

Хранится агрегатом по дням (`tenant_id, product_id, day, count`), не сырыми
событиями — `views_90d` не может показать «кто именно смотрел», только
сумму. Просмотры **не сбрасывают кэш карточки** (TTL кэша — 20 секунд) —
`views_90d` пересчитывается отдельным быстрым запросом при каждом обращении
к карточке, поэтому не отстаёт от факта даже при кэш-хите на остальные поля.

## 6. Настройка магазина: показывать точный остаток

Новое поле `Tenant.storefront_show_stock_qty` (`bool`, по умолчанию
`false`) — управляет видимостью `stock_qty` у товара и вариантов (п.2).

```ts
// GET /api/auth/shop — TenantResponse, новое поле
{ storefront_show_stock_qty: boolean }

// PATCH /api/auth/shop — UpdateShopRequest, новое опциональное поле
{ storefront_show_stock_qty?: boolean }
```

По умолчанию выключено — владелец сам решает, раскрывать ли конкурентам
объём своих продаж/остатков. Панель владельца: переключатель «Показывать
точный остаток на витрине» (в разделе настроек магазина — см. также B2, где
там же появятся остальные поля профиля витрины).

## Что нужно сделать на фронте

Ничего немедленно обязательного — контракт только пополнился, старые поля
не изменились по форме. Когда дойдёт очередь до реализации новой вёрстки
карточки товара (серия `F0`–`F8`):

1. **Список вариантов** — использовать `display_name` вместо ручной сборки
   из `size`/`color` на фронте; для остатка — `stockText(variant)` по
   правилу: `stock_qty` есть → «Осталось N шт»; иначе по `stock_level`:
   `"low"` → «Мало», `"out"` → «Нет в наличии», `"in"` → «В наличии».
2. **Наличие варианта** (`variants[].in_stock`) — приглушать строку варианта
   и скрывать степпер, если `false` (сейчас на фронте наличие вариантов не
   проверяется вообще — известный баг из README, п. «Найденные проблемы»).
3. **Категория** — хлебные крошки «Каталог › `category.parent.name` ›
   `category.name`» (при `category: null` — просто «Каталог»).
4. **Единица** — строка цены «`retail_price` ₽ за `unit_label`».
5. **Гарантии** — блок «Гарантии» с `warranty_text`, тот же компонент
   `ExpandableText`, что и «О товаре»; пусто → блок не рендерить.
6. **Просмотры** — вызвать `POST .../view` один раз при открытии страницы
   (после первой успешной загрузки карточки, не блокируя рендер);
   показывать «`views_90d` просмотров за 90 дней», только если `views_90d
   >= 10` (порог решает фронт, сервер не фильтрует).
7. **Настройки магазина** — переключатель «Показывать точный остаток на
   витрине» (`storefront_show_stock_qty`) в форме, где уже редактируется
   `storefront_enabled`.
8. **Форма товара владельца** — поле «Гарантия» (textarea, до 5000
   символов) рядом с «Описанием»; у варианта — поле «Название» с подсказкой
   «например, Aurum. Если пусто — цвет · размер».

# Часть B2: публичный профиль магазина — лого, рейтинг, контакты, FAQ, минимальная сумма заказа

Вторая часть бэкенда под новую карточку товара витрины (см. `docs/PRODUCT_PAGE_PROMPTS.md`,
промпт B2). Правая колонка карточки товара: карточка продавца, FAQ, кнопка
«Написать», прогресс до минимальной суммы заказа. Опирается на B1 (раздел
выше в этом же файле) — компоновка страницы и общий контекст не повторяются.
Отзывы v2 (несколько фото, теги, голоса) и похожие товары — в следующих
частях (B3/B4), здесь их ещё нет. Фронтенд не менялся.

## 1. Настройки магазина — контакты, описание, политики, минимальная сумма

`GET/PATCH /api/auth/shop` (`TenantResponse`/`UpdateShopRequest`) получили:

```ts
{
  storefront_description: string;   // до 500 символов, короткое "о магазине"
  contact_phone: string;            // формат как у обычного телефона (Phone) — "+79280001122"
  contact_whatsapp: string;         // тот же формат телефона, отдельное поле от contact_phone
  contact_telegram: string;         // username БЕЗ "@" — сервер сам обрежет "@", если прислать с ним;
                                     // 5-32 символа, латиница/цифры/подчёркивание, с буквы
  storefront_min_order_total: string | null;  // "1000.00" — Decimal с 2 знаками, как у цен
  policy_refund_money: string;      // до 5000 символов каждое; "" по умолчанию
  policy_payment: string;
  policy_delivery: string;
  policy_returns: string;
}
```

Важно для формы настроек:

- Все поля необязательные в `PATCH` — отсутствие поля в body не трогает
  текущее значение (обычный PATCH-принцип, как у `city`/`storefront_enabled`).
- **Единственное исключение** — `storefront_min_order_total`: явный `null` в
  body **сбрасывает** лимит (магазин снова принимает заказы любой суммы).
  Если поле просто отсутствует в body — значение не меняется. Строка/число —
  устанавливает новый лимит.
- `contact_phone`/`contact_whatsapp` валидируются как обычный телефон
  (национальный формат `89280001122` тоже принимается и приводится к
  `+7...`) — невалидный формат вернёт `400`. Пустая строка `""` — способ
  контакта не задан, это валидно (не ошибка).
- `contact_telegram`: можно прислать с `@` или без — сервер всегда отдаёт
  без `@`, собирайте `https://t.me/{contact_telegram}` на фронте сами.
- Логотип магазина — **то же поле `logo`**, что уже было в `TenantResponse`
  с B1 (`POST /api/auth/shop/logo`, multipart file, уже был реализован до
  B2). Новое здесь — **`DELETE /api/auth/shop/logo`**: сбрасывает `logo` в
  `""` и удаляет файл. Симметрично POST, тот же `TenantResponse` в ответе.
  Промпт B2 упоминал поле как `storefront_logo` — на бэкенде это ровно то же
  самое существующее поле `logo`, отдельного поля с именем `storefront_logo`
  нет и не будет.

## 2. Публичный профиль магазина

### `GET /api/storefront/{slug}/profile` → `StorefrontProfileResponse`

Без авторизации, кэш 60 секунд (профиль меняется реже каталога — TTL длиннее,
чем у каталога/карточки товара, которые кешируются на 20с). `404` — те же
случаи, что у каталога (магазин не существует, витрина выключена,
`is_suspended`).

```ts
interface StorefrontProfileRatingResponse {
  average_rating: number;
  reviews_count: number;
}

interface StorefrontProfileContactsResponse {
  phone: string;
  whatsapp: string;
  telegram: string;      // без "@"
}

interface StorefrontProfileAddressResponse {
  name: string;           // название склада
  address: string;
}

interface StorefrontProfilePoliciesResponse {
  refund_money: string | null;   // null, если владелец не заполнил — не рисовать пункт FAQ вообще
  payment: string | null;
  delivery: string | null;
  returns: string | null;
}

interface StorefrontProfileResponse {
  name: string;
  slug: string;
  logo: string;
  description: string;
  on_platform_since: string;      // "2026-09-18" — дата регистрации магазина (ISO date, не datetime)
  rating: StorefrontProfileRatingResponse;   // по ВСЕМ товарам магазина, не одного
  products_count: number;         // show_on_storefront && is_active
  orders_count: number | null;    // null — магазин новый, см. ниже
  orders_count_label: string | null;  // готовая строка "2000+"/"150+"/"12", null вместе с orders_count
  min_order_total: string | null; // "1000.00" — Decimal-строка, как у цен
  contacts: StorefrontProfileContactsResponse;
  addresses: StorefrontProfileAddressResponse[];   // только склады с show_on_storefront
  policies: StorefrontProfilePoliciesResponse;
}
```

**`rating`** — среднее и число **видимых** (не скрытых модерацией) отзывов
по **всем** товарам магазина, не одного конкретного. Скрытие/показ отзыва
владельцем сразу меняет это число (без ожидания TTL кеша — инвалидация кеша
происходит явно при каждой мутации отзыва).

**`products_count`** — количество товаров с `show_on_storefront=true` и
`is_active=true`, то же самое множество, что участвует в каталоге.

**`orders_count`** — принятые заявки с витрины (`accept`) + обычные продажи
магазина (не только через витрину — любая продажа считается «заказом» для
этого счётчика). **Решение по скрытию**: если суммарное число заказов **меньше
5**, `orders_count` и `orders_count_label` отдаются как `null` — у совсем
нового магазина «Заказов: 2» выглядит скорее как повод усомниться, чем как
довод в пользу покупки, лучше не показывать счётчик вообще, чем показывать
маленькое число. Порог `5` выбран тем же порядком величины, что «минимум 5
продаж» у бейджа «Хит» на маркетплейсе — общий язык сигналов доверия
платформы. **На фронте**: если `orders_count === null`, не рисовать строку
«Заказов» в карточке продавца вообще (не показывать «Заказов: —» и не «0»).

**`orders_count_label`** — готовая строка для показа, вычисляется на
бэкенде: числа **ниже 50** отдаются точно ("12", "37"), от 50 и выше —
округление вниз с шагом, зависящим от порядка величины (шаг 10 для
диапазона 50-99, 50 для 100-499, 100 для 500-999, 500 для 1000-4999, 1000
дальше), с суффиксом `"+"` ("50+", "150+", "1000+", "2734" → "2500+").
Фронту не нужно ничего пересчитывать — просто показать строку как есть.

**`min_order_total`** — то же значение, что и в `PATCH /api/auth/shop`
(`storefront_min_order_total`), продублировано здесь для удобства публичной
страницы (профиль магазина грузится отдельным запросом от настроек
владельца).

**`addresses`** — только склады с `show_on_storefront=true`, тот же набор,
что уже был в `warehouses` каталога (`GET /api/storefront/{slug}`), но здесь
в форме `{name, address}` без `id` (публичный профиль не предполагает выбора
конкретного склада, только показ «Где нас найти»).

**`policies`** — если владелец не заполнил текст (пустая строка `""` в
настройках), поле в ответе — `null`, не `""`. Так фронт может отличить
«пункт FAQ не нужно рисовать» от «пункт есть, но пустой текст».

### Что на фронте

- **Карточка продавца** (правая колонка карточки товара, блок с лого) —
  `logo`, `name`, `rating.average_rating` + `★`, `rating.reviews_count`
  («1273 отзыва»), `"На ВайСклад с " + formatMonthYear(on_platform_since)`,
  строка `products_count` «товаров» / `orders_count_label` «заказов» (весь
  блок с заказами скрыт, если `orders_count === null`) / `min_order_total`
  «мин. заказ». Клик по карточке — переход на `/store/{slug}` (каталог).
- **FAQ-модалки** — 4 пункта («Возврат денег», «Оплата», «Доставка», «Возврат
  товаров»), рисовать только те, где `policies.<ключ> !== null`. Открывать в
  модалке с текстом пункта.
- **Кнопка «Написать»** — открывает меню контактов
  (`contacts.whatsapp`/`contacts.telegram`/`contacts.phone`), пропускать
  пустые строки (способ связи не настроен). WhatsApp:
  `https://wa.me/{phone без "+"}`, Telegram: `https://t.me/{telegram}`,
  телефон — `tel:{phone}`.
- **Прогресс до минимальной суммы заказа** — вместо блока со скидками
  wikkeo: если `min_order_total !== null`, в корзине/на карточке товара
  показывать `"До минимального заказа осталось {max(0, min_order_total -
  текущая сумма корзины)} ₽"` с прогресс-баром `текущая_сумма /
  min_order_total`; когда сумма уже достигнута — плашку не показывать вообще.
- **Форма настроек магазина владельца** — новый раздел «Профиль витрины»:
  описание (textarea, счётчик до 500 символов), три поля контактов, поле
  минимальной суммы заказа (с кнопкой «Убрать лимит», которая шлёт явный
  `null`), 4 textarea для FAQ (до 5000 символов каждое, показывать счётчик).
  Логотип — уже существующий загрузчик (`POST /api/auth/shop/logo`),
  добавить кнопку «Удалить логотип» → `DELETE /api/auth/shop/logo`.

## 3. Короткий профиль магазина в карточке товара

`GET /api/storefront/{slug}/products/{product_id}` (`product`, не корень
ответа) получил новое поле `shop`:

```ts
interface StorefrontProductShopResponse {
  slug: string;
  name: string;
  logo: string;
  average_rating: number;   // рейтинг МАГАЗИНА (все товары), не рейтинг этого товара —
  reviews_count: number;    // для этого товара используйте product.average_rating/reviews_count, как раньше
}

// StorefrontProductDetailResponseV2 (B1) получил:
interface StorefrontProductDetailResponseV2 {
  // ...поля B1 без изменений...
  shop: StorefrontProductShopResponse;   // новое в B2
}
```

Цель — нарисовать шапку карточки товара (мини-блок продавца) без второго
запроса к `/profile`. Если нужна полная карточка магазина (адреса, FAQ,
контакты, `products_count`/`orders_count`) — грузите `GET
/api/storefront/{slug}/profile` отдельно (обычно лениво, когда пользователь
доскроллил до блока продавца или открыл его).

## 4. Минимальная сумма заказа при оформлении заявки

`POST /api/storefront/{slug}/requests` — если сумма заявки по серверным
ценам (розничная цена товара, либо цена конкретного варианта, если она
задана) меньше `storefront_min_order_total` магазина — `400`:

```json
{ "detail": "Минимальная сумма заказа в этом магазине — 1000 ₽" }
```

Число в тексте — без разделителя тысяч (в кодовой базе нет общего хелпера
форматирования денег, текст ошибки в едином стиле с остальными денежными
ошибками проекта). Граница включительная: сумма заявки **ровно равная**
минимуму проходит (строгое `<`, не `<=`). Если `storefront_min_order_total`
не задан (`null`) — проверка не применяется вообще, как и раньше.

Попутно исправлен баг: до B2 сумма заявки (и в проверке минимума, и в
тексте уведомления владельцу о новой заявке) считалась по `retail_price`
товара, даже если у выбранного варианта задана своя цена (`variants[].price`)
— теперь везде используется цена варианта, если она есть, иначе `retail_price`
товара, тот же приоритет, что уже был на витрине.

`GET /api/storefront/{slug}` (каталог) получил `min_order_total: string |
null` — то же значение, для прогресс-бара на странице каталога/корзины без
отдельного похода за профилем.

## 5. OG-превью магазина

`GET /api/storefront/{slug}/og` — OG-превью каталога магазина для ботов
соцсетей — теперь использует `logo` магазина как `og:image`, если он задан
(раньше OG каталога был без картинки вообще). OG карточки товара
(`.../products/{id}/og`) не менялся — там по-прежнему фото товара.

## 6. Изменения, важные для существующих экранов

- `TenantResponse` (`GET/PATCH /api/auth/shop`) — только добавленные поля,
  см. раздел 1, ничего не переименовано и не убрано.
- Если фронт уже где-то использовал `POST /api/auth/shop/logo` — контракт
  ответа (`TenantResponse`) не изменился.
