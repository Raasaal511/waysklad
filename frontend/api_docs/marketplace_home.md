# Главная маркетплейса M-B1: категории платформы, город, проверенный магазин, старая цена

Первая часть бэкенда под главную страницу маркетплейса «как на wikkeo» (см.
`docs/MARKETPLACE_HOME_PROMPTS.md`, промпт M-B1). Баннеры и единый эндпоинт
`GET /api/marketplace/home` — в следующей части (M-B2), здесь их ещё нет.

---

## 1. Справочник категорий платформы

Новая таблица `platform_categories` — общий для всех магазинов список
категорий (Электроника, Одежда, Обувь, Инструменты, Автотовары, Аксессуары,
Продукты, Для дома, Красота, Детские товары, Строительство, Прочее), не
привязанный к tenant. Категория магазина (`Category`, та, что владелец
заводит себе в товарах) теперь может опционально ссылаться на платформенную
через `platform_category_id`.

### `GET /api/marketplace/categories?city=<name>`

Публично, без авторизации. Rate limit 300/минуту.

```ts
{
  categories: {
    id: number,
    slug: string,
    name: string,
    image: string,        // путь картинки или "" — своей заглушки нет
    parent_id: number | null,
    products_count: number,
  }[]
}
```

Только активные категории (`is_active: true` в админке) и только те, где
`products_count > 0` — пустые категории не отдаются вовсе. Счётчик — видимые
товары видимых магазинов (`storefront_enabled: true`, `is_suspended: false`,
`show_on_storefront: true` у товара), с учётом `?city=`, если передан.
Кешируется на backend 5 минут.

Тот же эндпоинт используется владельцем для выпадающего списка «Категория на
маркетплейсе» в форме своей категории (`?city=` там не нужен).

### `GET /api/marketplace/products` — новый параметр `platform_category`

```ts
{
  platform_category?: string,  // slug, включает дочерние категории
  category?: string,           // старое поле (точное совпадение названия) — оставлено для совместимости
}
```

`platform_category=shoes` находит товары не только напрямую сопоставленной
категории «Обувь», но и всех её дочерних платформенных категорий (один
уровень вложенности). Неизвестный slug — пустой результат (`total: 0`), не
ошибка. Оба параметра (`category` и `platform_category`) можно передавать
одновременно — сужают выборку совместно (AND), обычно используется только
один.

### Владелец: PUT категории теперь принимает `platform_category_id`

**`POST /api/products/categories`** и новый **`PUT
/api/products/categories/{category_id}`**:

```ts
// запрос (оба эндпоинта)
{ name: string, parent_id?: number | null, platform_category_id?: number | null }
// ответ — CategoryResponse
{ id: number, name: string, parent_id: number | null, platform_category_id: number | null }
```

`PUT` — новый эндпоинт (раньше категорию нельзя было редактировать вообще,
только создать). `platform_category_id` не валидируется на существование —
неверный/несуществующий id просто не найдёт совпадений в справочнике
дальше по цепочке (не 400).

### Автосопоставление существующих категорий (одноразовый скрипт, не API)

`backend/scripts/map_platform_categories.py` — сопоставляет уже существующие
категории всех магазинов с платформенными по нормализованному названию
(lower, trim, ё→е) и словарю синонимов (например «кроссовки», «туфли» →
Обувь). Несопоставленные остаются `platform_category_id: null`, владелец
может выбрать вручную позже. Безопасно перезапускать — уже сопоставленные
категории пропускаются. Не касается фронта — разовая серверная миграция
данных, не эндпоинт.

### Админка (`require admin`, тот же JWT, что у остального `/api/admin/*`)

```
GET    /api/admin/platform-categories
POST   /api/admin/platform-categories
PUT    /api/admin/platform-categories/{id}
DELETE /api/admin/platform-categories/{id}
POST   /api/admin/platform-categories/{id}/image   (multipart, поле "file")
```

```ts
// PlatformCategoryResponse (все методы, кроме DELETE без привязок)
{
  id: number, name: string, slug: string, image: string,
  sort_order: number, is_active: boolean, parent_id: number | null,
}
```

`POST`/`PUT` тело:
```ts
{ name: string, slug: string, sort_order?: number, parent_id?: number | null, is_active?: boolean /* только PUT */ }
```

`slug` должен быть уникален — иначе `400`. Родитель обязан сам не иметь
родителя (только один уровень вложенности) — иначе `400`. `DELETE` — мягкое
отключение (`is_active: false`), если на категорию ссылается хоть одна
категория магазина или дочерняя платформенная категория; иначе — физическое
удаление. В обоих случаях `200` с телом категории (не `204`) — чтобы фронт
видел, было ли удаление мягким или полным, по полю `is_active` в ответе.

**На фронте (админка):** дерево категорий с картинкой, порядком,
активностью — раздел «Категории платформы» (см. чек-лист M-F6).

## 2. Город магазина

`Tenant` получил поле `city: string | null`. Справочник — константа на
бэкенде (расширяется только сервером, не query-параметром):

```
Грозный, Урус-Мартан, Гудермес, Шали, Аргун, Курчалой, Ачхой-Мартан, Наурская, Другой
```

### `GET`/`PATCH /api/auth/shop`

`TenantResponse` получил `city: string | null`. `UpdateShopRequest` —
новое опциональное поле `city?: string`. Как и остальные опциональные поля
этого эндпоинта (`summary_*`, `storefront_enabled`) — **если не передать,
город не меняется** (не PATCH-семантика null=сброс; явного способа снять уже
выбранный город на этом эндпоинте пока нет). Неизвестное значение (не из
справочника) → `400` с `detail` вида `«Неизвестный город: «Москва»»`.

### `GET /api/marketplace/cities`

Публично, без авторизации.

```ts
{ cities: { name: string, shops_count: number }[] }
```

Только города, где есть хотя бы один магазин с `storefront_enabled: true` и
`is_suspended: false`. Отсортировано по названию. Кешируется 5 минут.

### `GET /api/marketplace/products` — новый параметр `city`

```ts
{ city?: string }
```

Точное совпадение `Tenant.city`. Комбинируется с остальными фильтрами.

**На фронте:**
1. Поповер выбора города в шапке — список из `GET /api/marketplace/cities`,
   пункт «Все города» первым (означает отсутствие параметра `city`).
2. Настройки магазина у владельца — селект «Город» из фиксированного списка
   (значения см. выше — раз справочник не отдаётся отдельным эндпоинтом,
   продублируйте список констант на фронте; если список изменится на
   бэкенде, дайте знать, актуализируем документ).

## 3. Проверенный магазин

`Tenant.is_verified: boolean`, по умолчанию `false`. Меняется **только**
админом платформы — владелец никак не может повлиять сам.

### `POST /api/admin/tenants/{id}/verify` и `.../unverify`

Без тела запроса, по образцу `suspend`/`unsuspend`. Ответ (`200`) —
`TenantDetailResponse` с обновлённым `is_verified`. `404` — магазин не
найден.

`GET /api/admin/tenants` и `GET /api/admin/tenants/{id}` — оба получили поле
`is_verified: boolean`.

Действует немедленно — кеш витрины и кеш общего каталога маркетплейса
чистятся сразу при verify/unverify (не нужно ждать TTL, чтобы значок
появился/исчез).

**На фронте (админка):** переключатель «Проверенный магазин» в карточке
магазина (см. чек-лист M-F6).

## 4. Старая цена товара (обычная розничная скидка, не оптовая)

`Product.compare_at_price: string | null`. Владелец задаёт её в форме товара
рядом с обычной ценой.

### `POST /api/products` и `PUT /api/products/{id}`

```ts
{ compare_at_price?: string | null }  // например "1800"
```

**Валидация:** `null`, либо строго больше `retail_price` — иначе `400`
`{"detail": "Старая цена должна быть больше текущей"}`. Исключение: если
`compare_at_price` в запросе совпадает с уже сохранённым значением товара
(его не меняют, просто пере-отправляют форму целиком), а `retail_price` при
этом подняли выше старой цены — запрос **не отклоняется**, старая цена
остаётся в БД как есть, просто перестаёт быть видна на витрине (см. ниже).
Отклоняется только попытка **задать/изменить** `compare_at_price` на
значение ≤ `retail_price`.

`ProductResponse` (создание/обновление/список товаров владельцу) получил
`compare_at_price: string | null` — значение как оно хранится в БД, без
скрытия (владелец должен видеть, что сам ввёл, даже если сейчас оно
временно не показывается на витрине).

### Витрина и маркетплейс — `old_price` и `discount_percent`

`GET /api/storefront/{slug}` (список), `GET /api/storefront/{slug}/products/{id}`
(карточка), `GET /api/marketplace/products` (список), `GET
/api/marketplace/products/{id}` (карточка) — каждый товар получил:

```ts
{
  old_price: string | null,       // зачёркнутая цена
  discount_percent: number | null, // округление вниз, например 20 — «-20%»
}
```

**Оба поля — `null` одновременно** в трёх случаях: скидки не задано;
`retail_price` подняли выше `compare_at_price` (скидка «выключилась» сама,
без изменения `compare_at_price` в БД); скидка меньше 3% (например 195 от
200 — это 2.5%, визуальный шум от копеечной разницы, не показываем). Когда
`discount_percent` не `null`, `old_price` всегда равен `compare_at_price` из
БД.

### Фильтр `with_discount`

**`GET /api/marketplace/products`** и **`GET /api/storefront/{slug}`** —
новый параметр:

```ts
{ with_discount?: boolean }
```

`true` — только товары, у которых `discount_percent` не `null` (то есть
ровно те, что реально показывают зачёркнутую цену — товар со скидкой 2%
фильтром не считается «со скидкой»).

### На деньги не влияет

`compare_at_price` — только витринное отображение. Заявка с витрины
(`POST /api/storefront/{slug}/requests`) и последующий заказ по-прежнему
считаются по `retail_price`. Ничего в оформлении заявки не меняется.

**На фронте:**
1. Форма товара — поле «Старая цена» рядом с «Розничная цена», с живой
   подсказкой вида «Скидка 20% будет видна покупателям», когда оба поля
   заполнены и `compare_at_price > retail_price` (посчитать на фронте,
   бэкенд эту подсказку не отдаёт).
2. Карточка товара (список и детальная, витрина и маркетплейс) — если
   `old_price` не `null`, показывать зачёркнутой рядом с `retail_price`, и
   бейдж `-{discount_percent}%`.
3. Чекбокс/чип «Со скидкой» в фильтрах каталога → `with_discount=true`.

## 5. Новые поля карточки маркетплейса

**`GET /api/marketplace/products`** — каждый товар в списке получил:

```ts
{
  shop_logo: string,          // путь логотипа магазина или "" — заглушки нет
  shop_is_verified: boolean,
  shop_city: string | null,
  old_price: string | null,        // см. раздел 4
  discount_percent: number | null, // см. раздел 4
  is_new: boolean,   // created_at товара за последние 14 дней
  is_hit: boolean,   // топ-10% по продажам за 30 дней среди видимых товаров платформы, минимум 5 продаж
}
```

**`GET /api/marketplace/products/{id}`** — карточка одного товара получила
на верхнем уровне ответа (не внутри `product`):

```ts
{
  shop_logo: string,
  shop_is_verified: boolean,
  shop_city: string | null,
  is_new: boolean,
  is_hit: boolean,
  product: { /* без изменений, кроме old_price/discount_percent — см. раздел 4 */ },
}
```

**`is_hit`** — пакетный расчёт (не построчный запрос на каждый товар):
среди всех видимых товаров платформы с ≥5 продажами за 30 дней берётся
топ-10% по количеству продаж. Кешируется на backend 10 минут отдельно от
обычного TTL каталога (20 секунд) — тяжёлый агрегат по всей платформе,
пересчитывать его на каждый запрос не нужно. Изолирован по каждому товару
(не «магазин целиком хитовый») — у магазина с одним хитовым и одним тихим
товаром `is_hit` будет разным для этих двух товаров.

### Логотип магазина — `POST /api/auth/shop/logo`

```
POST /api/auth/shop/logo   multipart/form-data, поле "file"
```

Тот же паттерн, что и загрузка фото товара/логотипа склада — сохраняет
файл, старый логотип удаляется. Ответ (`201`) — `TenantResponse` с новым
полем `logo: string`. `GET`/`PATCH /api/auth/shop` тоже отдают `logo`
(пустая строка — логотипа нет).

Если в вашей версии фронта уже реализовано поле `storefront_logo` из другой
задачи (B2, `PRODUCT_PAGE_PROMPTS.md`) — это то же самое поле под другим
именем в документе; здесь оно называется `logo`, проверьте, что реально
отдаёт бэкенд (`logo`), не переименовывайте на фронте самостоятельно без
проверки.

**На фронте:**
1. Настройки магазина — загрузка логотипа (аналогично фото товара/склада).
2. Карточка товара в общей ленте маркетплейса — логотип магазина, щит
   «проверенный» (только если `shop_is_verified`), бейджи «Новинка»
   (`is_new`)/«Хит» (`is_hit`) снизу слева на фото (не больше двух бейджей
   одновременно — приоритет: нет в наличии → скидка → хит → новинка, порядок
   выбирает фронт).

## 6. Новые сортировки

**`GET /api/marketplace/products`** и **`GET /api/storefront/{slug}`** —
параметр `sort` получил три новых значения:

```ts
sort?: "name" | "price_asc" | "price_desc" | "created_desc" | "popular" | "rating" | "discount"
```

- `popular` — по `sold_count` за последние 30 дней, по убыванию.
- `rating` — по `average_rating`, по убыванию; при равном рейтинге — по
  `reviews_count`, по убыванию. Товары без единого отзыва уходят в конец
  списка (не в начало — `NULL` не считается «отсутствием рейтинга,
  равным лучшему»).
- `discount` — по `discount_percent`, по убыванию (см. раздел 4 — учитывает
  порог 3%, «no discount» тоже уходит в конец). Товары с `discount_percent:
  null` — в конце списка.

Неизвестное значение `sort` — по-прежнему `400` с понятным `detail`.

`min_rating` (уже существовал, без изменений) продолжает работать вместе с
новыми сортировками.

## 7. Изоляция между магазинами и видимость

Ничего специально нового для фронта, но зафиксировано тестами и стоит
знать: `is_hit`/рейтинг/скидка одного товара никак не связаны с другими
магазинами — общий кросс-tenant расчёт (`is_hit`) не «утекает» популярность
одного магазина на карточки другого. Заблокированный админом магазин
(`is_suspended: true`) полностью пропадает из `GET /api/marketplace/products`
и из `GET /api/marketplace/cities` (не только из детальной карточки, как
было раньше) — при `suspend`/`unsuspend` кеш общего каталога маркетплейса
чистится сразу, не только кеш витрины конкретного магазина.

# M-B2: баннеры и данные главной одним запросом

Вторая часть бэкенда под главную маркетплейса (`docs/MARKETPLACE_HOME_PROMPTS.md`,
промпт M-B2). Опирается на M-B1 выше — товар в ответах M-B2 использует тот же
формат, что `GET /api/marketplace/products` (раздел 5 M-B1: `shop_logo`,
`shop_is_verified`, `shop_city`, `old_price`, `discount_percent`, `is_new`,
`is_hit`). Фронтенд не менялся.

## 1. Баннеры платформы

Новая таблица `platform_banners` — карусель на главной (`placement: "hero"`)
и промо-плитки (`placement: "promo"`), ведёт только админ платформы.

### Админка (`require admin`, тот же JWT, что у остального `/api/admin/*`)

```
GET    /api/admin/banners
POST   /api/admin/banners
PUT    /api/admin/banners/{id}
DELETE /api/admin/banners/{id}
POST   /api/admin/banners/{id}/image          (multipart, поле "file", десктоп)
POST   /api/admin/banners/{id}/image-mobile   (multipart, поле "file", мобильная, необязательная)
```

```ts
// Banner (ответ всех методов)
interface Banner {
  id: number;
  placement: "hero" | "promo";
  title: string;          // может содержать [слово в скобках] — фронт выделяет плашкой (см. M-F2)
  subtitle: string;
  button_text: string;
  link: string;            // относительный путь "/..." или "https://..."
  image: string;            // путь картинки или "" — своей заглушки нет
  image_mobile: string;     // путь или "" — если нет, фронт использует image
  theme: "light" | "accent" | "dark";
  sort_order: number;
  is_active: boolean;
  starts_at: string | null; // "YYYY-MM-DD", включительно
  ends_at: string | null;   // "YYYY-MM-DD", включительно
  city: string | null;      // null — показывать во всех городах
}
```

`POST`/`PUT` тело:
```ts
{
  placement: "hero" | "promo";
  title: string;
  subtitle?: string;
  button_text?: string;
  link?: string;
  theme?: "light" | "accent" | "dark";   // по умолчанию "light"
  sort_order?: number;
  starts_at?: string | null;              // "YYYY-MM-DD"
  ends_at?: string | null;
  city?: string | null;
  is_active?: boolean;                    // только PUT, по умолчанию true
}
```

**Валидация `link`:** пусто, относительный путь (`/...`) или `https://...` —
иначе `400`. `javascript:`, `data:`, обычный `http://` — отклоняются.
**Валидация `placement`/`theme`:** только перечисленные значения, иначе `400`.
**Валидация дат:** `starts_at > ends_at` (если оба заданы) — `400`.
Изображение — то же файловое хранилище, что у фото товара, но с отдельным
лимитом: **максимум 3 МБ** (у фото товара — 5 МБ), иначе `400`. Загрузка
`image`/`image-mobile` — независимые вызовы, вторая не стирает первую.

Список/CRUD применяются немедленно — кеш `GET /api/marketplace/home`
чистится при любой мутации баннера (создание/правка/удаление/загрузка
картинки), как и при verify/unverify/suspend магазина.

**На фронте (админка):** раздел «Баннеры» — список с превью, датами,
активностью; форма создания/правки с двумя загрузками картинок и
подсказкой про `[квадратные скобки]` в заголовке (см. чек-лист M-F6).

## 2. `GET /api/marketplace/home?city=<name>`

Публично, без авторизации. Rate limit 300/минуту. Кеш 60 секунд на
город (`city` не передан — отдельный от переданного ключ кеша, т.е.
«все города» кешируется отдельно от каждого конкретного города).

```ts
interface MarketplaceHomeResponse {
  banners: {
    hero: Banner[];   // активные по датам и городу, отсортированы по sort_order
    promo: Banner[];
  };
  categories: PlatformCategoryResponse[];  // первые 12 по sort_order, только с товарами (см. M-B1 §1)
  shops: ShopChip[];                        // до 20
  sections: HomeSection[];
  stats: {
    shops_count: number;    // магазинов с хотя бы одним видимым товаром (не только показанные 20 в shops)
    products_count: number; // видимых товаров видимых магазинов, с учётом ?city=
    cities_count: number;   // городов среди видимых магазинов, с учётом ?city=
  };
}

interface ShopChip {
  slug: string;
  name: string;
  logo: string;              // путь или "" — заглушки нет
  city: string | null;
  is_verified: boolean;
  average_rating: number;    // 0, если отзывов нет
  reviews_count: number;
  products_count: number;    // видимых товаров магазина на витрине
}

interface HomeSection {
  key: "discount" | "popular" | "new" | "top_rated";
  title: string;              // русский заголовок, готов к выводу как есть
  products: MarketplaceProduct[];  // формат — как элемент GET /api/marketplace/products (M-B1 §5)
}
```

**Баннеры:** `hero` и `promo` — отдельные массивы (не нужно фильтровать по
`placement` на фронте). Баннер активен, если `is_active: true`, сегодняшняя
дата в `[starts_at, ends_at]` (обе границы включительно, `null` — без
ограничения с этой стороны), и (`city` баннера — `null`, либо совпадает с
`?city=` запроса; баннер без `city` показывается в любом городе). Если
`?city=` не передан в запросе — приходят все активные по датам баннеры
независимо от их собственного `city`.

**`categories`:** те же поля, что у `GET /api/marketplace/categories`
(M-B1 §1) — `id`, `slug`, `name`, `image`, `parent_id`, `products_count`.
Не более 12, по `sort_order`, только с товарами (с учётом `?city=`).

**`shops`:** до 20 штук. Порядок: сначала проверенные (`is_verified`),
затем с логотипом (`logo !== ""`), затем по числу продаж за 30 дней —
внутри каждой группы порядок по продажам сохраняется (устойчивая
сортировка). Магазины без единого видимого товара на витрине не
показываются вовсе. `stats.shops_count` — полное число подходящих
магазинов (не ограничено 20-ю, в отличие от массива `shops`).

**`sections`:** до 4 штук, в фиксированном порядке (`discount`, `popular`,
`new`, `top_rated`) — секция отсутствует в массиве целиком, если после всех
правил в ней набралось меньше 5 товаров (не приходит пустой массив, весь
объект секции пропущен). Правила:
- только товары в наличии (`in_stock: true`);
- не больше 10 товаров в секции;
- не больше 3 товаров одного магазина в секции (жадный отбор по порядку
  сортировки — если у магазина только 3-е место по сортировке уже занято
  своими же товарами, 4-й его товар в секцию не попадает, его место
  достаётся следующему подходящему товару другого магазина);
- `discount` — только товары со скидкой (`discount_percent !== null`),
  сортировка по размеру скидки;
- `popular` — сортировка по `sold_count` за 30 дней;
- `new` — сортировка по дате создания товара, по убыванию;
- `top_rated` — только `reviews_count >= 3` и `average_rating >= 4.5`,
  сортировка по рейтингу, затем по числу отзывов.

**Производительность:** весь ответ собирается пакетными запросами — при
типичном объёме данных 11 SQL-запросов независимо от числа товаров/магазинов
(измерено тестом `test_marketplace_home_query_count`, порог ≤ 12). Никаких
запросов на каждый товар/магазин (N+1).

## 3. `GET /api/marketplace/shops`

Публично. Rate limit 300/минуту. Кеш 60 секунд (по параметрам запроса).
Страница «Все магазины».

```ts
// параметры
{
  city?: string;
  query?: string;                          // поиск по названию магазина, ILIKE
  sort?: "popular" | "rating" | "new";     // по умолчанию popular
  limit?: number;                          // по умолчанию 20, максимум 50
  offset?: number;                         // по умолчанию 0
}

// ответ
interface MarketplaceShopsResponse {
  shops: ShopChip[];  // тот же тип, что в home
  total: number;
}
```

Те же правила видимости, что у `shops` в `/marketplace/home` (только
магазины с товарами на витрине, скрытые/заблокированные не попадают).
`sort=new` — по дате регистрации магазина, по убыванию (свежие сначала).
Неизвестное значение `sort` — `400`.

## 4. `GET /api/marketplace/suggest?q=<строка>&city=<name>`

Публично. Rate limit **120/минуту** (не 300, как у остального
маркетплейса — эндпоинт дёргается на каждое нажатие клавиши). Кеш 30
секунд на запрос (`q`+`city`).

```ts
interface SuggestResponse {
  products: {
    id: number;
    name: string;
    photo: string;       // путь или "" — заглушки нет
    price: string;        // retail_price, decimal-строка
    shop_slug: string;
  }[];                     // до 5
  shops: ShopChip[];        // до 3, тот же тип, что в home
  categories: { slug: string; name: string }[];  // до 3
}
```

`q` короче 2 символов — пустой ответ (`{products: [], shops: [], categories: []}`),
без обращения к БД; не нужно самостоятельно проверять длину на фронте, но
и незачем слать совсем короткие запросы. Поиск товаров — `ILIKE` по имени
и артикулу (точные совпадения по началу строки — выше в списке). Поиск
магазинов — `ILIKE` по названию, тот же порядок, что и в `/marketplace/shops`
(`sort=popular`). Поиск категорий — по вхождению подстроки в название
(регистронезависимо), только активные.

> Отклонение от буквального текста промпта: раздел 4 промпта упоминает
> «триграммы — если pg_trgm доступен» как альтернативу ILIKE. В проекте нет
> ни включённого расширения `pg_trgm`, ни существующего кода, который бы на
> него полагался (весь текстовый поиск в проекте — обычный `ILIKE`, см.
> `GET /api/marketplace/products`), поэтому подсказки тоже используют
> `ILIKE` — поведение не хуже существующего поиска по каталогу, а
> добавление нового расширения БД не входило в объём этой задачи.

## Отклонения от буквального текста промпта M-B2

- **`suggest` — ILIKE вместо триграмм** (см. выше, раздел 4) — в проекте нет
  `pg_trgm`, добавлять новое расширение БД не стали.
- **`sort=new` для магазинов** — датой для «новизны» магазина используется
  `Tenant.created_at` (регистрация магазина), в промпте явно не уточнено,
  что считать «новым» магазином.
- **`top_rated` не использует `min_rating` как единственный критерий** —
  порог `4.5` не целое число звёзд, поэтому сортировка/порог рейтинга
  считается отдельно от параметра `min_rating`, который используется в
  `/marketplace/products` (см. M-B1 §6).
- Формат `Banner.starts_at`/`ends_at` — `"YYYY-MM-DD"` (дата без времени),
  сравнение с «сегодня» — по UTC-дате сервера.
