# Авторизация покупателей на витрине (breaking change)

**Важно, прочитать в первую очередь:** оформление заявки с витрины
(`POST /api/storefront/{slug}/requests`) теперь требует авторизации
покупателя. **Анонимного оформления заявки больше нет.** Это сделано
осознанно и сразу (не поэтапно) — до тех пор, пока фронт не внедрит новый
флоу входа, кнопка «Оформить заказ» на витрине будет возвращать `401` для
любого неавторизованного посетителя. Каталог (`GET /api/storefront/{slug}`,
карточка товара) по-прежнему полностью публичны, без авторизации — ломается
только сама отправка заявки.

Это первая часть подготовки к будущим отзывам/рейтингу товаров (см. отдельную
будущую фичу) — отзыв сможет оставить только владелец аккаунта, поэтому
аккаунт понадобился раньше отзывов.

---

## Модель: Customer

Новая сущность — аккаунт покупателя, **общий на всю платформу**, не привязан
к одному магазину (в отличие от `User` — сотрудника конкретного tenant).
Один и тот же аккаунт покупателя работает во всех магазинах ВайСклада, где
он что-то заказывал. Вход — по номеру телефона, без пароля, подтверждение —
через Telegram-бота витрины (тот же бот, что уже используется для просмотра
каталога, `t.me/<bot>?start=<slug>`).

## Флоу входа

### 1. Запросить ссылку входа

**`POST /api/auth/customer/login-link`**
```json
{ "phone": "+79991234567" }
```
Формат телефона гибкий — как и везде в API, принимает и `89991234567`,
и `9991234567`, сервер нормализует. Rate limit `10/hour` на IP.

Ответ `200`:
```json
{
  "token": "zxK9f...",
  "telegram_deep_link": "https://t.me/waysklad_shop_bot?start=login_zxK9f..."
}
```

- `token` — сохранить в памяти фронта (не в localStorage — живёт всего 10 минут),
  понадобится для шага 3.
- `telegram_deep_link` — готовая ссылка, показать как кнопку «Войти через
  Telegram». По клику открывается Telegram (на телефоне — приложение, на
  десктопе — Telegram Web/десктоп-клиент).
- `400` — вход через Telegram не настроен на этом сервере (`TELEGRAM_BOT_USERNAME`
  не задан) — практически не должно происходить в проде, но обработать на
  всякий случай понятным сообщением.

### 2. Покупатель подтверждает в Telegram

Покупатель нажимает кнопку → открывается бот → бот сам присылает
подтверждение («Готово — возвращайтесь на сайт, вход подтверждён»). **Фронту
здесь ничего делать не нужно** — это происходит целиком в Telegram, вне сайта.

### 3. Поллинг статуса

**`GET /api/auth/customer/login-status?token=<token>`**

Ответ `200`, пока не подтверждено:
```json
{ "confirmed": false, "access_token": null }
```
Ответ `200`, как только подтверждено:
```json
{ "confirmed": true, "access_token": "eyJhbGci..." }
```

Рекомендация по частоте поллинга — раз в 2 секунды, пока `confirmed: false`.
`token` живёт 10 минут — если покупатель долго не подтверждает, имеет смысл
остановить поллинг и предложить запросить новую ссылку (шаг 1 заново).

Как только `confirmed: true` — сохранить `access_token` (обычный JWT) в
`localStorage`, это и есть аккаунт покупателя. Дальше — `Authorization: Bearer
<access_token>` на защищённых запросах ниже. Токен долгоживущий (30 дней, как
у обычного пользователя), обновлять/рефрешить не нужно — только заново
логиниться после истечения.

## Что теперь требует авторизации

**`POST /api/storefront/{slug}/requests`** (оформление заявки) — теперь
требует `Authorization: Bearer <access_token>`. Без него — `401`.

Изменилось тело запроса — **`customer_phone` больше не принимается**,
телефон берётся из аккаунта автоматически:
```json
{
  "customer_name": "Иван",
  "items": [{ "product_id": 1, "quantity": "2", "variant_id": null }],
  "note": "Уточнить наличие цвета"
}
```
`customer_name` остался обязательным полем формы (человекочитаемое имя для
конкретного заказа — можно оформлять «для мамы», «для офиса» и т.п. под
разными именами с одного аккаунта).

## Новое: история заявок покупателя

**`GET /api/storefront/requests/my`** (требует `Authorization: Bearer`)

Список всех заявок этого покупателя **во всех магазинах платформы**, новые
сначала:
```ts
{
  id: number,
  customer_name: string,
  customer_phone: string,
  note: string,
  status: "new" | "accepted" | "rejected",
  lines: { product_id: number, quantity: string, variant_id: number | null }[],
  insufficient_stock_at_request: boolean,
  shop_name: string,   // НОВОЕ поле — к какому магазину относится заявка
}[]
```
Это отдельный, новый способ посмотреть заявки — старый способ
(`GET /api/storefront/requests/status?token=<access_token>` по токену
конкретной заявки) **не убран**, продолжает работать как раньше (полезен,
например, для прямой ссылки на статус одной заявки без входа в аккаунт).

## Что нужно сделать на фронте

1. Экран/модалка входа: поле телефона → кнопка «Получить код» → вызов шага 1
   → показать кнопку-ссылку на Telegram (шаг 2) → поллинг (шаг 3) → сохранить
   `access_token` в `localStorage`.
2. Кнопка «Оформить заказ» на витрине — если покупатель не авторизован,
   сначала показать экран входа (п.1), затем продолжить оформление. Если уже
   авторизован (валидный токен в `localStorage`) — оформлять сразу, без
   повторного входа.
3. Убрать поле «Телефон» из формы оформления заказа — оно больше не
   отправляется (телефон уже известен из аккаунта).
4. Добавить экран/вкладку «Мои заказы» — список по `GET /requests/my`,
   сгруппировать или пометить по `shop_name`, раз один аккаунт может иметь
   заказы в разных магазинах.
5. Обработать `401` от `POST /requests` (например, если `access_token`
   истёк/отозван) — вернуть на экран входа, не показывать сырую ошибку.

## Telegram-бот витрины — тоже изменился (без действий на фронте)

Диалог оформления заказа через сам бот больше не даёт пропустить ввод
телефона («Пропустить» убрано) — телефон обязателен, бот сам заводит/находит
аккаунт покупателя по номеру и `chat_id` этого диалога. Отдельного шага входа
в боте нет — раз покупатель уже пишет боту, его `chat_id` и так известен.
Это внутреннее изменение бота, фронта не касается.
