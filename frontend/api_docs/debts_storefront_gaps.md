# Пилотные доработки: деактивация клиента с долгом, WhatsApp-напоминание, резерв заявки с витрины, уведомление о заявке

Четыре несвязанные точечные доработки по итогам ревью перед пилотом (5-10
живых магазинов) — не архитектурные изменения, а поведенческие пробелы,
которые иначе проявились бы в первую неделю реального использования.
Ничего не ломает существующие контракты — только новые опциональные поля
и одно новое явное поведение (деактивация с долгом).

---

## 1. Деактивация клиента с непогашенным долгом требует подтверждения

**Эндпоинт:** `PATCH /api/counterparties/clients/{id}`

Раньше деактивация клиента (`is_active: false`) молча проходила, даже если
за клиентом висел непогашенный долг — клиент пропадал из активных списков,
а сумма зависала без предупреждения.

**Новое поведение:** если `is_active` меняется с `true` на `false`, и у
клиента есть непогашенный долг (`balance > 0` хотя бы по одному долгу), а
новое опциональное поле `force` не передано или `false` — запрос отклоняется:

```json
// 400
{"detail": "У клиента непогашенный долг 1500 — подтвердите деактивацию (force=true), чтобы деактивировать невзирая на долг"}
```

Это **не жёсткая блокировка** — деактивация с долгом может быть законным
решением владельца (например, клиент съехал, а долг спишут отдельно).
Чтобы деактивировать невзирая на долг, повторить запрос с `force: true`:

```ts
// тело запроса — новое опциональное поле, по умолчанию false
{ name: string, phone?: string, whatsapp?: string, city?: string, debt_limit?: string, is_active?: boolean, force?: boolean }
```

Деактивация клиента **без** долга по-прежнему проходит как раньше, без
каких-либо изменений в поведении.

**Что нужно сделать на фронте:** при попытке снять чекбокс «Активен» (или
аналогичное действие) — если сервер вернул `400` с этим `detail`, показать
диалог-предупреждение с суммой долга («У клиента непогашенный долг 1500 ₽.
Деактивировать всё равно?») и при подтверждении повторить запрос с
`force: true`. Текст `detail` уже содержит сумму — можно либо показать его
как есть, либо распарсить сумму под свой дизайн диалога.

## 2. Готовая WhatsApp-ссылка для напоминания о просроченном долге

**Эндпоинт:** `GET /api/debts/due`

Каждый долг в ответе получил новое поле:

```ts
{
  // ...все поля DebtResponse, как раньше...
  whatsapp_reminder_link: string | null,
}
```

`null` в двух случаях: долг **не клиентский** (долг поставщику — `client_id: null`),
либо у клиента не указан ни телефон, ни WhatsApp. Когда ссылка есть — это
готовый `https://wa.me/<номер>?text=<текст>`, открывающий чат с клиентом с
уже подставленным текстом напоминания вида:

> Здравствуйте! Напоминаем о задолженности 1500 руб. по заказу от 05.09.2026.
> Будем благодарны за оплату.

Ссылка **ничего не отправляет сама** — просто готовый `<a href>`/`window.open`,
как уже используется для ссылки на квитанцию продажи (`build_whatsapp_link` в
квитанции — тот же паттерн, тот же формат ссылки).

**Что нужно сделать на фронте:** на экране «Долги» (вкладка просроченных/
раздел «Нам должны») — рядом с просроченным долгом кнопка/иконка «Напомнить
в WhatsApp», активная только когда `whatsapp_reminder_link !== null`,
открывающая ссылку в новой вкладке (`target="_blank"`).

## 3. Мягкий резерв товара под заявку с витрины + авто-освобождение через 72ч

Раньше заявка с витрины (`POST /api/storefront/{slug}/requests`) вообще не
трогала остаток — товар резервировался только при ручном принятии
владельцем. Значит несколько покупателей могли одновременно «заказать»
последнюю единицу товара, и только на этапе принятия выяснялось бы, что
остатка не хватает.

**Новое поведение при создании заявки:** `POST /api/storefront/{slug}/requests`
теперь **сразу мягко резервирует** запрошенное количество (на видимых на
витрине складах — то же множество складов, что учитывается в `in_stock`
каталога). Резерв уменьшает то, что увидит **следующий** покупатель как
доступное, но не физический остаток на складе.

Если остатка не хватило хотя бы на одну позицию заявки — заявка **всё равно
создаётся** (покупатель уже физически написал, отказывать нет смысла), но
помечается флагом:

```ts
// StorefrontRequestResponse (ответ создания заявки и все остальные, где он встречается)
{
  // ...все поля, как раньше (id, customer_name, status, lines, ...)...
  insufficient_stock_at_request: boolean,
}
```

**Что нужно сделать на фронте:**
1. После `POST /api/storefront/{slug}/requests` — если `insufficient_stock_at_request: true`,
   показать покупателю мягкое предупреждение («Возможно, часть товара уже
   разобрали — мы уточним наличие и свяжемся с вами»), не блокируя
   оформление (заявка уже создана, `201` пришёл как обычно).
2. В панели владельца, в списке заявок (`GET /api/storefront/requests/new`)
   и на карточке заявки (`GET /api/storefront/requests/{id}`) — если флаг
   `true`, показать бейдж/иконку «под вопросом остаток» рядом с заявкой,
   чтобы владелец сразу видел, что перед принятием стоит проверить наличие.

**Что происходит с резервом дальше (можно не отображать на фронте, но
полезно понимать для консистентности данных):**
- **Принятие** (`POST /api/storefront/requests/{id}/accept`) — резерв не
  задваивается: то, что зарезервировано при создании заявки, снимается и
  переставляется на конкретный склад, который выбрал владелец при
  принятии (сумма резерва не меняется, просто «переезжает» на нужный склад).
  Поведение и контракт самого эндпоинта `accept` не изменились.
- **Отклонение** (`POST /api/storefront/requests/{id}/reject`) — резерв
  снимается полностью, товар снова доступен для других заявок. Контракт
  эндпоинта не изменился.
- **Авто-освобождение через 72 часа** — если заявка простояла в статусе
  `new` дольше 72 часов (владелец не обработал), резерв снимается
  автоматически фоновой задачей. **Статус заявки при этом НЕ меняется** —
  заявка остаётся `new` и видна в списке новых, просто без резерва под ней
  (чтобы не терять её из истории, как случилось бы при авто-отклонении).
  На фронте это не видно напрямую как отдельное поле — только косвенно
  через то, что товар снова стал доступен другим покупателям. Если в
  будущем понадобится явно показать «резерв снят по истечении времени» —
  сообщите, добавим поле в ответ (сейчас это внутренний флаг, наружу не
  отдаётся, чтобы не усложнять контракт без явной необходимости).

## 4. Уведомление владельцу о новой заявке с витрины

Раньше создание заявки с витрины было полностью «тихим» для владельца —
узнать о новой заявке можно было только зайдя в раздел «Заявки с витрины» и
обновив список руками.

**Новое поведение:** после успешного создания заявки владелец и менеджеры
магазина получают обычное уведомление — **тот же канал**, что уже
используется для остальных уведомлений (in-app список + WS-push), никакой
новой инфраструктуры на фронте подключать не нужно.

Новый `NotificationKind`:

```ts
"storefront_request_new"
```

Приходит и через `GET /api/notifications`, и через существующий
`WS /api/notifications/ws` (см. `README.md`, запись про WS-канал
уведомлений) — колокольчик уведомлений сработает сам, если он уже слушает
этот канал типово, без выделения конкретных `kind`.

Формат — как у любого другого уведомления:
```ts
{
  id: number,
  kind: "storefront_request_new",
  text: string,     // например: "Новая заявка с витрины: Ахмед, 2 товаров на сумму 3400 ₽"
  link: string,      // "/orders/storefront-requests"
  entity_id: number, // id заявки
}
```

**Что нужно сделать на фронте:** если колокольчик уведомлений уже
обрабатывает произвольные `kind` универсально (показывает `text`, ведёт по
`link`) — ничего делать не нужно, новый тип подхватится автоматически. Если
где-то есть switch/маппинг конкретных `kind` на иконки/цвета — можно
добавить `storefront_request_new` туда для визуального различия (не
обязательно, просто на усмотрение).

## 5. OG-превью витрины для WhatsApp/Instagram (backend этим не занимался — нужно на фронте)

Не входит в backend-изменения этой доработки, но стоит держать в поле
зрения перед пилотом: ссылка на витрину (`/storefront/{slug}` или на
конкретный товар `/storefront/{slug}/products/{id}`), отправленная в
WhatsApp или Instagram Direct, сейчас разворачивается голым URL без
превью — ни названия магазина/товара, ни фото, ни описания. Учитывая, что
WhatsApp — основной канал распространения ссылок на витрину в этом
проекте, отсутствие превью заметно снижает вероятность того, что получатель
откроет ссылку.

Это чисто фронтенд-задача (SSR/prerender с `<meta property="og:*">`), не
API — backend уже отдаёт всё нужное сырьё через существующие эндпоинты:
`shop_name` (`GET /api/storefront/{slug}`), `name`/`photo` каждого товара
(`GET /api/storefront/{slug}/products/{id}`). Понадобится:
- `og:title` — название магазина или товара
- `og:description` — короткое описание/цена
- `og:image` — `photo` товара или логотип магазина, если он появится
- `og:url` — канонический URL страницы

Если на фронте нет SSR (чистый SPA) — обычный путь: отдельный
prerender-слой или мета-теги, генерируемые edge-функцией/прокси именно для
ботов соцсетей (User-Agent от WhatsApp/Telegram/Facebook), не для реальных
пользователей. Решать, как это встроить в текущий стек фронтенда, будет
фронтенд-разработчик — здесь просто фиксируем, что backend для этого уже
готов отдать нужные данные, самих meta-тегов нет нигде.
