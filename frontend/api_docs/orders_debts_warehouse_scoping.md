# Заказы/Долги: номер заказа, склад в долгах, сверка на дату, документ по id

Дата: 2026-09-04. Четыре доработки бэкенда по накопленному техдолгу. Одна из
них — **breaking**: `POST /api/debts` и `POST /api/debts/suppliers` теперь
требуют `warehouse_id`.

---

## 1. `POST /api/orders` — номер заказа сразу в ответе

Раньше сразу после создания `number` приходил `null` (нужен был повторный
`GET /api/orders/{id}`, чтобы получить настоящий номер — он уже был сохранён
в БД, просто не возвращался). Теперь `POST /api/orders` отдаёт готовый
`number` сразу. Ничего на фронте менять не нужно, просто перестаёт
понадобиться обходной перезапрос, если он где-то был.

---

## 2. Новый `GET /api/inventory/documents/{document_id}`

Точечный запрос одного документа склада (приёмка/списание/перемещение),
вместо полного `listDocuments()` + фильтрации на клиенте по id. Ответ — тот
же `DocumentHistoryResponse`, что и элементы списка `GET /api/inventory/documents`.

- `404` — документ не найден.
- `403` — сотрудник с ограничением по складу (manager/seller/storekeeper)
  запросил документ чужого склада (для перемещения — «чужой» значит ни один
  из двух складов документа не входит в список назначенных сотруднику).

Если карточка документа на фронте сейчас ищет нужный документ в уже
загруженном общем списке — можно (не обязательно) переключить на этот
эндпоинт.

---

## 3. `GET /api/debts/client/{id}` и `/api/debts/supplier/{id}` — снимок на дату

Новый опциональный query-параметр `?on=YYYY-MM-DD`. Без него — как раньше,
баланс на текущий момент. С ним — баланс и список погашений, каким он был
именно на эту дату (долги, выданные позже `on`, не показываются; погашения
и продления после `on` не учитываются).

Ответ — тот же `DebtsSummaryResponse` (`total_balance` + `debts[]`), просто
с другим набором данных внутри.

Полезно для функции «сверка с клиентом/поставщиком»: показать, каким был
баланс на конкретную дату в прошлом.

---

## 4. Breaking: `warehouse_id` обязателен в ручных долгах

**`POST /api/debts`** и **`POST /api/debts/suppliers`** — тело запроса
теперь требует `warehouse_id: number` (раньше такого поля не было).
Запрос без него вернёт `422`.

```ts
// было
{ client_id: number, amount: string, due_date?: string, note?: string }
// стало
{ client_id: number, warehouse_id: number, amount: string, due_date?: string, note?: string }
```

То же самое для `POST /api/debts/suppliers` (`supplier_id` вместо `client_id`).

**Что нужно на фронте:** формы «Записать долг клиенту» и «Взяли под долг у
поставщика» должны получить выбор склада — тот же список складов и тот же
UX, что уже есть в форме продажи/приёмки/заказа (если склад в магазине
один — можно не показывать выбор и подставлять его id автоматически, как
сделано для сотрудников в других формах).

`DebtResponse` теперь тоже содержит `warehouse_id` в ответе (для всех
эндпоинтов долгов, включая уже существующие продажи-в-долг и долги из
приёмки — они получили склад автоматически, без изменений на фронте).

**Побочный эффект (не баг, не требует действий):** `GET /api/orders`,
`GET /api/orders/completed`, `GET /api/debts`, `GET /api/debts/closed` и
одиночные `GET /api/orders/{id}`, `GET /api/debts/{id}` теперь на бэкенде
сами фильтруются по складам сотрудника — manager/seller/storekeeper видят
только заказы/долги своих складов. Раньше это применялось только к
продажам, остаткам и документам склада, к заказам/долгам — нет. Списки для
таких сотрудников могут стать короче, чем были.
