# Описание товара + галерея фото витрины + генерация через ИИ

Два новых поля у товара, оба — только для карточки товара **на витрине**
(покупателю), не складские характеристики:

- `description` — текст.
- `storefront_photos` — список фото (галерея), полностью независим от
  существующего складского `photo` (то, что видно в учёте/накладных — не
  меняется, остаётся одним фото).

Плюс отдельный эндпоинт, который предлагает текст описания через ИИ по
названию+категории — ничего не сохраняет сам, только возвращает предложение
для предпросмотра.

---

## Поле `description`

Обычное текстовое поле, как `name`/`sku` — приходит и принимается везде, где
и раньше был товар целиком:

- `GET /api/products/{id}`, `GET /api/products` (список), ответы
  `POST /api/products` и `PUT /api/products/{id}` — есть поле `description: string`
  (пустая строка, если не заполнено).
- `POST /api/products` (создание) и `PUT /api/products/{id}` (обновление) —
  принимают `description: string` в теле, необязательное (по умолчанию `""`).

На витрине:

- `GET /api/storefront/{slug}/products` (список каталога) — **description
  нет**, туда не отдаётся (сравнимо с `sku` — тоже только в детальной карточке,
  список остаётся лёгким).
- `GET /api/storefront/{slug}/products/{id}` (карточка одного товара) — есть
  `description: string`.

## Галерея `storefront_photos`

Отдельная от `photo` (складского) галерея — товар может иметь и одно
складское фото, и несколько витринных, они друг с другом никак не связаны.
Пустая галерея — валидное состояние (карточка витрины без фото), автоматической
подстановки складского `photo` в галерею нет и не будет.

- `GET/POST/PUT /api/products/...` (всё как у `description`) — есть поле
  `storefront_photos: string[]` (список URL, порядок = порядок показа).
  Через `POST`/`PUT /api/products/{id}` это поле **не меняется** — читается
  только, писать в него можно исключительно через два эндпоинта ниже.
- `GET /api/storefront/{slug}/products/{id}` (карточка товара витрины) — есть
  `storefront_photos: string[]`.
- `GET /api/storefront/{slug}/products` (список каталога) — **нет**, как и
  `description` (список остаётся лёгким, полный набор фото — только на карточке).

### Добавить одно фото в галерею

**`POST /api/products/{product_id}/storefront-photos`** (multipart, поле
`file` — тот же формат, что уже используется для `POST /api/products/{id}/photo`)

Добавляет фото **в конец** списка, возвращает `200` и обновлённый
`ProductResponse` целиком (как у обычного `set_product_photo`). `413`/`400`
при недопустимом формате или файле больше 5 МБ — то же поведение, что у
складского фото.

### Изменить порядок / удалить фото

**`PUT /api/products/{product_id}/storefront-photos`**
```json
{ "photos": ["/uploads/a.webp", "/uploads/c.webp"] }
```
Принимает **весь новый список целиком** — это не патч, а замена. Логика на
фронте: взять текущий `product.storefront_photos`, применить
drag-n-drop/удаление на клиенте, отправить получившийся массив сюда.

- Все URL в списке должны быть из уже существующих `product.storefront_photos`
  (то, что вернул `GET`/предыдущий `POST`) — нельзя вписать произвольный URL,
  сначала нужно загрузить его через `POST` выше. Чужой/выдуманный URL в списке
  → `400`.
- URL, которые были в старой галерее, но отсутствуют в переданном списке —
  считаются удалёнными и стираются на сервере безвозвратно.
- Возвращает `200` и обновлённый `ProductResponse`.

## Эндпоинт генерации через ИИ

**`POST /api/products/{product_id}/description/generate`**

Требует права `products.manage` (владелец/менеджер; продавцу — 403). Тело
запроса не нужно — товар уже существует, генератор сам берёт его название и
категорию.

Ответ `200`:
```json
{ "description": "Сгенерированный текст, 1-3 предложения." }
```

- Товар не найден: `404`.
- Нет прав: `403`.
- Генерация выключена на этом сервере (не настроен ключ провайдера) или сбой
  самого провайдера: `400`, `{"detail": "..."}` — с сообщением, которое можно
  показать как есть.

**Важно: этот эндпоинт ничего не сохраняет.** Он только возвращает текст.
Чтобы применить его к товару, нужно отдельно вызвать обычный
`PUT /api/products/{id}` с этим текстом (или с текстом, который владелец
поправил) в поле `description`.

## Что нужно сделать на фронте

1. На карточке/форме товара — поле «Описание» (многострочный текст), рядом с
   существующими полями. Сохраняется вместе с остальной формой через уже
   используемый `PUT /api/products/{id}`, ничего отдельного для сохранения
   не нужно.
2. Кнопка «Сгенерировать через ИИ» у этого поля — дёргает
   `POST /api/products/{id}/description/generate`, результат подставляет в
   то же текстовое поле как черновик (не сохраняет автоматически). Пользователь
   может поправить текст и сохранить форму как обычно.
   - Товар должен быть уже создан (эндпоинт по `product_id`) — на форме
     создания нового товара кнопка недоступна, пока товар не сохранён хотя бы
     раз (или доступна только на экране редактирования).
3. Обработать `400` от генерации — показать сообщение из `detail` (например,
   «Генерация описания через ИИ не настроена» — это ожидаемое состояние на
   серверах без настроенного ключа, не баг).
4. На карточке товара витрины — вывести `description`, если не пусто (обычный
   блок текста, например под характеристиками/ценой, см. `wikkeo_design_reference.md`
   про аккордеоны для второстепенной информации — description можно туда).
5. На форме товара — блок «Фото для витрины»: сетка/лента миниатюр
   `storefront_photos` + кнопка «Добавить фото» (`POST .../storefront-photos`,
   можно вызывать по одному на каждый выбранный файл, если выбрано сразу
   несколько). Drag-n-drop для порядка и крестик на миниатюре для удаления —
   оба действия в итоге собирают новый массив URL и отправляют его одним
   `PUT .../storefront-photos`.
   - Как и с описанием, эндпоинты работают по `product_id` — на форме
     создания нового товара блок галереи недоступен, пока товар не сохранён
     хотя бы раз.
6. На карточке товара витрины — если `storefront_photos` не пуст, показать
   галерею/карусель по этим фото (см. `wikkeo_design_reference.md` — там
   вертикальная лента миниатюр слева от главного фото, можно взять эту
   компоновку). Если пуст — фолбэка на складское `photo` нет, карточка без
   фото остаётся без фото (плейсхолдер решается на фронте, как и раньше для
   складского `photo`).
