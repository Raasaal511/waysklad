# Roadmap: что дальше после MVP

**Дата:** 2026-08-26
**Контекст на момент написания:** backend MVP закрыт целиком (README §5.1, сессии 01–15, 219
тестов), фронтенд — все 8 экранов готовы (сессии 16–20). Впереди — сессия 21 (пилот: демо-данные,
лендинг, внедрение в 5–10 живых магазинах), которая ещё **не начата**. Это значит: то, что ниже —
не «после пилота», а в основном **до и вокруг** него — продукт должен выдержать первых живых
пользователей, прежде чем расти вширь.

Документ не заменяет существующие частные планы, а даёт им общую рамку:
- [`COMPETITOR_MOYSKLAD_ANALYSIS.md`](COMPETITOR_MOYSKLAD_ANALYSIS.md) — фичи для владельца/продавца
  (внутренняя сторона прилавка).
- [`CUSTOMER_FEATURES_SKFO.md`](CUSTOMER_FEATURES_SKFO.md) — фичи для клиента магазина (внешняя
  сторона прилавка), включая публичную витрину и WhatsApp-паттерны.
- [`API_REQUESTS_OPTIMIZATION.md`](API_REQUESTS_OPTIMIZATION.md) — конкретные находки по дублям
  запросов на фронте, план кэширования справочников.

Здесь эти три документа не пересказываются, а вписываются в общую последовательность вместе с
темами, которых там нет: безопасность перед пилотом, ИИ, интеграции второй очереди, поставщики.

---

## 0. Как читать этот документ

Пять направлений роста:

1. **Безопасность** — закрыть перед тем, как в системе появятся чужие долговые книги и реальные
   магазины.
2. **Производительность** — не мешать пилоту техническим долгом, который сейчас незаметен на
   тестовых данных, но проявится на реальной нагрузке.
3. **Функциональность** — куда растёт продукт после MVP (частично уже расписано в двух документах
   выше, здесь — недостающие крупные куски и их место в очереди).
4. **ИИ** — аналитика/советы владельцу и чат-бот поддержки, по приоритету пользователя.
5. **Интеграции** — WhatsApp Business API, публичная витрина, экспорт в 1С, открытый API.

Внутри каждого раздела — что делать и почему, с пометкой приоритета. В конце — сводная
последовательность по времени (перед пилотом / во время пилота / после пилота).

## 1. Безопасность — перед пилотом

Специфика проекта обостряет тему: ВайСклад хранит **чужие долговые книги** (README §6.5 — «доверие
к сохранности данных критично»), а с сессии 21 в системе появятся первые реальные магазины и
реальные телефоны клиентов (152-ФЗ, README §11). До сих пор безопасность не была приоритетом
осознанно — не было живых пользователей, которых можно скомпрометировать. Это меняется с пилотом.

Фактическое состояние на сейчас (проверено по коду):

| Область | Есть | Нет |
|---|---|---|
| Авторизация | JWT (HS256), права по ролям, `require(actor, perm)` в каждом use case | Refresh-токен — только один долгоживущий access-токен (30 дней), без ревокации |
| Сеть | — | CORS не настроен вообще (`CORSMiddleware` не подключён в `main.py`) |
| Защита от перебора | — | Rate-limiting отсутствует полностью — ни на `/auth/login`, ни где-либо ещё |
| Секреты | `.env` вне git, `pydantic-settings` | Дефолты в коде — `secret_key = "dev-secret-change-me"`, пароль БД `change-me` — рискованно, если прод-`.env` что-то не переопределит |
| БД | Индексы на `tenant_id` везде, частичные уникальные индексы | Большинство FK (`product_id`, `client_id`, `sale_id` и т.п.) без явного индекса |
| Бэкапы | `deploy/backup.sh` — ежедневный `pg_dump`, 30 копий локально | Offsite-копии нет — сам скрипт помечен TODO «обязательно до пилота» |
| Мониторинг | `GET /api/health` | Нет логирования ошибок (Sentry и подобного), нет алертов о падении |

### 1.1. Что закрыть до пилота (жёсткий минимум)

- **CORS.** Прямо сейчас его нет — если фронт и бэк не всегда на одном origin (а с публичными
  read-only страницами витрины/статуса заказа, см. §3.2, появятся разные клиенты), это откроет
  дыру. Добавить `CORSMiddleware` с явным whitelist origin'ов из конфига, не `allow_origins=["*"]`.
- **Rate-limiting на `/auth/login` и `/auth/telegram`.** Без него — открытый брутфорс пароля
  любого магазина. `slowapi` (обёртка над `limits`, штатно ложится на FastAPI) — минимум 5
  попыток/минуту с IP на логин.
- **Убрать небезопасные дефолты из `config.py`.** `secret_key` и пароль БД не должны иметь
  осмысленных дефолтов в коде — либо `Settings` падает при старте без `.env`, либо дефолт —
  заведомо нерабочее значение, которое роняет приложение, а не тихо работает с `dev-secret-change-me`
  в проде.
- **Offsite-бэкап** (уже зафиксировано TODO в `deploy/backup.sh`) — rclone/scp копия на второе
  хранилище. Это прямое обещание из README §6.5 и §13 (риск «потеря данных = потеря доверия
  навсегда»), сейчас не выполнено технически.
- **Явные индексы на FK-поля**, которые участвуют в частых JOIN/фильтрах: `sales.client_id`,
  `debts.client_id` (уже есть), `stock_items.product_id`/`warehouse_id` (частично есть через
  уникальный индекс), `order_lines.order_id`, `sale_lines.sale_id`, `audit_log` уже хорошо
  индексирован. Пройтись по реальным запросам аналитики (§13 сессии) — они чаще всего JOIN'ят по
  этим полям.

### 1.2. Что сделать вскоре после (не блокирует пилот, но следующим шагом)

- **Refresh-токен + ревокация.** Сейчас скомпрометированный токен живёт 30 дней без возможности
  отозвать. Минимум — короткий access (15–60 мин) + refresh с возможностью инвалидировать сессию
  (например, при смене пароля/увольнении сотрудника — как раз кейс из README, «сотрудник ушёл»).
- **Security headers** (HSTS, X-Content-Type-Options, X-Frame-Options) — либо в приложении, либо
  проще всего на уровне Traefik/nginx перед бэкендом (уже есть в docker-compose).
- **Логирование ошибок** — минимум Sentry (бесплатный тариф покрывает соло-проект с лихвой) или
  структурированный лог в файл с ротацией. Сейчас при падении в проде разработчик узнает только от
  расстроенного владельца магазина по телефону — это прямой риск для доверия (README §13).
- **152-ФЗ на практике**: явное согласие на обработку персональных данных при регистрации магазина
  (чек-бокс + текст политики), т.к. с пилотом появятся реальные ФИО/телефоны клиентов магазинов.

## 2. Производительность

На тестовых данных всё быстро; проблемы всплывут именно на пилоте (несколько активных магазинов,
сотни SKU, тысячи продаж за месяц). Разложено по фронту и бэку — фронтовая часть уже подробно
разобрана в [`API_REQUESTS_OPTIMIZATION.md`](API_REQUESTS_OPTIMIZATION.md), здесь — сводка и то,
чего там нет.

### 2.1. Фронтенд (см. полный план в API_REQUESTS_OPTIMIZATION.md)

Уже сделано: убран двойной поллинг `NotificationBell`, введён `CatalogContext` с кэшем и
дедупликацией справочников (products/warehouses/units/categories/stock/employees), проверено
живым Playwright-прогоном.

Осталось по тому же документу:
- **Пагинация `/sales`** — сейчас фиксированный `limit=100` без `offset`, без общего count;
  фронт фильтрует плоский массив на клиенте. При месяце активной торговли (тысячи продаж) это
  начнёт тормозить и резать историю. Приоритет: сделать **до пилота**, если хотя бы один пилотный
  магазин будет активным (десятки продаж/день × 30 дней = не поместится в 100).
- Решить: свой `CatalogContext` (уже выбран и реализован) — дальнейшее расширение того же паттерна
  на любые новые справочники, не заводить параллельно react-query.

### 2.2. Бэкенд — не разобрано отдельным документом, добавляется здесь

- **Индексы на FK** — см. §1.1, это одновременно и безопасность (целостность), и
  производительность (JOIN-ы в аналитике и списках).
- **N+1 запросы в аналитике и списках с вложенными сущностями** — не проверено отдельно, стоит
  профилировать эндпоинты `/analytics/*` и списки с товарами/остатками на реальных объёмах данных
  пилота (`EXPLAIN ANALYZE` на медленных запросах, не заранее гадать).
- **Кэш на бэкенде** для нечасто меняющихся, дорогих в вычислении данных: дашборд аналитики
  (§5.1 README — выручка/прибыль за день/неделю/месяц) можно кэшировать на минуты, а не считать
  агрегатом при каждом открытии — но только если профилирование покажет, что это узкое место (не
  вводить Redis заранее «на всякий случай» — сначала измерить на пилоте).
- **`uvicorn --workers 4`** без gunicorn как менеджера процессов — рабочий вариант для старта
  (README п.7: «без оверинжиниринга»), пересматривать только если реальная нагрузка пилота покажет
  проблему (падение воркера не перезапускается автоматически без gunicorn/supervisor).

**Принцип для этого раздела: не оптимизировать вслепую.** Продукт ещё не видел реальной нагрузки —
после первых недель пилота снять метрики (время ответа ключевых эндпоинтов, самые частые запросы)
и чинить то, что реально медленно, а не то, что кажется медленным.

## 3. Функциональность — куда растёт продукт

### 3.1. Уже расписано подробно в двух документах — только сводка приоритетов

Из [`CUSTOMER_FEATURES_SKFO.md`](CUSTOMER_FEATURES_SKFO.md), высокий приоритет, низкая сложность,
одна волна работы (общий `wa.me`-паттерн):
- Отправка истории долга клиенту в WhatsApp.
- Статус заказа клиенту одной кнопкой в WhatsApp.
- Необязательная привязка клиента к обычной (не долговой) продаже.
- Проверка, что все `wa.me`-ссылки берут номер из профиля магазина, а не сотрудника.

Из [`COMPETITOR_MOYSKLAD_ANALYSIS.md`](COMPETITOR_MOYSKLAD_ANALYSIS.md) — единая карточка истории
клиента (покупки/долги/заказы в одном месте), это же — предпосылка для бейджа «постоянный
клиент» и для ИИ-советов по клиентам (см. §4.1 ниже).

### 3.2. Публичные read-only страницы — крупный отдельный блок

Три идеи из `CUSTOMER_FEATURES_SKFO.md` технически — один и тот же слой:
- Публичная витрина товара/каталога (README §5.2, уже запланировано, поднят приоритет).
- Публичная страница статуса заказа по ссылке.
- Публичная страница «Мой долг» по ссылке.

Стоит проектировать **одним слоем инфраструктуры**, а не тремя отдельными фичами: один принцип
непредсказуемых токенов в URL, один rate-limit на публичные роуты, одна точка внимания к
tenant-изоляции (это первая полностью открытая наружу поверхность в проекте — до сих пор всё было
за авторизацией). Разумная последовательность: витрина товара первой (прямое попадание в нишу
Instagram*-магазинов, см. README §4), статус заказа и «мой долг» — по факту обратной связи с
пилота (стоит ли овчинка выделки, или WhatsApp-сообщение и так снимает проблему).

### 3.3. Работа с поставщиками — сейчас слабое место продукта

README и оба существующих аналитических документа фокусируются почти целиком на клиенте
(покупателе). Поставщик в модели данных уже есть (`Supplier`, долг поставщику — сессия 11), но
как **направление продукта** не проработан отдельно, хотя пользователь явно просил подумать про
удобство работы «и с поставщиками». Ниши из README §4 (стройматериалы, мясные лавки/халяль,
оптовики рынка Беркат) описывают ровно обратную сторону той же боли, что решена для клиентов:

- **Карточка поставщика с историей** — по аналогии с единой карточкой клиента (§3.1): что и когда
  поставляли, баланс (мы должны/нам должны — уже частично есть), средние сроки поставки.
- **Заказ поставщику** (аналог заказа клиента, но в обратную сторону) — «закончился товар X,
  сформировать заявку поставщику»: список позиций с минимальным остатком (уже есть в модели
  «мин. остаток с предупреждением», README §5.1) в один клик собирается в заявку-сообщение
  поставщику через WhatsApp — тот же уже отработанный `wa.me`-паттерн, но в обратном направлении
  (не магазин → клиент, а магазин → поставщик).
- **Прогноз закупки** — естественная точка пересечения с ИИ-разделом (§4.1): «на основе скорости
  продаж товара X, через 5 дней остаток кончится, обычно заказываете у поставщика Y» — данные для
  этого уже собираются (продажи, остатки, история приёмок от поставщика).

Приоритет: средний — не входит в MVP и не критично для первого пилота, но стоит держать в поле
зрения, т.к. минимум 3 ниши из README §4 (стройматериалы, оптовики, мясо/халяль) явно ведут
активные расчёты именно с поставщиками, не только с клиентами.

## 4. Искусственный интеллект

Пользователь обозначил приоритет: (1) аналитика/советы владельцу, (2) чат-бот поддержки клиентов.
Оба — накладываются на уже существующую инфраструктуру (аналитика §13 сессии, Telegram-бот),
не требуют новой платформы.

### 4.1. Аналитика и советы владельцу — первая очередь

Сейчас аналитика (README §5.1) — это цифры: выручка, прибыль, топ товаров, мёртвый остаток,
вечерняя Telegram-сводка. Следующий шаг — не новые цифры, а **интерпретация** уже существующих
данных простым языком, тем более что сводка уже приходит в Telegram (готовый канал доставки):

- **Текстовые инсайты поверх дашборда**: не просто «мёртвый остаток: товар X — 60 дней», а
  «в товаре X заморожено 180 000 ₽, не продаётся 2 месяца — рассмотрите скидку или возврат
  поставщику». Формулировка «что делать», а не только «что произошло» — это и есть разница между
  отчётом и советом.
- **Аномалии в вечерней Telegram-сводке**: «сегодня продаж на 40% меньше обычного вторника»,
  «Ахмед второй месяц не платит по графику рассрочки» (данные о графике уже есть после сессии про
  учёт графика рассрочки в статусе долга). Это не требует полноценной ML-модели — базовые
  статистические пороги (сравнение со средним за N предыдущих периодов) дают 80% пользы почти
  бесплатно и не требуют внешнего LLM API вообще.
- **Прогноз «когда закончится товар»** — на основе скорости продаж последних недель, ровно то,
  что нужно для заявки поставщику (§3.3). Тоже не требует LLM — простая линейная экстраполяция по
  уже существующим данным продаж и остатков.
- **LLM-слой (второй, более амбициозный уровень)**: раз в день/неделю прогонять агрегированные
  показатели магазина через LLM API (например, Claude API — уже есть готовая инфраструктура работы
  с Anthropic в инструментах разработки) и получать 2–3 предложения в разговорном стиле для
  Telegram-сводки: «Заметил, что чай продаётся хуже с начала месяца — возможно, стоит проверить
  срок годности партии или сделать скидку». Здесь уже нужен внешний API-вызов, но данные, которые
  туда уходят (агрегаты, не персональные данные клиентов), можно жёстко ограничить по составу —
  важно для 152-ФЗ и для доверия («мы не сливаем ваши данные в облако», README тема доверия).

**Приоритет:** статистические инсайты без LLM — можно делать хоть сейчас, дёшево и без рисков.
LLM-слой — после пилота, когда будет реальная история продаж нескольких магазинов для проверки,
что советы действительно полезны, а не шум.

### 4.2. Чат-бот поддержки клиентов — вторая очередь

Задача: снизить нагрузку поддержки на одного разработчика (README §13, риск «нагрузка поддержки на
одного человека», ответ — «база знаний закрывает типовые вопросы»). ИИ-бот поверх базы знаний —
следующий логичный шаг за статичными видео-инструкциями (README п.8, неделя 11):

- Бот в Telegram (тот же канал, что уже используется для сводок и авторизации через
  `POST /auth/telegram`) — отвечает на вопросы «как сделать возврат», «как добавить сотрудника» на
  основе базы знаний/документации продукта (RAG поверх статей помощи, не поверх персональных
  данных магазина).
- Явная граница: бот не имеет доступа к данным конкретного магазина (остаткам, долгам, продажам) —
  только к документации продукта. Это снимает риски 152-ФЗ и утечки чужих данных через диалог с
  ИИ, и достаточно для типовых вопросов «как сделать X в интерфейсе».
- Эскалация к разработчику лично для нетиповых вопросов — сохраняет то самое личное доверие,
  которое README называет главным конкурентным преимуществом («поддержка лично, на месте» —
  ИИ-бот не должен пытаться заменить это, только отфильтровать типовой поток).

**Приоритет:** после первой волны пилота — сначала накопить реальные вопросы 5–10 живых магазинов
(это и есть материал для базы знаний бота), потом автоматизировать ответы на них. Строить бота
раньше — гадать на пустом месте, какие вопросы реально будут задавать.

## 5. Интеграции внешних сервисов

Из README §5.3 — принципиальный отказ от платёжных/фискальных интеграций (кассы, эквайринг, ЭДО)
остаётся в силе, это ядро позиционирования продукта, не пересматривается. Ниже — только
информационные/коммуникационные интеграции, которые не двигают деньги.

| Интеграция | Что даёт | Приоритет | Зависимости |
|---|---|---|---|
| **WhatsApp Business API** | Автоматическая (не вручную через `wa.me`) отправка квитанций/напоминаний о долге/статусов заказа | Средний | Сначала довести до конца ручной `wa.me`-паттерн (§3.1) — если он закроет боль, платный Business API не понадобится вообще для части кейсов; если пилот покажет, что владельцы хотят *автоматику* (не нажимать кнопку каждый раз) — тогда переходить |
| **Публичная витрина-каталог** | Прямое попадание в нишу Instagram*-магазинов, устраняет ручной рассинхрон каталога | Высокий | Уже спроектирована в README §5.2 и `CUSTOMER_FEATURES_SKFO.md` §2; требует слоя публичных read-only страниц (§3.2) |
| **Экспорт в 1С/бухгалтерию** | Отчётность для тех, кто всё же ведёт бухгалтерию параллельно (ИП на упрощёнке, растущие магазины) | Средний, по спросу | Не вести бухгалтерию самим (остаётся в силе из README §5.3) — только выгрузка данных (продажи, товары) в формате, который бухгалтер/1С может импортировать (CSV/Excel уже частично есть — README §5.2 «экспорт в Excel») |
| **Открытый API для партнёров** | Даёт разработчикам/партнёрам интегрироваться самим (например, локальные CRM, сайты-визитки магазинов) | Низкий, отложенный | README сам называет условие: «после 500+ магазинов» (п.9, премиум-тариф для сетей/API) — преждевременно при 5–10 пилотных магазинах, но стоит проектировать текущий REST API так, чтобы не пришлось ломать обратную совместимость при открытии наружу (версионирование `/api/v1/` уже сейчас, если его ещё нет) |

**Действие с низкой стоимостью уже сейчас:** проверить, есть ли префикс версии в путях API
(`/api/v1/...`) — если нет, добавить до того, как появятся внешние потребители API, иначе любое
будущее открытие API потребует breaking-change для всех текущих клиентов (включая свой же фронт).

## 6. Удобная работа с клиентами и поставщиками — сводный взгляд

Это не отдельное новое направление, а угол зрения, под которым стоит смотреть на §3.1 (клиенты,
уже подробно расписано) и §3.3 (поставщики, слабое место). Сведено здесь для полноты картины:

**Клиенты** — почти всё уже спроектировано (`CUSTOMER_FEATURES_SKFO.md`): история долга в
WhatsApp, статус заказа, привязка к продаже, бейдж постоянного клиента, публичная витрина. Не
хватает единой карточки истории клиента как предпосылки — см. `COMPETITOR_MOYSKLAD_ANALYSIS.md`.

**Поставщики** — прямо противоположная сторона тех же операций, но без отдельного продуктового
разбора (см. §3.3): карточка поставщика с историей поставок и балансом, заявка поставщику по
`wa.me`-паттерну на основе минимальных остатков, в перспективе — прогноз закупки. Стоит закрыть
этот перекос до того, как пилот с нишами вроде «СтройДом» и «оптовики Беркат» (README §4, §6.4)
явно вскроет его — там расчёты с поставщиками не менее важны, чем с клиентами.

## 7. Сводная последовательность по времени

### До пилота (сессия 21) — жёсткий минимум
- CORS, rate-limiting на auth-эндпоинты, устранение опасных дефолтов в `config.py`.
- Offsite-бэкап (TODO уже стоит в `deploy/backup.sh`).
- Индексы на горячие FK-поля.
- Явное согласие на обработку персональных данных при регистрации (152-ФЗ).

### Во время пилота / сразу после первой волны обратной связи
- Пагинация `/sales` (если хоть один пилотный магазин активен — сотни продаж/месяц).
- Волна WhatsApp-фич из `CUSTOMER_FEATURES_SKFO.md` (долг/статус заказа/привязка клиента) — одна
  сессия, общий паттерн.
- Публичная витрина товара — первая публичная поверхность, готовить внимательно (rate-limit,
  tenant-изоляция).
- Refresh-токены, security headers, логирование ошибок (Sentry) — не блокируют пилот, но не тянуть
  долго после первых живых магазинов.
- Статистические инсайты в аналитике/Telegram-сводке (без LLM) — дёшево, полезно, безопасно.

### После пилота, по факту накопленных данных и обратной связи
- Карточка поставщика + заявка поставщику по WhatsApp-паттерну.
- Публичные страницы статуса заказа и «мой долг» — только если WhatsApp-сообщений недостаточно.
- LLM-слой советов в Telegram-сводке.
- Чат-бот поддержки на базе накопленных реальных вопросов пилотных магазинов.
- WhatsApp Business API (автоматизация) — если ручной `wa.me`-паттерн окажется недостаточным.
- Экспорт в 1С — по спросу конкретных клиентов.
- Версионирование API как задел — открытый API для партнёров, только после масштабирования
  (500+ магазинов, согласно README §9).

## 8. Общий принцип, применённый ко всему документу

README уже формулирует его прямо: «скорость фич важнее архитектурной красоты первые полгода» и
«если неделя поплыла — режем функциональность, но не сдвигаем пилот». Этот roadmap — не список
обязательных задач, а **приоритизированное меню**: часть безопасности — не переговорный пункт
(чужие долговые книги), остальное — берётся по факту того, что покажет живая обратная связь от
первых 5–10 магазинов, а не спланировано заранее «на всякий случай».
