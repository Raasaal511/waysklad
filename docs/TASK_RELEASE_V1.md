**Сейчас:** `.github/workflows/ci.yml` → `git pull` → `up -d --build` →

  ```

  docker compose -f docker-compose.prod.yml build
  ```

- [ ] Перед `git pull` запомнить текущий коммит (`git rev-parse HEAD`) и
  вывести его в лог джобы — чтобы откат был одной командой

## Блок 3 — Частичная оплата при продаже в долг (≈1 день)

### Зачем

Самый частый сценарий в регионе: покупка на 5 000 ₽, клиент даёт 3 000,
остальное «запиши на меня». Сейчас `PaymentMethod = cash | transfer |
credit`, и в долг уходит **вся** сумма. Продавец вынужден: продать в долг →
открыть долг → внести погашение 3 000. Это 3 экрана, 8+ касаний и частые
ошибки («забыл внести погашение» → спор с клиентом). После — одно поле на
том же экране.

### Как должно работать

- В форме продажи при выборе «В долг» появляется одно необязательное поле
  **«Заплатил сейчас»** (пусто = 0). Под ним строка: «В долг: 2 000 ₽».
- Кнопка: `В долг · 2 000 ₽` (см. 1.2).
- Долг создаётся на **остаток** (5 000 − 3 000 = 2 000). В карточке долга и
  в чеке видно: «Продажа на 5 000 ₽ · оплачено сразу 3 000 ₽ · в долг
  2 000 ₽».
- Выручка и прибыль — по полной сумме продажи, как сейчас (так же, как
  работает `prepayment` у продажи из выдачи заказа — см. комментарий в
  `domain/sales/entities.py`).
- «Выдано в долг» в сводке владельцу — только остаток (это и так так
  будет, потому что считается по таблице долгов).

### Правила

- `paid_now` допустим только при `payment_method = credit`. Иначе — 422 с
  понятным текстом.
- `0 ≤ paid_now < к оплате`. Если заплатил всё — это не долг:
  «Клиент заплатил всю сумму — выберите „Наличные“ или „Перевод“».
- Проверка лимита долга (`_check_debt_limit` в `create_sale.py`) — по
  остатку, а не по всей сумме.
- Клиент и срок «Долг до» обязательны, как сейчас.

### Что поменять (уточнить в шаге 0 по коду)

- [ ] **Домен:** `Sale.paid_now: Money` (дефолт 0) + валидация в
  `Sale.validate()`; сумма долга = `total − paid_now`.
- [ ] **Миграция:** колонка `sales.paid_now NUMERIC NOT NULL DEFAULT 0`.
- [ ] **API:** `SaleCreateRequest.paid_now`, ответ продажи отдаёт `paid_now`
  и `debt_amount`.
- [ ] **Офлайн:** `OfflineSaleRequest.paid_now` (`presentation/sync/schemas.py`)
  и `QueuedSale.paid_now` (`shared/offline/outbox.ts`). Старые записи в
  IndexedDB без поля = 0.
- [ ] **Возврат** (`return_sale.py`): долг уменьшается до нуля; если сумма
  возврата больше остатка долга — разница возвращается клиенту деньгами, в
  ответе и на экране это видно («Вернуть клиенту 1 000 ₽»). Отрицательного
  долга не бывает.
- [ ] **Редактирование и удаление продажи** (`edit_sale.py`,
  `delete_sale.py`): долг пересчитывается с учётом `paid_now`, как сейчас
  пересчитывается от суммы.
- [ ] **Чек** (`get_receipt_data.py` + картинка/PDF): строки «Оплачено сразу»
  и «В долг».
- [ ] **Фронт:** поле в `NewSaleForm.tsx` (только при «В долг»), подсказка
  с остатком, валидация до отправки; черновик чека (`saleDraft.ts`) хранит
  поле; `SaleDetailView.tsx` и карточка долга показывают разбивку.
- [ ] **Тесты (pytest):** долг = остаток; `paid_now ≥ суммы` → ошибка;
  `paid_now` при наличных → ошибка; лимит долга по остатку; офлайн-синк с
  `paid_now` (и повтор той же `client_op_id` не задваивает); возврат после
  частичной оплаты (частичный и полный); редактирование продажи.

### Не делать в этом релизе

Разбивку «из них оплачено сразу» в аналитике и Excel; выбор «наличными или
переводом» для `paid_now`. Записать в «Не вошло».

**Проверка руками на dev:** продать на 5 000 в долг с «Заплатил 3 000» →
долг клиента 2 000; чек показывает разбивку; вернуть товар на 4 000 →
долг 0, «вернуть клиенту 2 000»; выключить сеть → та же продажа уходит в
очередь → включить → долг 2 000, продажа одна.

## Блок 4 — Мобильная навигация: 4 вкладки + «Ещё» + «Продать» (≈0,5–1 день)

### Зачем

Сейчас на ширине < 900px внизу 9–10 пунктов (`app/AppLayout.tsx`,
`NAV_ITEMS`), подписи 10px, на экранах < 400px остаются одни иконки. Это
нарушает правило «≤ 7 пунктов» из `UX_SIMPLICITY_RULES.md` и Material 3
(3–5 направлений). Главного действия — «продать» — среди них нет: сейчас
это «Продажи» → «Новая продажа».

### Как должно работать (только ширина < 900px; десктопный сайдбар не меняется)

```
┌────────┬────────┬───────────┬───────┬──────┐
│Продажи │ Товары │ ● ПРОДАТЬ │ Долги │ Ещё  │
└────────┴────────┴───────────┴───────┴──────┘
```

- **Пять мест максимум.** Порядок приоритета пунктов:
  Продажи → Товары → Долги → Заказы → Склады → Клиенты → Витрина →
  Задачи → Аналитика → Сотрудники. Берутся первые 4 пункта, **доступные
  роли** (те же `roles`/`feature`, что сейчас), остальное — в «Ещё».
- **«Продать»** — крупная круглая кнопка по центру, цвет `--accent`,
  открывает `/sales/new`. Только для ролей, которым можно продавать (сейчас
  это owner, manager, seller). У остальных ролей центральной кнопки нет —
  просто 4 пункта + «Ещё».
- **«Ещё»** открывает нижнюю шторку: оставшиеся разделы (иконка + подпись,
  строки ≥ 48px), затем «Профиль» и «Выйти». Закрытие — свайп вниз, тап по
  фону, Esc, «назад» в браузере.
- Если текущая страница — из «Ещё», активной подсвечивается «Ещё».
- Подписи у всех пунктов видны на любой ширине от 320px, шрифт не меньше
  11px, зона касания ≥ 44px.
- **Шапка на телефоне:** убрать кнопку «Выйти» (переезжает в «Ещё» и
  Профиль) — случайный выход посреди продажи. Логотип, название магазина,
  колокольчик, аватар остаются.
- **Офлайн-индикатор на телефоне.** Сейчас «Не отправлено: N» показывается
  только в сайдбаре (≥ 900px) — продавец на рынке с телефона не видит, что
  продажи ждут отправки. Показать в мобильной шапке маленький бейдж
  «⏳ N», по тапу — короткое пояснение.
- **Онбординг-тур** (`app/OnboardingContext.tsx`: шаги указывают на
