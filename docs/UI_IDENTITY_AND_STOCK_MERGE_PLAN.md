# План: визуальная идентичность UI + пересмотр раздела «Остатки»

Зафиксировано перед реализацией по запросу пользователя. Две связанные, но
независимые задачи: (1) уйти от «бутстрапного» плоского вида к своей
визуальной идентичности без пустоты, (2) решить дублирование
Остатки/Товары/Продажи — по ощущению пользователя «Остатки» наполовину
дублирует Товары и наполовину Продажи, и непонятно, зачем это отдельный раздел.

## Контекст: почему сейчас «бутстрапно»

Дизайн-токены в `frontend/src/index.css` уже настоящие (не дефолт Bootstrap):
`--text`, `--bg`, `--border`, `--accent` (4 акцентные палитры + light/dark
тема, `index.css:24-93`), `--radius`. Но токены нигде не превращаются в
характерный визуальный язык:

- `.card` — плоская белая коробка, обводка 1px, без тени/градиента/текстуры
  (`index.css:363-370`);
- `.btn-primary` — заливка одним плоским цветом (`index.css:498-501`);
- поля ввода — обычные обведённые прямоугольники (`index.css:411-419`);
- `.product-tile` — та же плоская коробка что и `.card`.

Единственное место с реальной визуальной работой — экран логина
(`.auth-screen`/`.auth-card`, `index.css:154-360`: градиентный фон, blur,
слоистые тени). Всё остальное приложение выглядит как черновик рядом с ним.

Пустота — отдельная, но связанная проблема:
- `.product-grid` колонки `minmax(160px, 1fr)` (`index.css:1591-1595`) на
  десктопном `.app-content` (`max-width: 960px`, padding `28px 32px`,
  `index.css:975-979`) — редкие плитки расползаются с большими промежутками;
- `.warehouse-grid` `minmax(220px, 1fr)` (`index.css:1544-1548`) — карточка
  склада (иконка, название, один адрес, бейджи) занимает узкую долю широкой
  колонки, остальное пусто (`StockPage.tsx:110-132`);
- `.grid-stats` (`index.css:1538-1542`) размазывает 2-3 цифры на всю ширину
  карточки на Остатках/Продажах/Истории;
- пустые фото товара — фиксированный квадрат `aspect-ratio: 1`
  (`index.css:2026-2032`) с одной иконкой-плейсхолдером посередине.

## Часть 1 — визуальная идентичность

Не рестайлинг токенов (они годные), а превращение токенов в конкретный язык
поверхностей, теней, плотности. Ориентир — уровень проработки `.auth-screen`,
распространённый на весь остальной интерфейс.

### 1.1 Поверхности (карточки, плитки, панели)
- Ввести настоящую глубину: мягкая тень + едва заметный градиент/подсветка
  на `.card`, `.product-tile`, `.warehouse-card` вместо плоской заливки +
  обводки 1px. Не имитировать Material «поднятые» карточки один в один —
  выработать свой почерк (акцентная кромка сверху/сбоку, или fade у нижнего
  края — решить на макете/прототипе перед массовым переносом).
- Пересмотреть `.card` `max-width: 360px` по умолчанию (`index.css:363`) —
  либо убрать дефолт, либо сделать плотность контента управляющим фактором
  (короткая карточка = узкая, длинная = full), а не наоборот.

### 1.2 Плотность и пустота
- Сузить авто-подбор колонок в `.product-grid`/`.warehouse-grid` или добавить
  верхнюю границу колонок на широких экранах (`repeat(auto-fill, ...)` →
  ограничить `minmax(160px, 220px)` с `justify-content` вместо `1fr`,
  чтобы плитки не растягивались до пустоты).
- `.grid-stats`: перепроверить каждое использование — если карточка почти
  пустая на широком экране, либо сузить контейнер, либо добавить контент
  (спарклайн/тренд), а не тянуть 3 цифры на всю ширину.
- Плейсхолдер пустого фото — заменить нейтральную иконку на что-то с меньшей
  «дырой»: паттерн/текстура вместо одной мелкой иконки в большом квадрате,
  либо уменьшить квадрат для товаров без фото.

### 1.3 Компоненты
- `Button`/`IconButton` уже централизованы (`shared/ui/`) — доработка тут
  дешёвая: обновить только CSS-классы, JSX не трогать.
- `.card`, `.badge`, `.product-tile`, голые `<table>` — это чистые CSS-классы
  без React-обёртки (см. `shared/ui/` — нет `Card`/`Table`/`Tile` компонентов).
  Редизайн этой части — в основном CSS + точечная правка разметки, не
  создание новой инфраструктуры компонентов. Не создавать `Card.tsx` и т.п.
  без явной необходимости — держаться принципа проекта «без лишних абстракций».

### 1.4 Порядок
1. Прототип на 1-2 экранах (предлагаю: `ProductsPage` — самый нагруженный, и
   `WarehouseDetailPage` — уже частично приведён к `product-tile` в прошлой
   сессии) — согласовать визуальное направление с пользователем до переноса
   на весь проект.
2. Перенести согласованный стиль в общие классы (`.card`, `.product-tile`,
   `.badge`, кнопки) — так как классы общие, обновление автоматически
   применится везде, где они используются.
3. Точечно поправить страницы, где паттерн не general-purpose (голые
   `<table>` в `ProductDetailCard`, `MovementHistoryPage` и т.д.).

## Часть 2 — пересмотр «Остатки»

### Подтверждённое дублирование (см. исследование перед этим планом)
- Плитка товара (фото+название+остаток) реализована заново в четырёх местах:
  `ProductsPage.tsx:369-395`, `WarehouseDetailPage.tsx:296-315`,
  `SalePage.tsx:1053-1104`, `shared.tsx:407-452` (MovementForm).
- Панель поиска/фильтра (`sale-search-panel`/`sale-filters-row`, названа по
  Продажам, но переиспользуется везде) — четыре независимые копии:
  `ProductsPage.tsx:307-351`, `WarehouseDetailPage.tsx:254-285`,
  `SalePage.tsx:961-1035`, `shared.tsx:361-390`.
- «Приёмка» (пополнение остатка) и «Продажа» — структурно одна и та же форма
  (подбор товара плиткой → корзина → таблица строк с шагами количества):
  `SalePage.tsx:1119-1219` против `shared.tsx:466-563`, одни и те же CSS-классы
  `cart-table`/`cart-qty-stepper`.
- Каждая страница отдельно тянет `listAllProducts()`/`listStock()` и сама
  пересчитывает остаток по товару — три независимые реализации одной и той
  же выборки.
- `StockPage.tsx` (верхний уровень «Остатки») — по сути список складов с
  агрегатами; всё уникальное содержимое — группировка по складу,
  «ответственные», рекомендации «стоит дозаказать»
  (`WarehouseDetailPage.tsx:321-378`). Всё остальное — повтор
  Товаров/Продаж. Это и есть источник ощущения «половина Товаров, половина
  Продаж».

### Что у «Остатки» есть уникального (нельзя просто удалить раздел)
- Разбивка по складам (мульти-склад — конкретный склад, конкретный остаток).
- Операции движения товара: приёмка, списание, перемещение между складами.
- «Ответственные» за склад (права доступа).
- Рекомендации «стоит дозаказать» — по складу.
- Журнал движений (`MovementHistoryPage.tsx`).

Это данные и операции, которых нет ни в Товарах (справочник без склада), ни в
Продажах (расход, не приход/перемещение). Раздел не лишний по сути — лишний
дублирующий UI вокруг него.

### Направления решения (на выбор/обсуждение с пользователем, не решать
### в одиночку — затрагивает структуру навигации)

**Вариант А — «Остатки» становится складским модулем, товарная витрина уходит.**
Убрать из `WarehouseDetailPage` общую плитку «Товары на складе» как способ
пролистать каталог (это задача Товаров) и оставить только то, что уникально
для склада: сводка остатков (числа, не карточки товара), операции
(приёмка/списание/перемещение), рекомендации к дозаказу, ответственные,
журнал. Просмотр/поиск конкретного товара — всегда через Товары
(`ProductDetailCard` уже открывается из Остатков без перехода страницы,
задел есть).

**Вариант Б — слить точку входа, оставить склад как фильтр.**
Убрать «Остатки» из верхней навигации. В Товарах добавить переключатель
склада (сейчас `ProductsPage` показывает суммарный остаток по всем складам
без разбивки) — просмотр по складу становится фильтром на одной странице,
а не отдельным разделом. Операции приёмки/списания/перемещения переезжают в
меню действий на Товарах (или остаются в отдельной модалке, но без отдельной
страницы-обёртки).

**Вариант В — оставить разделы, но выдернуть общий UI в переиспользуемые
компоненты.** Не менять структуру навигации, но убрать сам факт дублирования
кода/паттерна: общий `ProductTileGrid` (фото+название+остаток+действие),
общий `ProductSearchFilterBar`, общий `MovementCart` (переиспользовать между
Приёмкой и Продажей). Дублирование ощущений пользователя это не уберёт (три
раздела продолжат визуально пересекаться), но уберёт дублирование кода и
даст единую точку правки для части 1 (визуальная идентичность).

Рекомендация: начать с **варианта В** (низкий риск, чистит код, не ломает
привычную навигацию), затем по ощущениям от использования решить, нужен ли
А или Б поверх. Менять навигацию (А/Б) — обсудить с пользователем отдельно
перед реализацией, это меняет привычные маршруты в уже используемом
приложении.

## Порядок реализации (предложение)

1. Согласовать направление визуальной идентичности на 1-2 экранах (прототип,
   не весь проект сразу).
2. Вынести общие паттерны (плитка товара, панель поиска/фильтра, корзина
   движения) в переиспользуемые компоненты — вариант В из части 2.
3. Перенести согласованный визуальный стиль на общие классы/компоненты —
   часть 1, п.1.4.
4. По результатам использования — решить с пользователем, нужен ли перенос
   структуры навигации (варианты А/Б части 2).
5. Проверка на каждом шаге: `tsc --noEmit`, ручная проверка в браузере,
   backend pytest если задеты эндпоинты.
