# Задача: админ-панель платформы v2 — редизайн, данные о магазинах, состояние сервера

**Статус:** к реализации
**Дата постановки:** 2026-09-21
**Где:** `/admin` — `frontend/src/pages/admin/AdminPage.tsx`,
`backend/app/presentation/admin/`
**Объём:** бэкенд ~1.5 дня, фронтенд ~1.5–2 дня
**Кто пользуется:** только владелец платформы (вы), с ноутбука и с телефона

---

## Зачем это сейчас

Админка — единственное место, где вы увидите, работает продукт или нет.
Через месяц после пилота вопрос будет не «красиво ли», а «кто из десяти
магазинов ещё пробивает продажи, а кто бросил и почему». Сейчас панель
показывает шесть магазинов карточками, проценты CPU и четыре одинаковые
ошибки — по этому ничего решить нельзя.

Поэтому задача не «покрасить», а собрать рабочий инструмент: обзор
платформы, карточка каждого магазина с активностью, честное состояние
сервера.

**Приватность.** Админ платформы видит агрегаты и техническую
информацию, но не содержимое чужого бизнеса: не показываем суммы долгов
конкретных клиентов магазина, телефоны покупателей, тексты чатов и
закупочные цены. Это прямо следует из обещания в README про доверие к
сохранности данных. Всё, что показываем про магазин, — счётчики,
даты и статусы.

---

## Как работать (протокол)

1. Сначала план в чат: какие эндпоинты добавишь, какие файлы тронешь,
   где данные уже есть, а где понадобится новый запрос. Код — после «ок».
2. Порядок: сначала часть A (бэкенд) целиком, потом часть B (фронт).
   Один пункт — один коммит, отчёт не длиннее 10 строк.
3. Правила экономии контекста из `CLAUDE.md` действуют.
4. Тяжёлые агрегаты считаем в SQL, не в Python; никаких N+1.
   Каждый новый эндпоинт кэшируем на 30–60 секунд.
5. Все новые эндпоинты — под существующей админской авторизацией
   (`/api/admin/*`), rate limit как у текущих.

## Часть A — бэкенд

### A1. Обзор платформы — `GET /api/admin/overview`

```ts
{
  shops: { total, active_7d, active_30d, new_7d, new_30d, suspended, storefront_on },
  users: { total, active_7d },            // сотрудники магазинов
  customers: { total, new_7d },           // покупатели витрин
  sales: { today_count, today_sum, d7_count, d7_sum, d30_count, d30_sum },
  debts: { open_count, open_sum },        // агрегат по платформе, без разбивки по клиентам
  storefront: { requests_7d, accepted_7d },
  series_30d: {                            // массивы по дням, для графиков
    date: string[], new_shops: number[], sales_count: number[],
    active_shops: number[]
  }
}
```

- «Активен» = была хотя бы одна продажа за период.
- Сегодня — по московскому времени, как и вечерние сводки бота.

### A2. Список магазинов — расширить `GET /api/admin/tenants`

Параметры: `query`, `status` (all/active/quiet/churned/suspended),
`storefront` (on/off), `sort` (last_activity/sales_30d/created_at/name),
`limit`, `offset`.

На каждый магазин:

```ts
{
  id, name, slug, city, created_at,
  is_suspended, is_verified, storefront_enabled,
  owner_name, users_count, warehouses_count, products_count,
  last_sale_at, last_login_at,
  sales_7d, sales_30d, sales_sum_30d,
  debts_open_count, storefront_requests_30d,
  health: "active" | "quiet" | "churned" | "new"
}
```

`health`: `new` — зарегистрирован меньше 7 дней назад и продаж ещё нет;
`active` — продажа была ≤ 3 дней назад; `quiet` — 4–14 дней;
`churned` — больше 14 дней или ни одной продажи у магазина старше недели.
Пороги вынеси в константы домена, не разбрасывай по коду.

### A3. Карточка магазина — `GET /api/admin/tenants/{id}`

Профиль (всё из A2) плюс:

```ts
{
  sales_series_30d: { date: string[], count: number[], sum: string[] },
  users: [{ id, name, role, is_active, last_login_at }],
  warehouses: [{ id, name, address, show_on_storefront, positions_count }],
  top_products: [{ id, name, sold_30d }],        // 5 штук, только названия и счётчик
  storefront: { enabled, slug, products_on_storefront, requests_30d, reviews_count },
  recent_activity: [{ at, actor_name, action, entity }],  // последние 20 из audit_log
  totals: { products, sales_all_time, debts_open_count, customers_served }
}
```

Закупочные цены, суммы долгов по клиентам, телефоны покупателей и тексты
чатов сюда НЕ попадают.

### A4. Состояние сервера — расширить `GET /api/admin/status`

Добавить к тому, что есть:

```ts
{
  app: { version, git_sha, started_at, uptime_seconds, workers },
  system: { cpu_percent, load_avg: [1,5,15], ram_used, ram_total,
            disk_used, disk_total, disk_free_percent },
  db: { ok, size_bytes, connections_active, connections_max,
        slowest_query_ms_1h | null },
  redis: { ok, used_memory, keys, hit_rate_1h | null },
  uploads: { files_count, size_bytes },
  api: { rps_1h, p50_ms, p95_ms, errors_5xx_24h, errors_4xx_24h },
  backup: { last_at | null, size_bytes | null, offsite_ok: boolean },
  tls: { domain, expires_at, days_left } | null
}
```

- `p50/p95` и `rps` — из лёгкого счётчика в middleware (скользящее окно в
  Redis), без внешних систем мониторинга.
- `backup` — читаем метаданные последнего файла бэкапа; `offsite_ok`
  честно возвращает `false`, пока внешняя копия не настроена.
- Поля, которые получить нельзя, возвращаем `null`, а не выдумываем.

### A5. Ошибки — `GET /api/admin/error-logs` доработать

- Группировка: `GET /api/admin/error-groups` →
  `[{ signature, type, path, method, count_24h, count_7d, first_at, last_at, sample_id }]`,
  сортировка по `count_24h`.
- У отдельной записи — `GET /api/admin/error-logs/{id}`: время, путь,
  метод, тип, сообщение, статус, tenant_id (без персональных данных),
  стек (если хранится).
- Пометка «решено»: `POST /api/admin/error-groups/{signature}/resolve` —
  группа уходит из основного списка, но остаётся во вкладке «Решённые».
- Фильтры: период (24ч / 7д / 30д), тип, путь, только нерешённые.

### A6. Тесты и документация

Тесты на агрегаты (границы `health`, пустая платформа, магазин без
продаж), на права (обычный владелец не получает `/api/admin/*`), на
отсутствие персональных данных в ответах. Записать контракты в
`frontend/api_docs/admin_status.md` (раздел v2) и в `README.md` журнала.

## Часть B — фронтенд, редизайн

Тёмная тема остаётся, но по тем же токенам, что и остальной проект.
Никаких новых библиотек: графики — инлайновый SVG.

### B1. Каркас

- [ ] Контейнер `max-width: 1440px`, поля 24/20/16.
- [ ] Слева вертикальная навигация 220px (≥1024): Обзор, Магазины,
  Сервер, Ошибки. Внизу — «Выйти» и версия сборки. На <1024 —
  верхняя лента вкладок с горизонтальным скроллом.
- [ ] Шапка: слева название раздела H1 24/700, справа — переключатель
  периода (24ч / 7д / 30д, где применимо), время последнего обновления
  и кнопка обновить. Автообновление раз в 60 секунд, пауза, когда
  вкладка скрыта.
- [ ] Карточки: фон `--bg`, radius 16, padding 20, рамка 1px `--border`.
  Никаких «плиток в три ряда» ради заполнения пустоты — сетка
  подстраивается под содержимое.

### B2. Раздел «Обзор» (новый, главный)

- [ ] Первая строка — 4 крупных показателя: «Магазины», «Активны за 7
  дней» (с долей в процентах), «Продажи за 30 дней» (количество и
  сумма), «Заявки с витрины». В каждом — значение 32/700, подпись
  13/600 `--text-muted`, дельта к прошлому периоду (стрелка и процент,
  зелёная или красная).
- [ ] График за 30 дней: продажи по дням (столбики) и линия активных
  магазинов. Подписи осей, сетка по горизонтали, тултип по наведению с
  датой и значениями. Один компонент `<TimeSeriesChart>` на SVG,
  переиспользуемый.
- [ ] «Требует внимания» — список из трёх блоков: магазины, затихшие за
  последнюю неделю (было продажи, стало ноль); магазины без единой
  продажи спустя неделю после регистрации; топ-3 группы ошибок за 24
  часа. Каждая строка кликабельна и ведёт в нужный раздел.
- [ ] «Недавно зарегистрированные» — компактная таблица на 5 строк со
  ссылками на карточку магазина.

### B3. Раздел «Магазины»

- [ ] Вместо плиток — таблица с сортировкой по клику на заголовок:
  Магазин (название + slug), Город, Регистрация, Последняя активность,
  Продажи 7д / 30д, Товары, Пользователи, Витрина, Статус.
- [ ] Статус — цветная точка с подписью: активен (`--accent`), затих
  (`--warning`), бросил (`--danger`), новый (`--text-muted`),
  заблокирован (перечёркнутая строка).
- [ ] Панель сверху: поиск, чипы статусов со счётчиками, фильтр
  «витрина вкл/выкл», сортировка. Значения — в URL.
- [ ] «Последняя активность» показываем относительным временем
  («2 часа назад», «5 дней назад») с точной датой в тултипе.
- [ ] Строка кликом открывает карточку магазина.
- [ ] < 900px таблица превращается в список карточек с теми же данными
  (две колонки значений), без горизонтального скролла.

### B4. Карточка магазина (новая страница `/admin/tenants/:id`)

- [ ] Шапка: логотип, название, slug-ссылка на витрину, город, статус,
  дата регистрации, кнопки «Заблокировать / Разблокировать» и
  «Проверенный» (с подтверждением действия).
- [ ] Четыре показателя: продажи 30д (кол-во и сумма), товары,
  пользователи, открытые долги (только количество).
- [ ] График продаж за 30 дней (тот же `<TimeSeriesChart>`).
- [ ] Две колонки: слева «Пользователи» (имя, роль, последний вход),
  «Склады» (название, адрес, позиций, витрина); справа «Топ товаров за
  30 дней» и «Витрина» (вкл/выкл, товаров на витрине, заявок, отзывов).
- [ ] Лента последних действий (20 записей): время, кто, что сделал.
- [ ] Пустые состояния для каждого блока: «Продаж пока нет»,
  «Сотрудников нет» — без иллюстраций, просто текст.

### B5. Раздел «Сервер»

- [ ] Верхняя строка: три «светофора» — Приложение, База данных, Redis:
  крупный статус (в норме / деградация / недоступно), под ним ключевая
  цифра (uptime, соединения, память).
- [ ] Метрики карточками: CPU, RAM, Диск — кольцевой индикатор вместо
  полоски, под ним абсолютные значения («1.5 ГБ из 3.8 ГБ»), цвет по
  порогам: до 70% — `--accent`, 70–90% — `--warning`, выше —
  `--danger`.
- [ ] График нагрузки за час — как сейчас, но с осями, сеткой,
  подписями и тултипом; легенда сверху справа.
- [ ] Блок «API»: RPS за час, p50, p95, ошибки 5xx и 4xx за сутки.
- [ ] Блок «Данные»: размер БД, число соединений, объём uploads, память
  Redis.
- [ ] Блок «Эксплуатация»: версия и коммит сборки, время запуска,
  последний бэкап (дата, размер, отметка «внешняя копия: да/нет» —
  если нет, показать предупреждение `--warning`), срок действия
  сертификата (дней осталось, при < 14 — `--danger`).
- [ ] Значения `null` показываем как «нет данных», а не как ноль.

### B6. Раздел «Ошибки»

- [ ] По умолчанию — группы: тип, путь, счётчик за 24ч и 7д, первое и
  последнее появление, кнопка «Решено». Раскрытие показывает последние
  записи группы.
- [ ] Фильтры: период, тип, путь, «только нерешённые», поиск.
- [ ] Отдельная запись открывается панелью справа: полный текст,
  заголовки запроса без персональных данных, стек моноширинным
  шрифтом с переносами, кнопка «Скопировать».
- [ ] Пусто → «Ошибок за выбранный период нет» и подпись, за какой
  период смотрим.

### B7. Общее

- [ ] Скелетоны на загрузке каждого блока, ошибка запроса — «Не удалось
  загрузить» и «Повторить» внутри блока, а не на всю страницу.
- [ ] Относительное время везде одинаковое, одной функцией.
- [ ] Числа: разряды через тонкий пробел, суммы через `formatMoney`,
  байты через общий `formatBytes`.
- [ ] Клавиатура: таблицы и фильтры доступны табом, у иконочных кнопок
  `aria-label`.
- [ ] Мобильная версия проверена на 375: навигация лентой, таблицы
  карточками, графики ужимаются без горизонтального скролла страницы.

## Приёмка

Скриншоты всех четырёх разделов на 375 и 1440. На платформе с шестью
магазинами и одним активным видно: сколько магазинов живых, кто затих,
у кого ни одной продажи, какие ошибки повторяются и настроен ли внешний
бэкап. Карточка магазина открывается по клику и показывает активность за
30 дней. `npm run build`, `npm run lint`, `pytest` — чисто.

---

## Что НЕ входит

- Вход под владельцем магазина (impersonation) — отдельное решение, у
  него серьёзные последствия для доверия.
- Персональные данные покупателей и содержимое чатов.
- Внешние системы мониторинга (Grafana, Sentry) — только свои данные.
- Рассылки и уведомления админу — отдельная задача.
