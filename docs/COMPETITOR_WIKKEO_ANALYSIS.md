# Анализ Wikkeo — что взять для витрины/карточки товара

**Дата:** 2026-09-13
**Источник:** реальный обход через headless-браузер (Playwright, `npx
playwright screenshot`) — сайт полностью на JS-рендеринге (SPA), обычный
текстовый fetch отдаёт пустой каркас, поэтому первый заход по URL не сработал.
Просмотрены: главная страница + карточки трёх разных товаров (часы CS
3.6/3.8 см WCS4, компрессионный лонгслив Nike, колонка JBL Flip 7).

**Цель документа:** зафиксировать конкретные находки, чтобы позже осознанно
решить, что из этого имеет смысл для нашей витрины (`docs/STOREFRONT_PLAN.md`)
и общего ощущения «пустоты» приложения, которое отметил пользователь. Ничего
из этого не реализовано — список идей для будущего разбора.

## Важно: Wikkeo — маркетплейс, не единая витрина

Главная страница показывает **множество независимых продавцов** в одном
каталоге: логотипы брендов-магазинов (FAIR, ACSES HOLL, Optom Mosco…, HAS OPT
и др.), баннер «Продавайте на Wikkeo — Комиссия площадки 0%», разделы
Распродажа/Спецпредложения/Новинки/Тренды, каждый товар подписан именем
конкретного магазина-продавца («Похожие товары от других продавцов» — тоже
от разных магазинов). Это модель Wildberries/AliExpress: одна платформа, много
продавцов, общий поиск/каталог по всем сразу.

**Это принципиально другая архитектура, чем наша модель** — у нас один tenant
= одна изолированная витрина по своему `slug`, без общего кросс-магазинного
каталога. Прямое копирование модели маркетплейса означало бы новый продукт
(общий поиск по всем tenant'ам, модерация, эскроу-платежи, комиссия площадки)
— уже обсуждали и отклонили как выходящее за рамки роли «бесплатный учёт для
малого бизнеса». Ниже — только то, что применимо **внутри одной витрины
одного магазина**, не сама модель маркетплейса.

## Карточка товара — полная структура (по 3 просмотренным карточкам)

### Заголовок и цена
- Название, артикул, рейтинг + число отзывов, ссылка на город/магазин
- **Оптовая ценовая вилка по объёму**: «300₽ / 1шт», «280₽ / 10-29шт», «270₽ /
  30-1000шт» — цена падает по количеству в одной позиции (актуально скорее для
  B2B-опта, не для нашей модели розницы, но сама идея «цена по объёму» может
  быть интересна для оптовых клиентов малого бизнеса)
- Бейдж-лейбл товара («РЕКОРД ПРОДАЖ», «10+ расцветок») — маркетинговая метка
- Счётчик просмотров за период («729 просмотров за 90 дней», «11 217
  просмотров за 90 дней») и счётчик продаж («Продано: 121»)

### Галерея
- Фото/видео товара от продавца
- Отдельно — **«Фото и видео реальных покупателей»**: контент, подтянутый из
  отзывов (UGC), в отдельной галерее рядом с официальными фото

### Варианты
- Таб верхнего уровня по одному атрибуту (диаметр, или цвет — зависит от
  товара), внутри — список по второму атрибуту
- Каждый вариант в списке: своя миниатюра, **человекочитаемое название**
  («Полностью серебро WCS4-1», не просто «серебро»), точный остаток в штуках,
  степпер количества +/- прямо в списке (без перехода на отдельную страницу)
- **Уценённый вариант помечен прямо в названии**: «Чёрный (Повреждённая
  упаковка)» — тот же товар/цвет, но с явной пометкой дефекта как отдельная
  строка варианта, не отдельный товар

### Корзина по сумме заказа у одного продавца
- «Добавьте любых товаров в магазине MS ОПТ на 3 000 ₽, чтобы получить первую
  скидку» — правило скидки не по конкретному товару, а по общей сумме заказа
  клиента у ЭТОГО продавца, с прогресс-баром/слайдером визуализации
- «Минимальный заказ от 2 000 ₽» — порог минимальной суммы заказа у продавца

### Карточка продавца (не товара)
- Имя магазина, бейдж уровня («PRIME»), число подписчиков, число заказов,
  минимальная сумма заказа, «На Wikkeo с декабря 2023» — отдельный рейтинг
  магазина, независимый от рейтинга конкретного товара

### Текстовые блоки — аккордеоны
- «О товаре» — описание, буллет-список характеристик для техники («Качество
  звука 9/10», «Басса 7.5/10», «Мощность 35 Вт»)
- «Гарантии» — условия возврата/замены при браке
- Отдельный блок FAQ со ссылками: «Возврат денег», «Способы оплаты», «Условия
  доставки», «Возврат товара» — все свёрнуты по умолчанию, разворачиваются по
  клику

### Похожие товары
- «Похожие товары от других продавцов» — карусель товаров той же категории,
  но не обязательно того же магазина (межпродавцовая рекомендация — у нас
  неприменимо буквально, единая витрина одного магазина могла бы показывать
  «похожие товары этого же магазина»)

### Отзывы
- Общий счётчик + средний рейтинг с **гистограммой распределения** (сколько
  голосов на каждую из 5 звёзд, горизontal bar chart)
- Фильтры сортировки: «Дата», «Оценка», «Только с фото»
- Каждый отзыв: автор (обезличенный ник вида `@wikkeo-XXXXXX`), звёзды, текст,
  дата («2 дня назад»), опционально фото от покупателя, счётчик «полезно»
  (лайк/дизлайк), **ответ продавца на отзыв** отдельным блоком

## Разрыв с нашей моделью — конкретно

1. **`ProductVariant` (`app/domain/catalog/entities.py:24`) не имеет своего
   фото** — только `size`/`color`/`barcode`. У wikkeo каждый вариант — со
   своей фотографией.
2. **Наша витрина отдаёт `in_stock: bool`, не точное число** (см.
   `GetStorefrontProductUseCase`/`GetStorefrontCatalogUseCase`) — осознанное
   решение (не палить конкуренту точные остатки через публичный API). Wikkeo
   показывает голое число в штуках без всякой защиты — но там это нормально,
   так как площадка не конкурирует сама с собой (продавцы не видят чужой
   бэк-офис через фронт).
3. **Нет отзывов вообще** — ни на товар, ни на магазин. Это самый крупный
   структурный разрыв: вся секция «Отзывы» с рейтингом и UGC-контентом у нас
   отсутствует как концепция. Требует новой сущности (`Review`?), кто оставляет
   отзыв (покупатель через `StorefrontRequest`/чат после сделки?) — не решено.
4. **Нет счётчиков просмотров/продаж на карточке товара** — ни `views_count`,
   ни `sold_count` не хранятся и не показываются.
5. **Нет двумерной группировки вариантов** — `ProductVariant` сейчас плоский
   список `size`+`color`, без явного «таб по одной оси, список по другой».
6. **Нет понятия «эта позиция дефектная/уценённая»** — у нас `Product`/
   `ProductVariant` не различают «этот же товар, но с браком» как отдельную
   позицию каталога.
7. **Нет скидки по сумме заказа** — только по конкретному товару/скидка на
   продажу целиком, не «набери на N рублей у этого продавца — получи скидку».

## Разбор «взять / адаптировать / отклонить» — предварительно, не решено

- **Взять, вероятно:**
  - фото на уровне варианта (реальный, некрупный пробел — расширение
    `ProductVariant.photo`)
  - буллет-список характеристик в описании товара (чисто контентное решение,
    возможно уже покрывается свободным текстовым полем описания)
- **Обсудить отдельно, крупнее по объёму:**
  - отзывы/рейтинг — самая ценная находка с точки зрения доверия покупателя,
    но целая новая подсистема (сущность, кто оставляет, модерация ли нужна)
  - счётчики просмотров/продаж — простое дополнение к аналитике, но нужно
    решить, публичны ли они (конкурентный риск тот же, что с остатками)
- **Адаптировать, не копировать буквально:**
  - точный остаток в публичном API — уже обсуждали и отклонили; если делать
    точность, то не голым числом всем подряд, а с порогом или только владельцу
- **Скорее отклонить для нашего масштаба:**
  - скидка по сумме заказа у продавца, ценовая вилка по объёму закупки —
    больше про B2B-опт, чем про модель ВайСклада (малый бизнес ЧР, конечный
    покупатель, не перепродавцы)
  - «похожие товары от других продавцов» — требует кросс-tenant каталога,
    архитектурно другой продукт (см. раздел выше про маркетплейс)

## Общая тема: «приложение выглядит пустым»

Пользователь отдельно заметил, что наше приложение в целом выглядит
недостаточно информативным по сравнению с wikkeo. После полного обхода видно,
что главный источник «богатости» wikkeo — это социальное доказательство
(отзывы, рейтинги, счётчики продаж/просмотров), а не только больше полей на
карточке. Держать в уме при следующем заходе на эту тему:
- разобраться, что именно создаёт ощущение пустоты у пользователя — возможно,
  это не только карточка товара, но и общий стиль/плотность экранов
- отзывы/рейтинги — вероятно, самый весомый кандидат, если решать именно
  «ощущение пустоты», а не косметику карточки
- не начинать реализацию, пока пользователь явно не разберёт этот пункт и не
  укажет конкретные экраны/приоритет
