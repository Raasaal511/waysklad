## Как проверялось

Живой прогон через Playwright против dev-стека (`npm run dev`, backend на
`:18000`), с перехватом всех `fetch`-запросов на `/api/*` при обычной навигации
пользователя: логин → Товары → открыть форму нового товара → Продажи → открыть
форму новой продажи. Плюс чтение кода `entities/*/api.ts` и мест вызова в
`pages/*`.

## Корневая причина: нет ни одного слоя кеширования запросов

`shared/api/client.ts` — тонкая обёртка над `fetch`, без кеша, без
дедупликации параллельных одинаковых запросов, без инвалидации. Каждый
компонент, которому нужен список товаров/складов/сотрудников, вызывает
`listAllProducts()`/`listWarehouses()`/`listEmployees()` заново, даже если
соседний компонент на той же странице (или родитель) уже получил те же данные
секунду назад. Это системная причина почти всех находок ниже — не баг в одном
месте, а отсутствие архитектурного слоя.

**Вариант решения (не выбран, для рассмотрения в будущей сессии):**
[TanStack Query](https://tanstack.com/query) (react-query) — де-факто стандарт
для этого класса проблем, даёт кеш по ключу, дедупликацию одновременных
запросов, background-refetch, инвалидацию по мутациям. Альтернатива полегче —
свой минимальный in-memory кеш поверх `api.get` с TTL и ручной инвалидацией
после мутаций (`createProduct`, `receiveGoods` и т.п.), без новой зависимости.
Выбор — по вкусу, когда дойдут руки; оба варианта закрывают 90% находок ниже.

## Реальные (не dev-артефакт) находки

### 1. `NotificationBell` смонтирован дважды одновременно — двойной поллинг

`app/AppLayout.tsx:203` и `app/AppLayout.tsx:246` — два разных `<NotificationBell>`,
один для мобильной/свёрнутой шапки, один для десктопной. Оба видимости
переключаются CSS-медиа-запросами, но **оба остаются смонтированы в DOM
всегда** — значит у каждого свой независимый `useEffect` с
`setInterval(tick, 30_000)` (`app/NotificationBell.tsx:31-49`). Итог: `GET
/api/notifications` уходит **дважды каждые 30 секунд**, постоянно, пока открыта
вкладка — это не разовая загрузка, а вечный фоновый дубль.

**Фикс:** поднять состояние уведомлений в `AppLayout` (один `useEffect` с
поллингом на уровне layout), передавать `items`/`unread`/обработчики в оба
`NotificationBell` как пропсы — сам компонент становится чисто презентационным.

### 2. Одни и те же справочники перезапрашиваются на каждой странице

`listAllProducts()`, `listStock()`, `listWarehouses()`, `listUnits()`,
`listCategories()`, `listEmployees()` вызываются независимо (без кеша) в
как минимум 8 разных местах:

| Файл | Что грузит |
|---|---|
| `pages/products/ProductsPage.tsx:171,251-254` | products, categories, units, stock, warehouses |
| `pages/sales/SalePage.tsx:633-636` (в `NewSaleForm`) | categories, units, stock, warehouses |
| `pages/sales/SalePage.tsx:1431-1434` (в `LastSaleCard`) | products, units, employees — **повторно**, хотя открывается сразу после того же `NewSaleForm` |
| `pages/orders/OrdersPage.tsx:224-228` | products, units, warehouses, stock |
| `pages/tasks/TasksPage.tsx:158-162` | employees, products, warehouses, units, stock |
| `pages/stock/StockPage.tsx:24` | stock, warehouses, products |
| `pages/stock/WarehouseDetailPage.tsx:101-106` | stock, warehouses, products, units, categories, employees |
| `pages/stock/MovementHistoryPage.tsx:113-116` | warehouses, products, units, employees |
| `pages/stock/shared.tsx:57` | employees |

Ничего из этого не переиспользуется между переходами. Переключился
Продажа → Заказы → Задачи туда-обратно за 5 секунд — три независимых полных
перезапроса одного и того же каталога товаров (`limit=1000`), складов и
сотрудников, хотя данные заведомо не устарели.

Отдельно: `LastSaleCard` (открывается сразу после успешной продажи, из той же
`SalePage`) заново грузит `products`/`units`/`employees`, хотя `warehouses`/
`clients` ей уже передаются пропсами от `SalePage` — то есть паттерн
"передать уже загруженное как пропс" в проекте уже есть и работает, просто
применён не везде.

**Фикс без внешней библиотеки (минимальный):** поднять справочники
(products/warehouses/units/categories/employees), которые не меняются в
рамках одной страницы, на уровень `AppLayout` или отдельный React Context
(`CatalogContext`), с загрузкой один раз при входе в приложение и явной
`refresh()` после мутаций (создание товара, склада и т.п.). Все текущие
`useEffect(() => { listX().then(setX) }, [])` в дочерних страницах заменяются
на `useContext`.

**Фикс с react-query:** тот же результат "из коробки" — один и тот же
`queryKey` (`['products']`, `['warehouses']`) дедуплицирует параллельные
запросы и переиспользует кеш между страницами без Context вручную.

### 3. `listAllProducts()` тянет до 1000 товаров без пагинации на каждый чих

`entities/product/api.ts:102-105` — helper специально существует "для форм
выбора товара" (продажа/заказ/приёмка) и всегда шлёт `limit=1000` без
кеша. Для магазина с несколькими сотнями SKU это не критично по объёму
данных, но при том, что вызывается на **каждое открытие** формы продажи/заказа/
приёмки, это самый тяжёлый из дублирующихся запросов (по объёму ответа,
не по количеству).

**Фикс:** тот же общий кеш из находки 2 закрывает и это — товар грузится
одним запросом на сессию, а не на каждое открытие формы.

## Не находка (для контраста — так уже правильно сделано)

`ShopContext.tsx` — название магазина (`getShop()`) грузится **один раз** на
уровне `ShopProvider`, оборачивающего всё приложение, а не на каждой странице.
Это ровно тот паттерн, который надо применить к находке 2 — валидный прецедент
уже есть в кодовой базе, не нужно ничего изобретать с нуля.

## Что НЕ дубль (проверено, чтобы не гнаться за фантомом)

При живом прогоне через Playwright каждый запрос в логе Network видно **дважды
подряд** — это `<StrictMode>` (`main.tsx:1,7`), который в dev-режиме React
намеренно монтирует компоненты дважды для отлова side-effect багов. В проде
(`npm run build`) этого удвоения нет. Если пользователь видит дубли в Network
именно в dev-режиме (`npm run dev`) — часть из них может быть этим, не багом.
Находки 1-3 выше — это дубли **сверх** StrictMode-удвоения (видны как
отдельные, разные по контексту запросы, а не два идентичных подряд к одному
и тому же компоненту), поэтому они актуальны и в проде тоже.

## План действий (порядок по эффекту/затратам)

1. **`NotificationBell`** (находка 1) — самое дешёвое и самое вредное (вечный
   фоновый дубль, а не разовая загрузка). Поднять поллинг на уровень
   `AppLayout`.
2. Определиться: свой `CatalogContext` или react-query — до начала работы
   над находкой 2, чтобы не переписывать дважды.
3. Мигрировать справочники (products/warehouses/units/categories/employees)
   на выбранный слой кеша, по одной странице за раз, начиная с самых частых
   переходов (Продажа ↔ Заказы ↔ Задачи — три вкладки, между которыми
   пользователь переключается чаще всего за смену).
4. Проверить `LastSaleCard`/аналогичные "детальные карточки, открывающиеся
   сразу после формы" на предмет получения уже загруженных данных пропсами
   вместо повторной загрузки (тот же паттерн, что уже есть для
   `warehouses`/`clients` в этом же компоненте).
