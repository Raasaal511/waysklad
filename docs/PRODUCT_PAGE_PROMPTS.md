# Карточка товара витрины «как на wikkeo»: промпты для ИИ-ассистента

> Перед началом — свериться с `docs/UX_SIMPLICITY_RULES.md`: тест на простоту и бюджет сложности экрана.

Страница: `/store/:slug/products/:productId`
(`frontend/src/pages/storefront/StorefrontProductPage.tsx`)

Цель — сделать карточку товара по компоновке wikkeo (скриншоты владельца
от 17.09.2026): галерея слева, список вариантов со степперами в центре,
правая колонка с «Итого», магазином и FAQ, блоки «Фото покупателей»,
«О товаре», «Гарантии», отзывы с тегами и гистограммой, похожие товары.
**Компоновку берём с wikkeo. Цвета, шрифты и стиль остаются ВайСклада.**

---

## Как пользоваться

Всего 13 промптов: 4 для бэкенда (B1–B4) и 9 для фронтенда (F0–F8).

1. **Сначала бэкенд, B1 → B4.** Фронту нужны поля, которых сейчас в API нет.
   Каждый бэкенд-промпт заканчивается записью в `frontend/api_docs/`. Так
   фронт-сессия получит готовый контракт.
2. **Потом фронтенд.** Первым вставьте **F0** (общий контекст), затем
   F1 → F8 по одному.
3. Следующий промпт давайте только после проверки предыдущего: в конце
   каждого есть блок «Проверка».
4. Бэкенд и фронтенд лучше вести в разных сессиях ассистента.

### Найденные проблемы в текущем коде

- **Баг цены варианта.** Бэкенд отдаёт `variants[].price`, а фронт всегда
  показывает `retail_price`.
- **Баг отзывов.** `reviews.storefront_request_id` уникален, поэтому в
  заявке с тремя товарами можно оценить только один. Уникальность должна
  быть по паре `(storefront_request_id, product_id)`. Исправляется в B3.
- На фронте нет типов `average_rating`, `reviews_count`, `variants[].photo`
  и `variants[].price`. Отзывы на фронте не реализованы вообще.
- Модерации отзывов в панели владельца нет (пункт 3 в `reviews.md`).
- `in_stock` считается по товару целиком, а не по варианту: размер, которого
  нет, выглядит доступным.

# ЧАСТЬ B — БЭКЕНД

## Промпт B1 — карточка товара: варианты, наличие, гарантия, просмотры

```text
Проект ВайСклад, бэкенд: FastAPI + SQLAlchemy 2 + Alembic + Postgres 16 +
Redis. Чистая архитектура: app/domain, app/application, app/infrastructure,
app/presentation. Multi-tenant через TenantMixin и SqlAlchemyUnitOfWork(tenant_id).
Перед работой изучи:
  app/presentation/storefront/schemas.py, router.py
  app/application/storefront/get_product.py, get_catalog.py
  app/infrastructure/db/models/catalog.py, inventory.py, identity.py
  frontend/api_docs/README.md (формат журнала), storefront_extras.md
Фронтенд не трогай.

Задача: расширить публичную карточку товара
GET /api/storefront/{slug}/products/{product_id}.
Контракты не ломаем, только добавляем поля.

1. НАЗВАНИЕ ВАРИАНТА
   - ProductVariant: новое поле name: str (String(100), default "").
     Миграция Alembic.
   - Принимать и отдавать name во всех существующих API товара для
     владельца (создание, обновление, список, деталка) — там же, где size
     и color.
   - В ответе витрины у варианта: name и display_name.
     display_name = name, если name не пустой, иначе «color · size»
     (пустые части отбросить), иначе «Вариант N».

2. НАЛИЧИЕ ПО ВАРИАНТАМ
   - Сейчас in_stock считается по товару целиком. Добавь у каждого
     варианта in_stock: bool — остаток именно этого variant_id на видимых
     складах (Warehouse.show_on_storefront), логика как у in_stock товара.
   - Уровень запаса у товара и у каждого варианта:
     stock_level: "out" | "low" | "in".
     "low" — остаток > 0 и ≤ product.min_stock (если min_stock > 0), иначе ≤ 3.
   - Точный остаток: stock_qty: string | null у товара и у вариантов.
     Заполняется ТОЛЬКО если у магазина включена новая настройка
     Tenant.storefront_show_stock_qty (bool, default False, миграция).
     Иначе null. Настройку принимать и отдавать в GET/PATCH /api/auth/shop.
   - Не делай N+1: собери остатки одним запросом, сгруппировав по
     (product_id, variant_id).
   - Каталог GET /api/storefront/{slug} не меняй, кроме того, что
     in_stock_only и variant_size/variant_color должны учитывать наличие
     именно подходящего варианта. Если это сложно — опиши в журнале как
     известное ограничение и не делай.

3. КАТЕГОРИЯ И ЕДИНИЦА
   - product.category: { id, name, parent: { id, name } | null } | null
   - product.unit_code: string, product.unit_label: string («шт», «кг», «л»,
     «м», «уп»). Возьми существующий справочник единиц, если он есть
     (ищи по unit_code), иначе заведи маппинг в domain.

4. ГАРАНТИЯ
   - Product: новое поле warranty_text: Text, default "". Миграция.
   - Принимать и отдавать в API товара для владельца (как description),
     до 5000 символов.
   - На витрине: product.warranty_text (в каталоге не отдавать — список
     должен оставаться лёгким).

5. ПРОСМОТРЫ
   - POST /api/storefront/{slug}/products/{product_id}/view → 204.
     Без авторизации. Дедупликация: Redis-ключ по (tenant, product, ip)
     на 30 минут, повторный просмотр не считается. Rate limit 120/минуту.
     Несуществующий или скрытый товар — 404, как у карточки.
   - Хранение: новая таблица product_view_daily (tenant_id, product_id, day,
     count) с upsert (INSERT … ON CONFLICT DO UPDATE count = count + 1).
     Сырые события не храним.
   - В ответе карточки: product.views_90d: int — сумма за последние 90 дней.
   - Кэш GetStorefrontProductUseCase (to_json/from_json) должен пережить
     старые записи без новых полей: значения по умолчанию при чтении.
     Просмотры не должны инвалидировать кэш карточки. Отставание до TTL
     допустимо.

6. ТЕСТЫ (pytest, по образцу существующих тестов storefront):
   - display_name во всех трёх случаях
   - вариант без остатка → in_stock false, при этом товар в целом in_stock true
   - stock_qty = null при выключенной настройке и число при включённой
   - stock_qty и остаток скрытого склада не видны
   - повторный view с того же IP не увеличивает счётчик
   - views_90d не учитывает дни старше 90
   - изоляция tenant: чужой product_id → 404

7. ДОКУМЕНТАЦИЯ: новая запись сверху в frontend/api_docs/README.md и файл
   frontend/api_docs/product_page_v2.md с полным TypeScript-описанием
   нового ответа карточки и разделом «Что нужно сделать на фронте».

В конце: список изменённых файлов, имена миграций, вывод pytest.
```

## Промпт B2 — публичный профиль магазина: лого, рейтинг, контакты, FAQ, минимальный заказ

```text
Проект ВайСклад, бэкенд (контекст и правила — как в предыдущей задаче B1:
чистая архитектура, миграции Alembic, тесты, запись в frontend/api_docs).
Фронтенд не трогай.

Задача: данные для правой колонки карточки товара — карточка магазина,
FAQ, контакты, минимальная сумма заказа.

1. НОВЫЕ ПОЛЯ Tenant (миграция, все необязательные):
   - storefront_logo: str (путь к файлу, default "")
   - storefront_description: str (до 500 символов)
   - contact_phone: str, contact_whatsapp: str, contact_telegram: str
     (telegram — username без @, валидируй формат)
   - storefront_min_order_total: Decimal | None
   - policy_refund_money, policy_payment, policy_delivery, policy_returns:
     Text (до 5000 символов каждое)
   Все поля принимать и отдавать в GET/PATCH /api/auth/shop, права —
   как у текущего PATCH.
   Логотип: POST /api/auth/shop/logo (multipart file, те же ограничения
   и тот же сервис хранения, что у фото товара), DELETE /api/auth/shop/logo.

2. ПУБЛИЧНЫЙ ПРОФИЛЬ: GET /api/storefront/{slug}/profile. Без авторизации,
   кэш 60 с, rate limit как у каталога. 404 — в тех же случаях, что
   у каталога.
   {
     name, slug, logo, description,
     on_platform_since: "2024-09-01",        // Tenant.created_at, дата
     rating: { average_rating: number, reviews_count: number },
        // по всем видимым отзывам всех товаров магазина
     products_count: number,                 // show_on_storefront и is_active
     orders_count: number,                   // принятые заявки витрины + продажи
     orders_count_label: string,             // "2000+", "150+", "12" — округление вниз
                                             // до 10/50/100/500/1000 для чисел ≥ 10
     min_order_total: string | null,
     contacts: { phone, whatsapp, telegram },  // пустые строки допустимы
     addresses: { name, address }[],           // видимые склады
     policies: { refund_money, payment, delivery, returns }
        // пустое поле → null, чтобы фронт не показывал пустой пункт
   }
   Подумай, стоит ли показывать orders_count, если продаж меньше 5. Предложи

- вариант !in_stock → строка приглушена, степпер скрыт, текст «Нет в наличии».
- выбранная строка (qty > 0) → рамка 1px var(--accent).

Над списком: если вариантов больше 6 — поиск-фильтр по названию и

видимую область. Первый «+» по нему — как обычно.

Проверка: товар без вариантов, с 3 вариантами, с 20 вариантами; вариант
без остатка; stock_qty ограничивает «+»; min/step работают.
```

## Что сознательно НЕ переносим с wikkeo

- **Ценовая вилка «от 5 000 ₽ / от 20 000 ₽» и скидка от суммы с
  прогрессом 0/5к/20к/50к.** Это оптовое ценообразование. Для него
  понадобятся правила скидок, пересчёт в заявке, заказе и долге. Вместо
  этого прогресс-бар показывает путь до минимальной суммы заказа. Если
  решите делать оптовые цены, нужен отдельный бэкенд-промпт.
- **Подписчики магазина.** Функции подписки нет, вместо подписчиков
  показываем число товаров.
- **«Укажите город — рассчитаем доставку» и «Безопасная сделка».** Расчёта
  доставки и приёма денег нет: ВайСклад денег не принимает. Вместо этого
  показываем адрес магазина и оплату при получении.
- **Видео** в галерее и в отзывах. Пока только фото.
- Синяя палитра и красные бейджи «-58%», «ЛИКВИДАЦИЯ». Используем
  цвета ВайСклада.
