# Продажи — что доделать, а что осознанно не делать

**Дата:** 2026-08-10 (обновлено: пункты 1.1–1.3 реализованы; квитанция
переделана с PNG на PDF-документ по образцу пользователя — см. раздел 3)
**Контекст:** аудит экрана продажи (`frontend/src/pages/sales/SalePage.tsx`) на
соответствие README §5.1, по итогам сессии 20. Документ — план идей без кода,
разбит на «делать» (закрывает реальную боль розницы малого/среднего бизнеса
ЧР) и «не делать» (создаёт видимость фичи, но на деле — лишний интерфейс,
который никто не будет трогать после первой недели).

**Статус реализации:** все три пункта раздела 1 сделаны — сдача с наличных
(переиспользован уже существовавший, но не подключённый backend `Sale.
change_for`/`cash_received`), квитанция-документ (`GET /sales/{id}/receipt.pdf`,
reportlab + DejaVu — табличный PDF с границами, шапкой, номером и датой,
кнопка «Поделиться чеком» с `navigator.share`), индикатор «мало на складе» в
корзине продажи и в общей таблице остатков. 116 тестов backend проходят,
`tsc`/`build` фронтенда чисты, PDF-эндпоинт проверен живым интеграционным
тестом и вручную в Docker-контейнере (кириллица через DejaVu подтверждена
визуально). Первая версия квитанции была PNG-картинкой построчным текстом —
по фидбэку заменена на настоящий табличный PDF-документ (см. раздел 3).

Критерий отбора везде один: **облегчает ли это работу продавца за прилавком**
(экран продажи используется по 50–200 раз в день, каждая лишняя секунда или
лишнее поле — реальная стоимость), а не «что умеет 1С/МойСклад».

## 1. Делать — закрывает конкретную дыру из README §5.1

### 1.1. ✅ Сдача с наличных (высокий приоритет) — сделано

README прямо требует: «сумму чека, скидку **и сдачу** программа считает
автоматически». Сейчас при `payment === 'cash'` нет поля «получено» — продавец
считает сдачу в уме или на калькуляторе, хотя вся идея фичи — снять с него
арифметику.

**Что именно сделать:**
- Поле «Получено» появляется только при `payment === 'cash'` (по аналогии с
  тем, как «Долг до» появляется только при `credit`) — не захламляет форму в
  остальных случаях.
- Сдача считается и показывается крупно рядом с итогом: `Сдача: 340 ₽`.
- Не блокировать продажу, если «получено» меньше суммы — наличкой в долг
  тоже расплачиваются, это не ошибка ввода, программе не стоит спорить с
  продавцом.
- Опционально — кнопки быстрого набора (500/1000/5000 ₽), но это уже
  косметика поверх, не обязательно в первой итерации.

**Почему не мусор:** это последняя операция каждой продажи наличными
(большинство продаж в рознице ЧР), заметная экономия времени 50+ раз в день.

**Как реализовано:** backend уже имел готовую доменную операцию
`Sale.change_for()` и принимал `cash_received` в `CreateSaleCommand`/
`CreateSaleUseCase`, просто это не было подключено ни к одному клиенту —
фронтенд теперь передаёт `cash_received` при оплате наличными (только если
суммы хватает, иначе не отправляет поле вовсе, чтобы не словить
`DomainError` от `change_for` — недостача не блокирует продажу, как и
планировалось) и показывает сдачу live при вводе (клиентский предпросмотр)
и итоговую сдачу с сервера на экране «Продажа проведена».

### 1.3. ✅ Индикатор «мало на складе» прямо в корзине — сделано

`min_stock` уже вводится в карточке товара, но нигде не подсвечивается.
Продавец узнаёт, что товар кончается, только когда остаток стал 0.

**Что сделать:** если остаток товара ≤ `min_stock` — маленькая пометка на
плитке товара («осталось 2») жёлтым/акцентным, не блокирующая продажу.

**Почему не мусор:** README прямо называет это частью MVP («минимальный
остаток с предупреждением «заканчивается»») — сейчас поле существует, но
предупреждения физически нет нигде в UI, это не новая фича, а дозакрытие уже
объявленной.

**Как реализовано:** плитка товара в корзине продажи подсвечивает остаток
акцентным жёлтым (`--warning`), если `qty ≤ min_stock`; таблица «Все товары
по складам» на `StockPage` получила такой же значок «заканчивается» рядом с
количеством.

## 2. Не делать (пока) — раздувает интерфейс без реальной пользы на этом этапе

Явно решил не включать в ближайшие итерации, чтобы не превращать «быструю
кассу» в перегруженный ввод данных:

- **Скидка на отдельную строку корзины (не на весь чек).** Красиво звучит, но
  почти никогда не нужно в рознице — скидки дают на чек целиком («скинь
  сотку») или на конкретный товар меняют цену прямо в поле цены (это уже
  можно). Отдельный UI на каждую строку — второй ряд кнопок в каждой строке
  корзины, для фичи, которой воспользуются раз в месяц.
- **Множественная оплата одного чека (часть наличными, часть переводом).**
  Реальный кейс существует («тысячу наличкой, остальное на карту»), но
  сейчас `payment_method` — это одна пометка на весь чек, и переделка на
  сплит-оплату — это уже не косметика, а модель данных (`Sale.payment_method`
  → список из нескольких сумм/способов). Крупная задача ради редкого кейса на
  этом этапе; если пилот покажет частоту — тогда отдельная сессия.
- **Штрих-код на каждой строке корзины для быстрого удаления сканом.** Кнопка
  «X» на плитке товара уже решает эту задачу без камеры.
- **Программа лояльности/бонусы/кешбэк.** Прямо вне README §5.1 и §5.2 —
  не наш продукт, это уже про маркетинг, а не про учёт.
- **Настраиваемые шаблоны чека (свой логотип, цвета, доп. поля).** Один
  адекватный формат текста квитанции достаточен для 100% нашей аудитории —
  кастомизация нужна бизнесу с брендом и маркетинговым отделом, не нашему
  клиенту.
- **Печать чека на физическом принтере/фискальный регистратор.** Прямо
  противоречит README §5.3 («мы не касса и не заменяем её») — если
  добавить, автоматически попадаем под требования к фискализации ККТ,
  которых явно решили избежать.

## 3. Проблема чеков — отдельный, более серьёзный разбор

**✅ Реализовано (финальная версия — PDF, не PNG).** Первая итерация
(2026-08-10, утро) была PNG-картинкой с построчным текстом без таблицы — по
прямому фидбэку («нет понятного разделения по линиям, нечитаемо, нужен
уникальный номер, нужно как документ») переделана в тот же день на
табличный PDF: `GET /sales/{id}/receipt.pdf`
(`app/infrastructure/receipt_pdf.py`, reportlab + DejaVu из
`fonts-dejavu-core`, формат A5, зелёная шапка таблицы, чередующиеся строки,
границы у каждой ячейки — рендерится по запросу и не хранится). Номер
документа — `№{sale.id}` (существующий числовой id продажи, уникален в
рамках магазина, без отдельной схемы нумерации). Из состава документа
осознанно убрано то, что вне нашей ответственности: НДС (мы не онлайн-касса
и не фискализируем продажи — README §5.3), гарантия и серийный номер
(это удобно для конкретно электроники/техники в референсе пользователя, но
не универсально для нашей аудитории — магазин одежды или кондитерская этим
полям не найдут применения). Кнопка «Поделиться чеком» на фронтенде вызывает
`navigator.share` с PDF-файлом, при недоступности — скачивает файл напрямую;
кнопка «В WhatsApp текстом» (старый `render_receipt_text`) оставлена как
fallback, ничего не выброшено.

### Что было раньше
`GET /sales/{id}/receipt` возвращает **текст** + готовую ссылку `wa.me` с
этим текстом (`backend/app/domain/sales/receipt.py`). Кнопка «В WhatsApp»
открывает чат с предзаполненным сообщением. Работает, но есть три реальные
проблемы для малого/среднего бизнеса:

1. **Это не то, что люди привыкли получать как «чек».** Голый текст в
   WhatsApp выглядит как случайное сообщение, не как подтверждение покупки —
   не сохраняется отдельно, теряется в переписке через неделю, не вызывает
   доверия у клиента («это точно от магазина?»).
2. **Клиент не может переслать/показать чек без контекста магазина.**
   Текстовое сообщение без опознавательных знаков (лого, форматирования) при
   пересылке третьему лицу (например, при возврате) не читается как
   официальный документ покупки.
3. **README требует именно «картинкой/PDF»** — то есть это не пожелание, а
   уже принятое решение, которое сейчас не выполнено буквально.

### Правильный совет для малого/среднего бизнеса (не «сделать красивую PDF ради PDF»)

Ключевая мысль: **малому бизнесу не нужен фискальный чек — он и так вне
закона о ККТ при таком масштабе учёта** (см. README §5.3 — это осознанный и
верный отказ). Но малому бизнесу **нужно** нечто, что решает две настоящие
задачи:

- **Клиенту** — подтверждение «что купил, за сколько, когда» на случай
  возврата/спора/памяти.
- **Владельцу** — ощущение профессионализма перед клиентом (магазин с
  нормальной квитанцией выглядит солиднее тетради и голого текста).

Из этого — конкретная рекомендация, без переусложнения (пересмотрено
2026-08-10 после фидбэка — изначально предполагали PNG, но образец от
пользователя показал, что нужна именно табличная структура документа с
границами, которую PNG-текст построчно дать не может так же аккуратно, как
нормальная таблица PDF-библиотеки):

1. **Генерировать настоящий документ — PDF с таблицей**, не картинку текста.
   Табличная библиотека (`reportlab.platypus.Table`) даёт ровные границы,
   выравнивание колонок, чередующиеся строки и перенос длинных названий
   товара — то, что вручную через Pillow пришлось бы либо не делать вовсе
   (первая версия так и выглядела — плохо), либо реализовывать заново
   вручную, отрисовывая линии координатами. PDF на телефоне открывается через
   системный просмотрщик — на один шаг менее прямой, чем картинка в чате, но
   выглядит как настоящий документ, а не фото.
2. **Рендерить на сервере одной функцией** (`reportlab`, уже в экосистеме
   бэкенда): название магазина, номер документа и дата, покупатель (если
   есть), таблица позиций (№/наименование/кол-во/цена/сумма), скидка, итог,
   способ оплаты, «Спасибо за покупку». Никакого визуального редактора
   шаблонов не нужно — один аккуратный фиксированный макет закрывает 100%
   случаев.
3. **Не хранить документ постоянно** — рендерить по запросу (`GET
   /sales/{id}/receipt.pdf`) и отдавать сразу. Не превращать это в новую
   сущность с собственным жизненным циклом.
4. **WhatsApp-ссылка не может нести файл** — технически `wa.me` с текстом не
   поддерживает вложение файла напрямую по ссылке (ограничение самого
   WhatsApp, не наше), поэтому реалистичный путь: кнопка скачивает
   PDF-документ, продавец одним движением делится им через системное
   «Поделиться» на телефоне (`navigator.share` в браузере, там где
   поддерживается) — привычнее для продавца, чем открытие чужого чата с
   готовым текстом.
5. **Текстовый вариант не выбрасывать** — оставить как fallback там, где
   `navigator.share`/файл недоступны (десктоп без поддержки Web Share API) —
   уже написанный `render_receipt_text` не становится мёртвым кодом, а
   становится запасным путём.

**Чего делать не стоит:** не пытаться сделать «настоящий фискальный чек» с
QR-кодом ОФД, ИНН продавца и прочими обязательными реквизитами ККТ — это
прямой путь к юридическим обязательствам, которые README §5.3 сознательно
отвергает. Товарная квитанция картинкой — это ровно тот уровень
«профессионально выглядит, но без бюрократии», который нужен нашей
аудитории.
