# Мастер-план ВайСклад

Сводит в одно место: `README.md`, `docs/ROADMAP.md`, `docs/NEXT_PLAN.md`,
`docs/STOREFRONT_PLAN.md`, `docs/NEXT_FEATURES_FROM_COMPETITORS.md`,
`frontend/api_docs/PRIORITY.md`, `frontend/api_docs/README.md`,
`docs/PRODUCT_PAGE_PROMPTS.md`, `docs/MARKETPLACE_HOME_PROMPTS.md`,
`docs/ILLUSTRATIONS_PROMPTS.md`, `docs/PUBLIC_PAGES_FINISH_PROMPTS.md`.
Проверено против кода 2026-09-19 (см. сноски "код:").

Ни один существующий документ не переписан — этот план не отменяет их,
а расставляет приоритет и режет лишнее. Правило продукта: конкурент —
не Wildberries, а тетрадь. Целевой пользователь — владелец и продавец
магазина в райцентре, которые сейчас считают в тетради, и покупатель,
который открывает витрину с телефона по ссылке из WhatsApp.

## 4. Волны

### Волна 0 — нельзя запускать пилот без этого
**Цель одной фразой:** не потерять чужие данные и не нарушить закон, прежде чем в системе появятся реальные магазины.

id: P-01, P-03, P-04, P-06, P-10, P-11

Критерий завершения: CORS настроен явным whitelist, `secret_key`/пароль БД падают приложение при отсутствии `.env` (не тихо работают с дефолтом), бэкап уходит на второе хранилище и проверен восстановлением хотя бы раз, чекбокс согласия стоит на регистрации, `docker-compose.prod.yml` роняет и перезапускает `backend` при неработающем `/api/health`.

Объём: ~3-4 дня (все задачи S, кроме P-05, которая уже частично закрыта и не входит явно в волну 0 — индексы добавлять по факту профилирования в волне 1-2).

### Волна 1 — что увидит первый живой магазин и его покупатели
**Цель одной фразой:** пилотный магазин может полноценно торговать и его покупатели могут оформить заказ с телефона без сбоев.

id: P-41 (фронт, критично — иначе витрина не работает вообще), P-43 (фронт), P-44/P-45 (фронт, тривиально), P-58 упрощённо (только PWA-иконки, которые сейчас 404 — не весь объём I1), P-64 упрощённо (только реальные баги из таблицы дефектов 1-9, не весь P0-P7)

Критерий завершения: покупатель проходит путь «открыл витрину → положил в корзину → вошёл через Telegram → оформил заявку» без ошибок на реальном телефоне; продавец видит корректную сдачу в отчёте; на экранах нет «1 товаров», «5.000 шт», обрезанного текста, пустого «Итого: 0 ₽» без подсказки.

Объём: ~4-6 дней.

### Волна 2 — после первых отзывов пилота
**Цель одной фразой:** закрыть то, что реально попросят первые 5-10 магазинов, а не то, что кажется важным заранее.

id: P-07, P-08, P-09 (алерт поверх уже готового лога), P-27, P-28, P-29, P-30 (WhatsApp-паттерн для клиентов, единая сессия), P-12 (проверить, использует ли фронт `total` из уже готовой пагинации), P-50 (фронт «Упущенные продажи»), упрощённая версия P-31/P-32 (заявка поставщику)

Критерий завершения: определяется обратной связью пилота, не планируется заранее — держать список готовым, брать по факту вопросов.

Объём: не оценивается заранее — зависит от того, что реально попросят.

### Волна 3 — рост (маркетплейс, площадка, десятки магазинов)
**Цель одной фразой:** платформа работает для покупателя, который сравнивает несколько магазинов, а не для одного.

id: P-57 (главная маркетплейса, полный объём M-F0-M-F6), P-64 (полный объём P0-P7), P-56 (полный объём wikkeo-уровня), P-53 (теги/голоса отзывов v2), P-33/P-34/P-35 (прогноз и ИИ-советы), P-36 (чат-бот поддержки), P-37/P-38/P-39/P-40 (интеграции и открытый API), P-65 (общая корзина)

Критерий завершения: определяется по факту — когда на платформе одновременно активны десятки магазинов и покупатель реально сравнивает их между собой (не когда код написан, а когда есть кому его использовать).

Объём: не оценивается — сама постановка «когда 50+ магазинов» откладывает точный расчёт.

## 6. Один следующий шаг

**P-06 — добавить чекбокс согласия на обработку персональных данных при регистрации магазина (152-ФЗ).**

Почему именно эта задача, а не более крупная или более «интересная»:
- Это единственная задача волны 0, которая одновременно (а) юридический риск с первого реального клиента, (б) объём S (меньше 0.5 дня — один чекбокс, один текст политики, одно поле в форме регистрации), (в) не зависит ни от какой другой задачи.
- CORS (P-01) и дефолты секретов (P-03) технически важнее по риску безопасности, но они invisible для пользователя и не имеют юридической природы «нельзя запускать пилот, пока не сделано» — их можно закрыть в тот же день следующим шагом.
- P-06 — единственная задача, где промедление имеет накопительный эффект: каждый день без согласия — это потенциально каждая новая регистрация без него, и это нельзя исправить задним числом для уже собранных данных.
- Она также самая маленькая по объёму во всей волне 0 — хороший первый шаг, который сразу закрывается полностью за один присест, а не растягивается.

## Вопросы (не больше 5, только те, что нужны для расстановки волн)

1. **Пагинация `/sales` — использует ли фронт `total` из ответа?**
   Backend уже отдаёт `limit`/`offset`, но не проверено, обрезает ли фронт список на 50 записей молча или подгружает следующие страницы.
   Варианты: (а) фронт уже всё умеет — тогда P-12 полностью закрыт, вычеркнуть из волны 2; (б) фронт показывает только первые 50 — тогда это мелкая фронт-задача, поднять в волну 1.
   Зависит: P-12.

2. **Что считать «пилотом» для целей волны 2 — первый живой магазин или все 5-10?**
   Документ ROADMAP говорит «после первой волны обратной связи», README — про 5-10 магазинов сразу. Если ждать всех 10 — волна 2 стартует поздно.
   Варианты: (а) начинать волну 2 после первого живого магазина с реальными продажами за неделю; (б) ждать 3+ магазинов для более уверенных сигналов.
   Зависит: весь состав и порядок волны 2.

3. **Офлайн-продажа в долг (P-15) — считать закрытой или требует ручной проверки?**
   Grep находит `debt_due_date` в нескольких фронт-файлах, похоже на реализацию, но не проверено вручную (без сети, реальный сценарий рынка).
   Варианты: (а) считать закрытой, снять с реестра; (б) провести один ручной прогон сценария «выключить сеть → продать в долг → включить сеть → проверить синк» перед тем как считать готовой.
   Зависит: P-15, косвенно приоритет волны 0/1 (это ключевой офлайн-сценарий README).

4. **Нужна ли волна 3 (wikkeo-уровень) вообще, если пилот останется на уровне «несколько соседних магазинов», а не «платформа»?**
   Весь объём P-57/P-64 предполагает конкуренцию многих магазинов за внимание одного покупателя. Если бизнес-модель пилота — «внедрение по одному магазину, каждый получает свою ссылку на витрину», а не «общая платформа для города» — часть этой работы может не понадобиться вовсе, а не просто отложиться.
   Варианты: (а) маркетплейс — стратегическая ставка на будущее, работа была не зря, ждём масштаба; (б) переосмыслить necessity уже написанного кода M-B1/M-B2/F1-F8 под более скромный сценарий.
   Зависит: весь состав волны 3, отчасти P-56/P-57 из волны выше.

5. **Кто закрывает волну 0, если задание жёстко разделяет backend/frontend роли (`feedback_backend_only_scope` в памяти)?**
   P-01, P-03, P-04, P-06, P-10, P-11 — все backend/инфраструктура, это укладывается в текущий backend-only режим работы. Но если волна 0 требует и фронт (например, чекбокс P-06 — это форма на фронте), нужно уточнить, кто это делает.
   Варианты: (а) backend готовит API-поле и текст политики, фронт-разработчик (по памяти — «свой разработчик» с 2026-09-02) добавляет чекбокс отдельно; (б) в этой сессии/сессиях делать и то и другое, раз это критично для волны 0.
   Зависит: P-06 исполнение, весь темп волны 0.
