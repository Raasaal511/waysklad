# Сессия 24 — Витрина: чат по заявке (шаг 3 плана)

**Дата:** 2026-09-03
**Этап плана:** README §5.2 (публичная витрина), последний из трёх шагов плана

## Контекст

Продолжение витрины сразу после заявки (сессия 23) — пользователь явно
попросил три работы разом: избранное (чистый фронтенд, не требует backend),
заявки/заказы (сделано в сессии 23) и чат. Перед реализацией уточнены три
развилки: к чему привязан чат (`StorefrontRequest`, не `Order` — покупатель
должен мочь писать сразу после отправки заявки, ещё до принятия владельцем),
как покупатель без аккаунта получает доступ (токен в ответе на создание
заявки — переиспользует решение из открытых вопросов исходного плана), кто
из сотрудников может отвечать (любой с `ORDERS_VIEW`/`ORDERS_MANAGE`, без
нового права).

## Что сделано

Новая сущность `StorefrontMessage` (`app/domain/storefront/entities.py`) —
`author: customer|staff` + текст, живёт вместе с заявкой (не переносится
при принятии в `Order`).

**Токен доступа** — `StorefrontRequest.access_token` (43-символьная строка,
`secrets.token_urlsafe(32)`), генерируется при создании заявки, уникален
глобально (не в пределах tenant — сам факт владения токеном доказывает
право на заявку). Возвращается ТОЛЬКО в ответе на создание
(`StorefrontRequestCreatedResponse`) — owner-side ответы (`StorefrontRequestResponse`)
токен не содержат.

**Публичный доступ по токену без знания tenant** — потребовало добавить
`tenant_id` полем в domain-entity `StorefrontRequest` (аналог существующего
`User.tenant_id` — тот же паттерн: единственный способ анонимного клиента
узнать свой tenant, чтобы открыть tenant-scoped UoW). Заполняется только
`IStorefrontRequestRepository.get_by_token()`, нигде больше.

**REST:**
- `GET/POST /api/storefront/requests/chat?token=` — покупатель, без авторизации.
- `GET/POST /api/storefront/requests/{id}/chat` — сотрудник, авторизация.

**WebSocket:** `WS /api/storefront/requests/chat/ws?token=`. Потребовало
расширить `Broadcaster`/`ConnectionRegistry` (`app/infrastructure/ws_broadcast.py`)
— раньше адресация была жёстко по `user_id: int` (только для уведомлений
сотрудников), теперь по произвольному строковому каналу (`user:<id>` для
уведомлений, `storefront_request:<id>` для чата). Один Redis pub/sub
обслуживает оба сценария, обратная совместимость с уведомлениями сохранена
(`notify_user`/`notifications/router.py` переведены на новый `user_channel()`).

Новое сообщение от покупателя создаёт `NotificationKind.STOREFRONT_MESSAGE`
владельцу/менеджерам через уже существующий `notify_user` — отдельный
алертинг не заводили.

## Итог по плану витрины

Все три шага `docs/STOREFRONT_PLAN.md` реализованы на backend: каталог
(+ фильтр по складу), заявка, чат. Фронтенд для витрины целиком не начат
(backend-only режим всех трёх сессий) — полные контракты в
`frontend/api_docs/README.md`.
