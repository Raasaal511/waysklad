# Сессия 06 — Slug для магазина (публичный URL витрины)

**Дата:** 2026-08-04
**Этап плана:** подготовка к публичной витрине (README п. 5.2), попутно к обсуждению
безопасности идентификаторов (UUID vs int PK)

## Контекст решения
Обсуждали переход на UUID для PK ради безопасности — отклонили: реальная граница
изоляции в проекте уже tenant_id-фильтр на каждом запросе (сессия 01), а не
непредсказуемость числового id. Отдельно всплыла идея slug для будущей публичной
витрины магазина (`waysklad.ru/aina-dress` вместо `.../shop/48291`) — это про
брендинг/читаемость, не про security, и её решили сделать сразу, пока контекст свежий.

## Что сделано

- **requirements.txt**: `python-slugify>=8` (транслитерация кириллицы: «Айна» → `aina`).
- **`domain/common/slug.py`** — `generate_slug(text) -> str`: транслитерация +
  приведение к `[a-z0-9-]`, fallback `"shop"` на нечитаемый ввод (например, только
  спецсимволы).
- **`domain/identity/entities.py`**: `Tenant.slug: str | None = None`. Optional — по
  тому же паттерну, что `Product.barcode`/`sku` (NULL допускает несколько строк без
  конфликта UNIQUE в Postgres; реальные регистрации всегда получают значение).
- **`TenantModel.slug`**: `String(120)`, `unique=True, index=True`. Миграция
  `2026-08-04_add_tenant_slug.py`, применена на dev-БД.
- **`ITenantRepository.get_by_slug`** + реализация — прямой lookup без tenant-фильтра
  (Tenant — сам корень мультиарендности, TenantMixin к нему не применяется).
- **`RegisterShopUseCase`**: генерирует slug из `shop_name`, разрешает коллизии
  циклом `aina → aina-2 → aina-3…` до первого свободного (проверка через
  `get_by_slug` в той же транзакции). Возвращает `RegisterShopResult(owner, shop_slug)`
  вместо голого `User` — сигнатура use case изменилась.
- **API**: `TokenResponse.shop_slug` — заполнен только в ответе `/api/auth/register`
  (в `/login` — `None`, чтобы не гонять лишний запрос за тенантом при каждом входе).
