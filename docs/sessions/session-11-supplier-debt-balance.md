# Сессия 11 — Долг поставщику, баланс, «должны сегодня»

**Дата:** 2026-08-05
**Этап плана:** неделя 7 (README п. 8) — «Долги: долговая книга, рассрочка, балансы контрагентов»

## Контекст
Пользователь добавил в `docs/sessions/` два управляющих файла: `NEXT_STAGES_PROMPT.md`
(чек-листы по неделям 7–12 с Definition of done, статус «недели 1–6 готовы») и
`TECH_DEBT.md` (реестр отложенных мелочей). С этой сессии — работаем строго по
чек-листу очередной недели, некритичные шероховатости не чиним на месте, а
заносим в TECH_DEBT.md; фронтенд не трогаем до отдельного указания.

Долговая книга клиента (запись, частичные погашения, история, рассрочка,
привязка к продаже) была полностью реализована ещё в сессии 02. Сверка с
чек-листом недели 7 (README п. 5.1: «Баланс по каждому клиенту и поставщику
(мы должны / нам должны), сверка одной кнопкой») показала три реальных пробела:
1. «Сегодня должны вернуть» — `IDebtRepository.list_due()` был реализован в
   SQL-репозитории, но без use case и без эндпоинта — данные лежали, наверху
   ничего не было.
2. Баланс клиента — был только сырой список долгов (`GET /debts/client/{id}`),
   без агрегированной суммы.
3. Долг поставщику («мы должны») — отсутствовал полностью: `Supplier` не имел
   ни малейшего понятия о балансе, была смоделирована только дебиторская
   задолженность (клиент нам должен), но не кредиторская (мы должны
   поставщику).

Перед реализацией пункта 3 уточнил у пользователя: обобщить существующую
`Debt` на клиента/поставщика или завести отдельную параллельную сущность.
Выбрано обобщение — переиспользует весь код погашений/рассрочки/аудита для
обеих сторон без дублирования.

## Что сделано

- **domain**: `Debt.client_id`/`Debt.supplier_id` — оба `int | None`, ровно
  один должен быть заполнен (`Debt.validate()`, вызывается в местах создания:
  `IssueDebtUseCase`, `IssueSupplierDebtUseCase`, `CreateSaleUseCase`).
  `total_balance(debts) -> Money` — общий хелпер для суммы остатков,
  переиспользован в лимите долга клиента (`issue_debt.py`, `create_sale.py`)
  вместо дублирования цикла.
- **infrastructure**: миграция `2026-08-05_supplier_debt.py` — `debts.client_id`
  стал nullable, добавлена `debts.supplier_id` (FK на `suppliers`) и
  `CHECK (client_id IS NOT NULL) != (supplier_id IS NOT NULL)`; применена на
  dev-БД. `SqlAlchemySupplierRepository.get()` (раньше был только `add`/`list`) —
  нужен, чтобы дружелюбно проверять существование поставщика перед выдачей
  долга. `SqlAlchemyDebtRepository.list_by_supplier()`.
- **application**: `IssueSupplierDebtUseCase` («взяли товар под долг у
  поставщика», право `DEBTS_MANAGE` — то же, что и у клиентского долга).
- **presentation**:
  - `POST /api/debts/suppliers` — выдать долг поставщику.
  - `GET /api/debts/supplier/{id}` и обновлённый `GET /api/debts/client/{id}` —
    теперь возвращают `DebtsSummaryResponse{total_balance, debts}` вместо
    голого списка (это и есть «сверка одной кнопкой» — одно число, не нужно
    считать вручную). **Ломает форму ответа для существующих клиентов API** —
    оправдано, фронтенда ещё нет, менять сейчас дешевле, чем после.
  - `GET /api/debts/due?on=` — долги «должны сегодня» (по умолчанию — сегодня,
    можно указать дату).

## Проверено
87 тестов (было 82): `Debt.validate()` отклоняет «оба заполнены» и «оба
пустые», `total_balance()` суммирует и работает на пустом списке; выдача
долга поставщику и `list_by_supplier`; кладовщику (нет `DEBTS_MANAGE`)
недоступно; API-тест на весь новый маршрут (выдать → баланс поставщика →
долг виден в `/due` сегодня и отсутствует на «завтра»). Существующий
`test_full_trading_flow` обновлён под новую форму ответа. Дополнительно —
сквозная проверка через живой `uvicorn` с реальной применённой миграцией.
`compileall` — чисто.
