# Промпт: продолжение разработки ВайСклад до MVP

> Использовать как рабочий промпт при продолжении разработки (в чате с AI-ассистентом или как чек-лист для себя). Контекст проекта — см. `README.md` в корне репозитория.

## Роль и правила

Ты помогаешь соло-разработчику довести MVP системы **ВайСклад** до конца по плану из `README.md` (раздел 8, план на 12 недель). Действуй строго поэтапно, не перепрыгивая вперёд и не смешивая этапы без необходимости.

**Жёсткие правила:**
1. **Функциональность MVP (README §5.1) не режем.** Если что-то из обязательного ядра не помещается по срокам — сигнализируй об этом явно, не удаляй тихо.
2. **Второй очереди (README §5.2) не касаемся** до завершения MVP, если только это не блокирует пилот.
3. Всё, что найдено по ходу работы и **не является недоделанной MVP-функцией**, а именно **мелкий баг / шероховатость / технический долг** (опечатка, некрасивый край UI, неоптимальный запрос, отсутствие валидации на редком edge-case и т.п.) — **не чинить на месте**, если это не блокирует прохождение сценария. Зафиксировать в `docs/TECH_DEBT.md` по шаблону оттуда и идти дальше.
4. Если баг **блокирует** основной сценарий этапа (например, продажа не сохраняется, остаток не пересчитывается) — это не техдолг, это часть MVP, чинится сразу.
5. Правило срока из README: если неделя «поплыла» — режем функциональность второй очереди, но **не сдвигаем пилот** (неделя 12).

См. `TECH_DEBT.md` №4/№8/№11 — все три закрыты.

Ничего из этого не блокирует технический MVP и не блокирует пилот — можно делать параллельно с первыми живыми внедрениями или отложить, если продажи идут через личные визиты с реальным товаром клиента (сценарий демо из README §10.3 и так рассчитан на «покажи на моём товаре», не на выдуманные данные).

1. Скоммитить текущий незакоммиченный объём работы (см. `git status` — много несохранённых правок: generic filter, задачи, онбординг, история изменений) — иначе легко потерять.
2. Прогнать `docker-compose.prod.yml` целиком на тестовом сервере (сам `scheduler`-сервис ещё не проверялся вживую, только typecheck/импорт) — убедиться, что уведомления и сводка реально доходят в Telegram.
3. Дальше — можно сразу идти в пилот (README §10.1: «первые 10 внедрений — бесплатно», обучение на месте компенсирует отсутствие видео/лендинга).

### Неделя 8 — Заказы, роли, журнал действий

**Цель:** магазин может принимать заказы из мессенджеров и не бояться недостач от продавцов.

Задачи:
- [x] Заказ клиента: состав, предоплата, дата готовности, статусы (новый → в работе → готов → выдан)
- [x] Быстрое создание заказа
- [x] Роли: закупочные цены/прибыль скрываются на уровне сервера (`ShowPurchaseDep`, `Permission.PURCHASE_PRICES_VIEW`/`ANALYTICS_VIEW`) — продавец физически не может получить эти данные даже через прямой запрос к API, не только через UI
- [x] **Журнал действий** — реализован не как общая страница `/audit` (та версия из сессии 21 удалена целиком, включая `Permission.AUDIT_VIEW`), а как детальная история прямо в карточке каждой сущности (`HistoryDisclosure`: продажа/заказ/товар/долг/задача) — кто, когда, что изменил, с человекочитаемыми деталями (старые/новые суммы, значения). `list_by_entity` в `SqlAlchemyAuditRepository` отдаёт `user_name` через JOIN на `users`.
- [x] **Роли и склады** (внеплановая доработка, сессия 21, по запросу пользователя) — сотрудники (кроме owner) теперь привязаны к списку складов (`warehouse_assignments`, переиспользован для manager/seller/storekeeper, не только storekeeper); при единственном складе в магазине привязка проставляется автоматически без вопроса в форме. Продажи/остатки/аналитика фильтруются по складам сотрудника. Менеджер получил `Permission.ANALYTICS_VIEW` (раньше не мог смотреть аналитику вовсе — исходный баг, из-за которого доработка стартовала). См. `docs/UX_ROLES_SMALL_SHOP_ANALYSIS.md` для обоснования архитектурных решений.

**Definition of done (уточнено):** ✅ заказы, роли и журнал действий полностью соответствуют плану.
