# Сессия 10 — Возврат продажи и квитанция в WhatsApp

**Дата:** 2026-08-05
**Этап плана:** недели 5–6 (README п. 8) — «Продажи: экран продажи, возвраты, списания,
перемещения, квитанция в WhatsApp»

## Контекст
Сверка с уже сделанным показала: экран продажи (`create_sale`), списания
(`write_off`), перемещения (`transfer`) реализованы ещё в сессии 02. Оставались
два реальных пробела: возврат продажи (`application/sales/return_sale.py` был
файлом-заглушкой с сессии 02) и квитанция в WhatsApp. Схема БД для возвратов
(`sale_returns`, `sale_return_lines` с `sale_line_id` FK) и право
`Permission.SALES_RETURN` (уже выданное продавцу) существовали с сессии 01 —
их не хватало только реализовать поверх.

## Что сделано

### Возврат продажи
- **domain**: `SaleLine` получил `id` (нужен, чтобы возврат ссылался на
  конкретную строку продажи, как того требует схема БД). Новые сущности
  `SaleReturn`/`SaleReturnLine` (`domain/sales/entities.py`). `ISaleReturnRepository`
  (`add`, `list_by_sale` — нужен для проверки остатка к возврату).
- **infrastructure**: `SaleReturnMapper`, `SqlAlchemySaleReturnRepository`;
  `SqlAlchemySaleRepository.add()` теперь простреливает `id` каждой строки
  продажи после flush (как уже делалось для вариантов товара).
- **application**: `ReturnSaleUseCase` — право `SALES_RETURN`; для каждой
  возвращаемой строки проверяет остаток к возврату (продано минус уже
  возвращено по всем прошлым возвратам той же строки — частичные возвраты
  накапливаются корректно); возвращает товар на склад (`uow.stock.change` с
  положительной дельтой); если продажа была в долг — уменьшает соответствующий
  `Debt` через существующий `Debt.repay()` (возврат физически не двигает
  деньги, но по сути уменьшает то, что клиент должен, — тот же инвариант, что
  и у оплаты долга); одна audit-запись `sale.return`.
- **presentation**: `POST /api/sales/{id}/returns`.

### Квитанция в WhatsApp
README (п. 5.1) просит «чек-квитанцию картинкой/PDF» для отправки в WhatsApp
(не фискальный чек). Честно оценив среду: надёжно встроить кириллический TTF-шрифт
для PDF/изображения здесь не из чего — ни `fpdf2`, ни `reportlab` не несут
такой шрифт по умолчанию (только латиница), а скачать и провалидировать
шрифт в этой сессии не вышло бы визуально проверить. Вместо рискованной
имитации PDF реализован рабочий и проверяемый вариант:
- **domain**: `domain/sales/receipt.py` — `render_receipt_text()` (магазин,
  номер и дата чека, клиент, позиции, скидка, итого, способ оплаты) и
  `build_whatsapp_link(phone, text)` — готовая ссылка `wa.me/<номер>?text=...`,
  открывающая чат с клиентом с уже подставленным текстом чека одним нажатием
  (без шага «скачать/прикрепить файл»).
- **presentation**: `GET /api/sales/{id}/receipt` — читает продажу, магазин
  (`ITenantRepository.get()` — новый метод, раньше был только `get_by_slug`),
  товары и клиента напрямую через `uow` (как уже принято для остальных
  read-эндпоинтов вроде `get_product`), отдаёт `{text, whatsapp_link}`.
  `whatsapp_link` — `None`, если у продажи нет клиента с телефоном/WhatsApp
  (розничная продажа без записи покупателя).

## Проверено
82 теста (было 77 после возвратов, из них 5 новых на возвраты и API-тест;
плюс 5 на квитанцию — 4 доменных + 1 API): полный/частичный возврат,
уменьшение долга по возврату, перевозврат (запрос больше доступного к
возврату) отклоняется, кладовщику возврат недоступен (403); текст квитанции
содержит магазин/товары/итог/способ оплаты, wa.me-ссылка корректно кодирует
кириллический текст и убирает `+` из номера, отсутствует при продаже без
контакта клиента. Дополнительно — сквозная проверка через живой `uvicorn`:
продажа → частичный возврат → остаток восстановлен → квитанция сгенерирована.
`compileall` — чисто.
