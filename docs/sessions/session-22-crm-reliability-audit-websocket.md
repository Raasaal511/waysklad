## Что сделано

### 1. CRM — «клиент как центр» (`9702602`, `1f8df8e`)

Пользователь явно попросил сначала обсуждение целей, не код — обнаружили,
что «клиент как центр» требует нового поля данных, не просто визуального
объединения вкладок Заказы/Задачи. Реализовано по согласованному плану
из 3 этапов:

1. `Task.client_id` (nullable FK на clients) — задачи можно привязать к
   клиенту, `POST/PATCH /api/tasks` принимают поле, `ITaskRepository.list_by_client()`.
2. `GET /api/counterparties/clients/{id}/timeline` — единая лента событий
   клиента (продажи, заказы, долги: выдача/погашения/продления, задачи),
   отсортированная по дате, с готовыми человекочитаемыми `title` —
   `GetClientTimelineUseCase` (`app/application/counterparties/get_client_timeline.py`).
3. `GET /api/counterparties/clients/{id}` — сводка клиента (раньше не было
   вообще, только список/поиск): `debt_balance`, `active_orders_count`,
   `open_tasks_count` — `GetClientSummaryUseCase`.

Подтверждает приоритет «единая карточка истории клиента» из
`docs/COMPETITOR_MOYSKLAD_ANALYSIS.md`.

### 2. Аудит надёжности — три направления одной темой (`3689db5`, `38ddc06`, `d79bbd1`, `08717e3`)

Пользователь запросил "тема надёжность" как отдельный фокус после CRM.

- **Офлайн-синк, дублирующийся `client_op_id` в одной пачке** (`3689db5`):
  `ApplyOfflineSalesUseCase` ловил только `DomainError` на каждую продажу,
  повтор `client_op_id` внутри одной пачки бился об `UNIQUE` constraint
  необработанным `IntegrityError`, ронял весь запрос в общий 409. Исправлено —
  `IntegrityError` теперь ловится, дубль резолвится в уже применённую продажу.
- **Гонка первого создания строки остатка** (`38ddc06`): первая операция
  над парой товар+склад (`stock_items` ещё нет) делала `SELECT FOR UPDATE`
  → `None` → `INSERT` без защиты — две параллельные первые операции
  (например, две приёмки на разные склады сразу после заведения товара)
  бились об уникальный частичный индекс. Исправлено через
  `session.begin_nested()` (savepoint откатывает только конфликтующую
  вставку, не всю транзакцию) + перечитывание под блокировкой.
- **Tenant-изоляция, аудит всех репозиториев** (`d79bbd1`): проход по
  `app/infrastructure/db/repositories/*.py` — эксплуатируемых дыр не нашли,
  но три места держались на инварианте «id уже провалидирован выше по
  стеку», не на самом SQL: `WarehouseAssignmentModel` (без `tenant_id`
  физически, методы не проверяли принадлежность склада), `catalog.py::find_duplicates`
  fallback без `tenant_id ==`, `debt_filter.py::_counterparty_name_expr` без
  tenant-фильтра на подзапросе. Все три получили явный tenant-фильтр —
  страховка на будущее, не реакция на найденный баг.
- **Наблюдаемость** (`08717e3`): в приложении не было `logging` и обработчика
  на непредвиденные исключения — `app/infrastructure/logging.py` (stdout
  structured logging), `app/infrastructure/admin_alerts.py` (Telegram-алерт
  на `ADMIN_ALERT_CHAT_ID` — чат разработчика/оператора, не владельца
  магазина), общий `@app.exception_handler(Exception)` в `errors.py`.

### 3. Складская часть — три пункта по прямому запросу (`b1af7ae`, `9e4afc1`)

Пользователь: "надо сделать каждый пункт" — себестоимость при приёмке,
партии/сроки годности (отложено по выбору пользователя через AskUserQuestion),
проактивный алерт по остаткам.

- **Себестоимость при приёмке** (`b1af7ae`): `ReceiveGoodsUseCase` теперь
  обновляет `Product.purchase_price` ценой последней приёмки (по строкам
  документа с `cost`, несколько строк одного товара — побеждает последняя
  по порядку). Раньше `cost` использовался только для суммы долга
  поставщику, карточка товара не менялась.
- **Проактивный алерт по остаткам** (`9e4afc1`): `notify_low_stock.py` по
  образцу `notify_due_debts.py` — та же выборка, что и отчёт «Рекомендации
  к дозаказу», дедупликация не чаще раза в день на товар, рассылка
  owner/manager, подключено в `scheduler.py`.

### 4. WebSocket вместо опроса уведомлений (`d55d3f5`)

Пользователь явно указал на архитектуру: "надо доделать уведомления и
сделать его на другом стеке — мешается что делает лишние запросы", выбрал
WebSocket (не рекомендованный изначально SSE) с Redis pub/sub между
воркерами прода.

`WS /api/notifications/ws?token=<access_token>` — авторизация через
query-параметр (браузер не может выставить заголовок Authorization на
WS-хендшейке). `app/infrastructure/ws_broadcast.py::Broadcaster` — в dev
(один процесс) форвардит в памяти; в проде (`--workers 4`) требует
`NOTIFICATIONS_REDIS_URL` (та же Redis-инстанция, что и rate limit, БД
`/1`) — без него открытое соединение клиента живёт только в одном воркере.
`notify_user` (единая точка создания уведомлений) публикует событие после
сохранения в БД. Попутно закрыты две инфраструктурные дыры: `nginx.conf` не
проксировал WS-заголовки (`Upgrade`/`Connection`), `vite.config.ts` dev-proxy
без `ws: true`.
