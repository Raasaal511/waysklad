# Сессия 14 — Синхронизация офлайн-очереди продаж

**Дата:** 2026-08-05
**Этап плана:** неделя 10 (README п. 8) — «PWA, офлайн-режим, полировка» (backend-часть)

## Контекст
Неделя 10 в README — преимущественно фронтенд (PWA-манифест, Service Worker,
IndexedDB, полировка UI). Пользователь явно попросил backend-only работу, так
что из этой недели в этой сессии сделана только backend-часть: приём и
идемпотентное применение офлайн-очереди операций («сервер прав, продажи
докатываются» — политика конфликтов из README), плюс первый плановый проход
по `TECH_DEBT.md` (п. 5 чек-листа недели 10).

`sales.client_op_id` (колонка + `UniqueConstraint("tenant_id", "client_op_id")`)
существовала в БД с сессии 01 — идемпотентность на уровне схемы была заложена
заранее, но нигде не использовалась: ни в domain-сущности `Sale`, ни в
`CreateSaleCommand`, ни в API. `presentation/sync/` и
`application/sync/apply_offline_ops.py` были пустыми заготовками.

## Что сделано
- **Идемпотентность в `CreateSaleUseCase`**: `Sale.client_op_id`,
  `CreateSaleCommand.client_op_id`, `ISaleRepository.get_by_client_op_id()` —
  если операция с таким `client_op_id` уже применена, use case возвращает уже
  существующую продажу вместо повторного списания остатка. Работает и для
  обычного `POST /api/sales` (опциональное поле), и для sync-очереди.
- **`application/sync/apply_offline_ops.py`**: `ApplyOfflineSalesUseCase` —
  применяет пачку `CreateSaleCommand` последовательно; ошибка одной операции
  (`DomainError`, например недостаточно остатка) не прерывает остальные —
  каждая обрабатывается независимо, результат содержит и применённые продажи,
  и список ошибок по `client_op_id`.
- **`presentation/sync/`**: `POST /api/sync/sales` — принимает пачку продаж с
  обязательным `client_op_id` на каждой, возвращает `{applied, errors}`.
- **`domain/sales/entities.py`, `mappers/sales.py`, `repositories/sales.py`**:
  `client_op_id` прокинут через весь стек (только для sales — возвраты и
  другие мутации в очередь пока не входят, см. TECH_DEBT #2).

## Проверено
96 тестов (было 93): повторный вызов `CreateSaleUseCase` с тем же
`client_op_id` не создаёт вторую продажу и не списывает остаток дважды;
`ApplyOfflineSalesUseCase` на пачке из валидной и невалидной (переспрос
остатка) операции — одна применяется, вторая падает с ошибкой, привязанной к
своему `client_op_id`, без отката первой; API-тест на `/api/sync/sales` с
повторной отправкой той же пачки (эмуляция обрыва связи после ответа сервера)
подтверждает отсутствие задвоения. Живой `uvicorn` + `waysklad_dev`: та же
проверка вручную — второй вызов вернул тот же `id`. `compileall` — чисто.

## TECH_DEBT — первый плановый разбор (п. 5 чек-листа недели 10)
Реестр был пуст. Заведены 3 находки: (1) нет use case «подключить Telegram»
(сессия 13 — сводка технически некому доходить), (2) sync принимает только
продажи, не возвраты/приёмки, (3) `ApplyOfflineSalesUseCase` не типизирует
причины ошибок. Ничего не оказалось «дешёвым для немедленного закрытия» — все
три требуют отдельного проектирования, оставлены в реестре с приоритетами.

## Сверка с README

прав, докатываются») закрыта. Остальное (PWA-манифест, Service Worker,
