# Сессия 25 — Витрина: карточка товара, сортировка, статус заявки, спам-защита

**Дата:** 2026-09-03
**Этап плана:** README §5.2 (публичная витрина), доработки поверх закрытого плана

## Контекст

После завершения трёх шагов плана витрины (сессии 23-24) пользователь
попросил список идей для дальнейшего развития — предложил список из 8
пунктов, выбрал 5 для реализации сразу: карточка товара, сортировка
каталога, статус заявки по токену, категории со счётчиком, защита от спама
заявками. Остальные (SEO/шеринг, информация о магазине) отложены.

Отдельно уточнена одна деталь: избранное на витрине — не backend-функция,
решение принято ранее (localStorage на стороне покупателя); пользователь
явно попросил держать контракты для фронта в отдельном файле, не смешивая
с основным журналом API — заведён `frontend/api_docs/storefront_extras.md`.

## Что сделано

1. **Карточка товара** — `GET /{slug}/products/{id}`
   (`GetStorefrontProductUseCase`), урезанный ответ (без закупочной
   цены/маржи) + `sku`/`variants` (размер/цвет) сверх списка каталога.
2. **Сортировка** — `?sort=` на `GET /{slug}`, безопасное подмножество
   `ProductFilterFactory.allowed_order_fields` (`name`/`retail_price`/
   `created_at` — без `margin`/`stock`).
3. **Категории со счётчиком** — новый `IProductRepository.count_storefront_by_category()`
   (`GROUP BY category_id` с фильтром `show_on_storefront`), пустые
   категории отфильтрованы на уровне use case.
4. **Статус заявки по токену** — `GET /requests/status?token=`
   (`GetStorefrontRequestStatusUseCase`), переиспользует существующий
   `access_token` (тот же, что и у чата), после принятия отдаёт снимок
   `Order` (`due_date`/`total`/`to_pay`/`status`).
5. **Спам-защита** — `IStorefrontRequestRepository.count_new_by_phone()`,
   не более 5 необработанных заявок с одного телефона на магазин
   одновременно; действует только когда телефон указан (анонимные заявки
   не ограничены — нечем идентифицировать).
