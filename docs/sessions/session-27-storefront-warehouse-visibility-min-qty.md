# Сессия 27 — Витрина: видимость склада, мин.кол-во заказа, фильтры «как в WB»

**Дата:** 2026-09-04
**Этап плана:** доработки поверх закрытого плана витрины, backend-only

## Контекст

Пользователь описал сценарий покупателя на витрине: видит товары со всех
складов сразу (уже так работает по умолчанию — `?warehouse_id=` не задан),
хочет опционально фильтровать по конкретной точке, и хочет ограничивать
заказ товара минимальным количеством и шагом (продажа мешками/партиями).

Явное решение по обсуждению: **не делать отдельный раздел «Склады»** с
собственной навигацией — покупателю физически не важно, с какого склада
товар, это внутренняя логистика владельца после приёма заявки. Список
складов — только опциональные метаданные в ответе каталога.

## Что сделано

1. **`Warehouse.show_on_storefront`** (миграция `3f7a2c9d1b6e`, дефолт
   `false`, как и `Product.show_on_storefront`) — склад можно скрыть от
   витрины независимо от товара. `PUT /api/inventory/warehouses/{id}`
   принимает новое поле.
2. **`GET /api/storefront/{slug}`** — новое поле `warehouses` в ответе
   (только видимые склады). `in_stock` и фильтр `?warehouse_id=` теперь
   учитывают только видимые склады — товар с остатком только на скрытом
   складе отдаётся как `in_stock: false`.
3. **`Product.storefront_min_qty`/`storefront_step_qty`** (миграция
   `8b1e4f6c2a9d`, оба `Decimal | None`, дефолт `None` = без ограничения) —
   настраиваются в форме товара владельцем, как цена/единица измерения.
   Валидируются только при создании заявки с витрины
   (`CreateStorefrontRequestUseCase._validate_storefront_quantity`) — не
   действуют в обычной продаже/заказе. Кратность шага считается от
   минимума (`(quantity - min) % step`), не от нуля.
4. Публичные поля названы иначе, чем в форме владельца — `min_order_qty`/
   `order_step_qty` в `StorefrontProductResponse` (список каталога и
   карточка товара), `storefront_min_qty`/`storefront_step_qty` в
   `ProductResponse` (форма владельца).

Отчёт для фронтенда — новые разделы 6 и 7 в
`frontend/api_docs/storefront_extras.md`.

## Фильтры «как в Wildberries» (та же сессия, продолжение)

Пользователь уточнил конкретно: фильтр по цене (от-до), «только в наличии»,
фильтр по размеру/цвету варианта — все три выбраны.

5. **Цена и наличие** — `GetStorefrontCatalogCommand.min_price`/`max_price`/
   `in_stock_only`, транслируются в уже существующий `ProductFilterFactory`
   через `retail_price__gte`/`__lte` и `stock__gt=0` — никакой новой
   инфраструктуры фильтрации не потребовалось, только новые query-параметры
   на публичном роуте.
6. **`_stock_expr` расширен** принимать список складов (`warehouse_ids`), не
   только один `warehouse_id` — иначе фильтр `in_stock_only` считал бы
   остаток по ВСЕМ складам тенанта, а не только видимым на витрине.
   `ProductFilterFactory.build_fields()`/`IProductRepository.list_filtered()`
   получили этот параметр как расширение сигнатуры (единственный вызывающий
   код — каталог товаров владельца — передаёт `None`, поведение не меняется).
7. **Фильтр по варианту (size/color)** — сделан НЕ через generic `field__op`
   DSL (`EQ`/`IN` там не выражают «есть хотя бы один вариант с size == X» на
   уровне одной колонки без искусственных трюков — пробовал и отказался от
   двух вариантов: булев scalar_subquery с плейсхолдером, array_agg + IN).
   Вместо этого — явный `EXISTS(SELECT 1 FROM product_variants WHERE ...)`
   прямо в `SqlAlchemyProductRepository.list_filtered()`, in параметры
   `variant_size`/`variant_color` отдельно от generic `raw_params`. Решение
   осознанно точечное — не тянуть публичный edge case в общий фреймворк
   фильтрации, которым пользуется весь остальной продукт.
8. **`IProductRepository.list_storefront_variant_options()`** — новый метод,
   отдаёт уникальные size/color среди вариантов товаров, видимых на витрине
   (`show_on_storefront=True`) — иначе фильтр по размеру бесполезен без
   списка доступных значений. `GET /api/storefront/{slug}` — новые поля
   `available_sizes`/`available_colors` в ответе.

Явное решение по обсуждению: **никакого отдельного раздела/страницы
«Склады»** с собственной навигацией не делаем — см. выше, покупателю
физически не важно, с какого склада товар.

## Самопроверка после сдачи (по запросу пользователя) — 2 находки

Пользователь попросил перепроверить собственную работу на недочёты. Нашёл
и исправил один реальный баг, задокументировал один реальный риск:

1. **Баг: мин.кол-во/шаг проверялись по каждой СТРОКЕ заявки отдельно, не
   суммарно по товару.** Если покупатель заказывает один товар в двух
   вариантах (например, платье 5 шт размера M + 5 шт размера L), при
   `storefront_min_qty=10` обе строки отклонялись бы (5 < 10), хотя
   суммарно это 10 штук одной модели. Исправлено — `CreateStorefrontRequestUseCase`
   теперь группирует `cmd.items` по `product_id` и суммирует `quantity`
   по всем строкам (вариантам) перед валидацией. Новый тест-кейс внутри
   `test_storefront_request_min_and_step_qty_via_api` (5+5=10 — валидно).
2. **Риск (не исправлено сейчас, задокументировано как TECH_DEBT №23):**
   миграция `warehouses.show_on_storefront` (дефолт `false`) — breaking
   для уже работающих витрин. Любой магазин, где витрина уже была включена
   ДО этой сессии, после миграции разом теряет видимость всех складов —
   товары молча показывают `in_stock: false`. На момент находки в проде
   реальных пилотных магазинов с витриной не было, но перед следующим
   деплоем (если появятся живые магазины) нужен backfill-скрипт или явное
   предупреждение владельцам.

239/239 тестов после исправления.
