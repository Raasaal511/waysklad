# Сессия 21 — Роли/склады для управляющего, закрытие фронтенд-хвостов недель 7–10

**Дата:** 2026-08-12
**Этап плана:** внеплановая доработка (роли/склады) + недели 7, 8, 9, 10 (закрытие фронтенд-хвостов из `NEXT_STAGES_PROMPT.md`)

## Контекст

Пользователь спросил, почему роль «Управляющий» не видит аналитику, и захотел,
чтобы управляющий видел аналитику своего склада, а остальные роли
(кладовщик, продавец) видели только релевантные им вкладки — «более
правильное для бизнеса распределение». По итогам обсуждения (см. вопросы
пользователю в переписке) договорились:

- Каждый сотрудник (кроме owner) при создании привязывается к складу(-ам).
- Owner — без привязки, видит весь бизнес.
- Роль `analyst` убирается из выбора при создании сотрудника (не удаляется
  из кода/БД — для обратной совместимости с уже существующими пользователями).

Отдельно пользователь запросил UX-анализ удобства этой модели для типичного
целевого клиента (маленький магазин одежды на рынке Беркат — один склад,
1–3 человека) и поручил параллельно закрыть накопленные долги из
`NEXT_STAGES_PROMPT.md` по недельным этапам 7–10, не дожидаясь отдельных
запросов.

## Что сделано

### Роли и склады (внеплановая доработка)

Первая попытка реализующего агента не внесла ни одной правки (сработала
как research-агент вместо implementation) — перезапущена с явным указанием
не останавливаться и не спрашивать подтверждения.

Промежуточный UX-анализ (`docs/UX_ROLES_SMALL_SHOP_ANALYSIS.md`) вскрыл
риск исходного плана «один сотрудник — один `warehouse_id`» (жёсткий FK):
не позволяет тому же продавцу подменять на двух точках при росте бизнеса до
двух складов. Рекомендация — переиспользовать уже существующий паттерн
`Warehouse.assigned_user_ids` (многие-ко-многим, раньше только для
storekeeper) для всех непривилегированных ролей, и не показывать выбор
склада в форме сотрудника, если склад в магазине всего один. Реализация
учла обе рекомендации:

- `backend/app/domain/identity/permissions.py` — `Role.MANAGER` получил
  `Permission.ANALYTICS_VIEW` (было явно исключено — причина исходного
  вопроса пользователя).
- `backend/app/domain/identity/repository.py`,
  `infrastructure/db/repositories/identity.py` — `WarehouseAssignmentModel`
  (таблица `warehouse_assignments`, миграция уже существовала) переиспользуется
  для manager/seller/storekeeper, не только storekeeper; `add_assignment`,
  `set_user_assignments`.
- `backend/app/application/auth/employee_warehouses.py` (новый) —
  `resolve_warehouse_ids()`: owner → `[]`; единственный склад в tenant →
  назначается автоматически независимо от того, что передал фронт;
  несколько складов → обязателен явный выбор ≥1 склада, все должны
  принадлежать тому же tenant.
- `backend/app/application/auth/update_employee.py` (новый) —
  `UpdateEmployeeUseCase`, которого раньше не было вообще (только
  create+list) — правка роли/имени/статуса/списка складов сотрудника.
- `backend/app/presentation/deps/auth.py` — `Actor` пополнился
  `warehouse_ids: list[int] | None` (`None` = без ограничения, для
  owner/analyst); `require_warehouse()` — проверка доступа к складу
  документа.
- Фильтрация по складу применена к продажам (`Sale.warehouse_id` — уже
  существовавшее поле документа, не выводится из текущей привязки
  сотрудника — исторические продажи не «телепортируются» при смене
  склада сотрудника), остаткам и всей аналитике (`dashboard`,
  `top_products`, `dead_stock`, `stock_value`, `category_profit`).
  **Сознательно НЕ применена** к `Order`/`Debt`/`Client`/`Supplier` — в их
  domain-схеме нет `warehouse_id` вообще, добавление потребовало бы новой
  миграции и выходит за рамки задачи (зафиксировано как находка
  `TECH_DEBT.md` №5).
- Frontend: `AppLayout.tsx` — меню сужено по ролям (storekeeper видит
  только Товары/Остатки, seller — без Аналитики/Сотрудников, полная
  матрица в файле); `EmployeesPage.tsx` — форма создания/редактирования
  сотрудника, чекбоксы складов показываются только когда складов больше
  одного, роль `analyst` убрана из select.
- 7 новых backend-тестов (авто-назначение единственного склада, валидация
  на нескольких складах, отказ по неизвестному `warehouse_id`, продавцу
  запрещена продажа на чужом складе, аналитика менеджера ограничена его
  складом, `UpdateEmployeeUseCase`).

### Неделя 7 — «Должны сегодня» и баланс поставщика

- `DebtsPage.tsx` — блок «Должны сегодня и просрочено»: объединение
  `listDueDebts()` (уже существовавшая, но не вызывавшаяся обёртка) и
  долгов со статусом `overdue` из уже загруженного списка, без дублей.
- `ClientsPage.tsx` — вкладка «Поставщики» стала кликабельной, модалка
  `SupplierDebtsSummary` (по образцу уже существующей `ClientDebtsSummary`)
  показывает контакт, сумму активных долгов и список долгов с бейджами
  статусов. Backend не потребовал изменений — `GET /debts/supplier/{id}`,
  `GET /counterparties/suppliers` уже существовали.

### Неделя 8 — Общий журнал действий

- Backend `GET /audit` расширен: join по `users` для имени сотрудника
  (`user_name` в ответе — раньше отдавался только `user_id`),
  `limit`/`offset` для постраничной подгрузки.
- `frontend/src/pages/audit/AuditPage.tsx` (новая страница) — таблица
  «Дата/Сотрудник/Действие/Объект» со словарём человекочитаемых подписей
  действий, кнопка «Показать ещё». Пункт меню «Журнал» видим только
  owner/analyst (`Permission.AUDIT_VIEW`).

### Неделя 9 — Прибыльность по категориям

- `AnalyticsPage.tsx` — секция «Прибыльность по категориям» поверх уже
  готового `GET /analytics/category-profit` и фронтенд-обёртки
  `getCategoryProfit()` (существовали, но нигде не вызывались). Таблица:
  категория/выручка/прибыль/маржа % (маржа считается на фронте из
  revenue/profit — backend её отдельным полем не возвращает), сортировка
  по прибыли убыванию.

### Неделя 10 — Офлайн-очередь продаж (самый крупный пробел MVP)

- `frontend/src/shared/offline/outbox.ts` — сырой IndexedDB (без
  Dexie/idb — не оправдано для одного object store с несколькими
  функциями). `queueSale()` генерирует `client_op_id` через
  `crypto.randomUUID()`, использует уже существующую на бэкенде
  идемпотентность по этому полю (`CreateSaleUseCase.execute`).
- `frontend/src/shared/offline/useOfflineSync.ts` — синхронизация при
  монтировании приложения (на случай сети, появившейся пока вкладка была
  закрыта) и по событию `online`; батч в `POST /api/sync/sales`, ошибки
  по отдельным операциям не блокируют остальные (уже так работало на
  бэкенде).
- `SalePage.tsx` — при создании продажи отличает сетевую ошибку
  (`navigator.onLine === false` или `TypeError` от fetch) от бизнес-ошибки
  (`ApiError`, например «нет остатка») — только первая уходит в очередь,
  вторая показывается как обычно. **Продажи в долг не ставятся в
  очередь** — контракт `/api/sync/sales` не принимает `debt_due_date`
  (находка `TECH_DEBT.md` №6, приоритет — высокий, оплата в долг слишком
  частый сценарий для ЦР, чтобы оставлять без офлайн-поддержки).
- `AppLayout.tsx` — тост с итогом синхронизации, бейдж «Не отправлено: N»
  в сайдбаре.
- `vite.config.ts` — `workbox.runtimeCaching`, `NetworkFirst` для
  `GET /api/(products|inventory|counterparties)`, чтобы экран продажи
  открывался хотя бы с последними закэшированными данными без сети.

## Как была организована работа

Все куски (роли/склады, журнал, прибыльность по категориям, долги
поставщика, офлайн-очередь) реализовывались параллельно фоновыми агентами
в изолированных git worktree, чтобы не блокировать друг друга. Слияние в
`develop` — вручную через `git merge-file` (трёхстороннее слияние: общий
коммит-предок → текущее состояние `develop` → правки агента) для файлов,
которые редактировались в нескольких потоках одновременно
(`AppLayout.tsx`, `SalePage.tsx`, `DebtsPage.tsx`, `ClientsPage.tsx`,
`entities/sale/api.ts`, `index.css`, `vite.config.ts`) — все слияния
прошли автоматически без ручного разрешения конфликтов. Один worktree
(иконка журнала) использовал уже удалённый в основной ветке компонент
`shared/ui/icons/Icon.tsx` — заменён на `@tabler/icons-react` (`IconHistory`)
вручную при слиянии.
