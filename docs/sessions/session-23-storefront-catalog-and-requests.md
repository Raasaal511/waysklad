# Сессия 23 — Товары на generic-фильтрах, публичная витрина (каталог + заявка)

**Дата:** 2026-09-03
**Этап плана:** README §5.2 (публичная витрина), техдолг №14, backend-only режим

## Контекст

Пользователь захотел начать работу над публичным каталогом-витриной
(`docs/STOREFRONT_PLAN.md`, план зафиксирован в предыдущей сессии), но
попросил сначала закрыть находку №14 из `TECH_DEBT.md` (generic
filter-система для Долгов/Товаров) — витрина сама потребует такую же
фильтрацию каталога, лучше не городить второй одноразовый фильтр поверх.

## Что сделано

### 1. Товары на generic-фильтрах (закрывает находку №14)

Выяснилось, что находка была наполовину устаревшей: инфраструктура
(`app/domain/filtering/`, `app/infrastructure/db/filtering/` —
`BaseQueryFilterFactory`, `FieldSpec`, `Operator`) уже существовала и
использовалась Долгами. Дописан симметричный `ProductFilterFactory`
(`product_filter.py`) — `IProductRepository.list_filtered()` заменил
ручной `search()`. Остаток на складе (`in_stock_only`, `sort=stock_desc`)
теперь SQL-выражение (subquery по `stock_items`, опционально по
конкретному `warehouse_id`), а не Python-фильтр на клиенте по одной
загруженной странице — перенос на фронт зафиксирован как находка в
`TECH_DEBT.md` (клиентский код в `ProductsPage.tsx` не тронут — backend-only).

### 2. Витрина, шаг 1 — публичный каталог без заявки

`GET /api/storefront/{slug}` без авторизации. Требует оба флага разом:
`Tenant.storefront_enabled` (дефолт `false`) + `Product.show_on_storefront`
(дефолт `false`) — оба выключены по умолчанию по прямому решению
пользователя (осторожность: включение витрины на заполненном каталоге не
должно ничего раскрыть неявно). Урезанный ответ без `purchase_price`/`margin`/
точного остатка — только `in_stock: bool`. Rate limit `60/minute` (тот же
механизм, что и `/auth/register`).

### 3. Витрина одного склада — `?warehouse_id=`

Уточнение пользователя после первого прохода: «витрина» — всегда единый
каталог магазина (не разные витрины на товар/категорию), но нужна
возможность поделиться ссылкой на ассортимент конкретного склада. Список
товаров не сужается — меняется только `in_stock` (без параметра — сумма
по всем складам, с параметром — остаток именно на этом складе, товар без
остатка там всё равно показан с `in_stock:false`). Несуществующий/чужой
`warehouse_id` тихо игнорируется, не даёт перебором узнавать id чужих
складов.

### 4. Витрина, шаг 2 — заявка с публичной страницы

Отличается от изначального черновика плана: заявка НЕ становится `Order`
сразу. Причина — `due_date` (обязательное поле `Order`) покупателю
неизвестен, а требование указать его сразу отсекает пустые/спам-заявки
(решение пользователя). Новая лёгкая сущность `StorefrontRequest`
(`app/domain/storefront/`) — имя (обязательно), телефон и комментарий
(опционально), корзина с количеством, без резерва остатка.

- `POST /api/storefront/{slug}/requests` — публично, `20/hour` rate limit.
- `GET /api/storefront/requests/new` — владелец, отдельный список (не
  смешивается с обычными заказами).
- `POST /api/storefront/requests/{id}/accept` — владелец указывает склад
  и дату готовности → резервируется остаток, создаётся `Order` с
  `source=storefront`, цена берётся из АКТУАЛЬНОГО `retail_price` (не из
  момента заявки — могла измениться).
- `POST /api/storefront/requests/{id}/reject`.

Клиент ищется по телефону среди существующих (`IClientRepository.get_by_phone`,
новый), не создаётся заново при повторном обращении. Потребовало отдельного
решения: **`clients.phone` стал уникальным** в пределах магазина —
частичный уникальный индекс `clients(tenant_id, phone) WHERE phone != ''`
(пустой телефон не считается дублем) — прямое указание пользователя
"сделай номер уникальным", коммит отдельно от заявок.

Токен доступа покупателя к своей заявке (был в открытых вопросах плана) —
НЕ реализован в этой итерации, заявка read-only только для владельца.

## Найдено попутно

`SqlAlchemyOrderRepository.add()` не присваивает `order.number` обратно
в domain-объект после генерации — ответ создания заказа отдаёт
`number: null` (данные в БД корректны, `GET` вернул бы верный номер). Не
регрессия этой сессии — тот же баг был бы и в обычном `POST /api/orders`.
Заведена находка №22 в `TECH_DEBT.md`, не исправлялась (не в скоупе).
