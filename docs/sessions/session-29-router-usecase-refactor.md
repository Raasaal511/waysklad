# Сессия 29 — Роутеры: read-only эндпоинты через use case вместо async with uow

**Дата:** 2026-09-05
**Этап плана:** плановый разбор `TECH_DEBT.md` (backend-only)

## Контекст

По итогам предыдущей сессии (закрытие №2/№3/№5) пользователь заметил при ревью
диффа, что `search_clients`/`list_suppliers` — раздутые (4-6 строк с прямым
`async with uow`) эндпоинты, тогда как остальной `counterparties/router.py` —
однострочники, делегирующие в use case. Проверка показала: это не локальный
огрех, а существующий паттерн всего проекта — 42 места в 10 роутерах
(`sales`, `orders`, `debts`, `products`, `counterparties`, `auth`, `inventory`,
`notifications`, `tasks`, `storefront`). Заведено находкой №24, пользователь
явно попросил отдельную сессию на весь проект целиком, не смешивать с
точечными правками — эта сессия и есть тот проход.

## Что сделано

Единый паттерн по всем 10 модулям: для каждого read-only эндпоинта с
`async with uow` заведён Command dataclass + UseCase класс в
`app/application/<module>/`, зарегистрированный в `deps/use_cases.py` через
уже существующий в проекте хелпер `_with_uow(use_case_cls)` +
`Annotated[..., Depends(...)]` — тот же паттерн, что уже использовался для
всех мутирующих эндпоинтов. Роутеры стали однострочниками (`return
Response.from_x(await use_case.execute(actor, cmd))`), кроме мест, где
нужна HTTP-специфика:

- **`sales/router.py::list_sales`** — `response.headers["X-Total-Count"]`
  осталась в роутере, use case возвращает `ListSalesResult(sales, total)`.
- **`inventory/router.py`** — экспорт документов (xlsx/csv/pdf): данные
  через новый `GetDocumentExportDataUseCase` (бывший приватный хелпер
  `_load_document_export_data`), само форматирование в конкретный файл
  (`render_documents_xlsx/csv/pdf`) осталось в роутере — это presentation-
  забота, не бизнес-логика.
- **`counterparties/router.py`** — warehouse-scoping клиентов/поставщиков
  (находка №5, предыдущая сессия) перенесён внутрь
  `SearchClientsUseCase`/`ListSuppliersUseCase` без изменения поведения.
- **WebSocket-эндпоинты** (`notifications_ws`, `storefront_chat_ws`) не
  тронуты — используют `SessionFactoryDep`, не относятся к этой задаче.

По ходу найден один довесок вне изначального списка: `sales/router.py::edit_sale`
(мутирующий эндпоинт) держал прямой `async with uow` для повторного чтения
продажи после `EditSaleUseCase.execute()` (которая ничего не возвращает по
дизайну) — заменено на переиспользование уже существующего `GetSaleUseCase`,
отдельный 11-й коммит.

## Проверено

245/245 тестов бэкенда — прогонялись после каждого модуля, не только в конце.
`grep -rn "async with uow" app/presentation/*/router.py` — пусто, все 42 места
закрыты. 38 новых use case классов в 35 файлах. Миграций не потребовалось —
чисто структурный рефакторинг слоёв, схема БД не менялась.

## Компромисс по границам коммитов (задокументировано, не исправлялось)

`deps/use_cases.py` и `deps/__init__.py` — общие файлы. Коммиты `products` и
`inventory` физически содержат ещё и DI-регистрации для `counterparties`/
`auth` и `notifications`/`tasks`/`storefront` соответственно — агент готовил
несколько модулей параллельно, пока ждал прогон тестов, и не разделил дифф
общего файла по границам сообщений коммитов. Функционально не влияет (каждый
коммит зелёный по тестам), но `git log` для этих двух коммитов не полностью
соответствует заявленной теме. Пользователь решил не переписывать историю
(`git rebase -i`) ради косметики — оставлено как есть.
