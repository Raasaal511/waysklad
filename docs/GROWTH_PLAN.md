## 0. Коротко

1. **Продукт по функциям уже больше MVP.** Ядро README §5.1 закрыто, сверху —
   витрина, CRM, задачи, админка, отзывы. 20+ живых пользователей. Новые
   модули сейчас рост не дадут. Его дадут: надёжность, скорость трёх главных
   сценариев (продажа, долг, заявка с витрины), рабочие каналы связи и сарафан.
2. **Каналы в РФ поменялись.** WhatsApp с февраля 2026 открывается только
   через VPN, Telegram с февраля 2026 работает с задержками, трафик к
   Cloudflare режется с июня 2025. На них завязаны чеки и напоминания (`wa.me`),
   вечерние сводки и подтверждение телефона покупателя (Telegram), а
   возможно, и доступ к проду (если DNS домена проксируется через Cloudflare). Это главный
   риск плана и одновременно окно: у МАКС 100 млн пользователей и бесплатный
   Bot API, а МойСклад поднял тарифы с 1 июля 2026.
3. **Есть риски, которые могут обнулить доверие, и они дешёвые.** 164 коммита
   лежат только на ноутбуке, `docs/` и `README.md` не в git, прод отстаёт от
   кода на 177 коммитов (включая согласие по 152‑ФЗ), фото товаров не входят в
   бэкап, восстановление из бэкапа ни разу не проверялось.
4. **Главное по UX:** на телефоне 9–10 пунктов в нижней навигации (при правиле
   проекта «не больше 7»), покупателю для заявки нужен логин, пароль и
   Telegram, нельзя продать «часть сейчас, остальное в долг», мобильную панель
   «В корзину» на карточке витрины перекрывает нижняя навигация.
5. **По технике:** нет слоя кэша серверных данных (291 `useEffect`, экраны
   каждый раз грузятся с нуля), нет фронтенд‑тестов, нет замеров скорости
   работы пользователя. Без замеров правило «фичи ускоряют, а не утяжеляют»
   нечем проверить.

**Порядок на полгода:** ничего не потерять (сентябрь) → надёжность и каналы
(октябрь) → касса быстрее тетради (ноябрь) → долги лучше тетради (декабрь) →
владелец видит всё за 30 секунд (январь) → внедрение за час и сарафан
(февраль) → запас на 100 магазинов (март).

## 4. Принципы скорости — как проверять «ускоряет, а не утяжеляет»

Дополняет `UX_SIMPLICITY_RULES.md` числами. Любая задача из плана должна
улучшать одну из строк таблицы или хотя бы не ухудшать её.

| Бюджет | Сейчас (оценка по коду) | Цель |
|---|---|---|
| Продажа 1 товара по скану, от открытия приложения | 3 касания + скан: «Новая продажа» → «Сканировать» → скан → «Провести» (из другого раздела — 4) | **2 касания + скан** из любого раздела: «Продать» (камера открывается сама, если продавали сканером) → скан → «Продать · N ₽» |
| Продажа частого товара без штрихкода | поиск + ввод 2–4 букв + выбор | **2 касания** через плитки «Часто продают» |
| Продажа с частичной оплатой в долг | 3 экрана, 8+ касаний | **1 экран**, поле «Заплатил сейчас» |
| Запись долга из карточки клиента | отдельная страница, 6+ полей | **≤ 10 секунд**: сумма → «Дал в долг» |
| Повторное открытие экрана | загрузка + спиннер | **мгновенно из кэша**, обновление в фоне |
| Нижняя навигация на телефоне | 9–10 пунктов | **5** (4 вкладки + «Ещё», «Продать» в центре) |
| Текст на телефоне | 47% объявлений ≤ 13px | основной **16px**, вторичный **14px**, ≤ 12px только бейджи |
| Зона касания | кнопки ~40px, чекбоксы 16px | **≥ 44px** |
| Заявка с витрины | аккаунт + пароль + Telegram | вход оставляем (решение 22.09); **отвал на шаге входа ≤ 25%** |
| LCP витрины (моб.) | 2,7–3,1 с | **≤ 2,5 с** |

Правило для каждой новой фичи (добавляю к тесту простоты шестой вопрос):
**«Какие шаги у пользователя она убирает?»** Нет ответа — значит, фича
утяжеляет.

## 5. UX/UI‑референсы: что берём и чего не берём

Выбраны продукты, которые решают **ту же задачу для той же аудитории**, а не
просто красивые сайты. Красота без скорости в нашем сегменте не работает.

| Референс | Что у них работает | Берём | Не берём |

## 6. Дизайн: не редизайн, а порядок

Цель — удобство и скорость, а не новый стиль. Цвета, акценты и тёмная тема
остаются как есть. Меняются шкала, отступы и мобильные паттерны.

### 6.1. Токены (кабинет получает ту же шкалу, что уже описана для публичных страниц)

`PUBLIC_UI_GUIDE.md` уже задаёт шкалу для витрины, но только текстом — в CSS
её нет, и кабинет живёт без неё. Предлагаю сделать её переменными в
`index.css` и использовать везде:

```css
:root {
  /* Типографика: 8 ступеней вместо 48 (значения из PUBLIC_UI_GUIDE.md) */
  --fs-12: 12px;  /* только бейджи и подписи */
  --fs-14: 14px;  /* вторичный текст, таблицы на десктопе */
  --fs-16: 16px;  /* основной текст, поля, кнопки на телефоне */
  --fs-18: 18px;  /* заголовок карточки, цена в карточке */
  --fs-20: 20px;  /* заголовок раздела на телефоне */
  --fs-24: 24px;  /* заголовок экрана */
  --fs-28: 28px;  /* крупные суммы: итог продажи, выручка */
  --fs-32: 32px;  /* H1 на десктопе (на телефоне — 24) */

  /* Отступы: шкала 4..64 из PUBLIC_UI_GUIDE.md, других нет */
  --sp-4: 4px;   --sp-8: 8px;   --sp-12: 12px; --sp-16: 16px; --sp-20: 20px;
  --sp-24: 24px; --sp-32: 32px; --sp-40: 40px; --sp-48: 48px; --sp-64: 64px;

  /* Радиусы: 4 вместо 31 */
  --r-8: 8px; --r-12: 12px; --r-16: 16px; --r-full: 999px;

  /* Тени: 2 вместо 54 */
  --shadow-1: 0 1px 2px rgb(0 0 0 / 0.06), 0 1px 3px rgb(0 0 0 / 0.08);
  --shadow-2: 0 8px 24px rgb(0 0 0 / 0.12);

  --tap: 44px; /* минимальная зона касания */
}

/* деньги и количества — моноширинные цифры, колонки не «прыгают» */
.num { font-variant-numeric: tabular-nums; }
```

Как не расползтись снова: простой скрипт в CI (grep, без новых зависимостей)
падает, если в `*.module.css` появился `font-size`, `border-radius` или
`box-shadow` не через переменную. Миграцию делать по экрану, начиная с самых
частых: Продажа → Долги → Товары → Клиенты.

### 6.2. Мобильная навигация (G‑14)

```
Владелец / управляющий                    Продавец
┌───────┬───────┬─────────┬──────┬─────┐   ┌───────┬───────┬─────────┬──────┬─────┐
│Сегодня│Товары │ ПРОДАТЬ │Долги │ Ещё │   │Продажи│Товары │ ПРОДАТЬ │Долги │ Ещё │
└───────┴───────┴─────────┴──────┴─────┘   └───────┴───────┴─────────┴──────┴─────┘
«Ещё» владельца → Заказы · Витрина · Клиенты · Склады · Задачи · Аналитика · Сотрудники · Профиль
«Ещё» продавца  → Заказы · Клиенты · Склады · Задачи · Витрина · Профиль
```

- «Продать» — крупная кнопка в центре, открывает экран продажи сразу с фокусом
  в поиске. Если в прошлый раз продавали сканером — сразу с камерой.
- До появления экрана «Сегодня» (G‑25) первая вкладка владельца — «Продажи».
- Десктопный сайдбар не меняется, только группировка: «Работа» (Продажи,
  Заказы, Долги, Клиенты) / «Склад» (Товары, Склады) / «Управление» (Аналитика,
  Задачи, Сотрудники, Витрина).
- Кладовщик и аналитик получают те же 4 + «Ещё», наполненные по их правам
  (без «Продать», если продавать им нельзя).
- «Выйти» уходит в Профиль, из шапки на телефоне его убираем.

### 6.3. Экран продажи на телефоне (G‑15, G‑16)

```
┌─────────────────────────────────┐
│ 🔍 Поиск или скан          [📷] │
│ Часто продают                   │
│ [Хлеб ] [Молоко] [Сахар] [Чай ] │  ← 8–12 плиток, сортировка по продажам за 30 дней
│ [Спички] [Мука ] [Масло] [Соль] │
│ Чек · 3 позиции           ▾     │
├─────────────────────────────────┤
│ ( Наличные ) ( Перевод ) ( Долг ) │
│ Заплатил сейчас: [ 3 000 ]      │  ← только при «Долг»
│ ┌─────────────────────────────┐ │
│ │     Продать · 5 000 ₽       │ │  ← закреплено над навигацией
│ └─────────────────────────────┘ │
└─────────────────────────────────┘
```

### 6.4. Мобильные паттерны, которые вводим один раз и используем везде

- **Закреплённая панель действия** снизу (над навигацией) у всех форм:
  «Создать товар», «Продать», «Записать долг», «В корзину» на витрине.
- **Нижняя шторка вместо модалки** на телефоне (выбор клиента, способ оплаты,
  фильтры). Большой палец достаёт, а модалка по центру требует тянуться.
- **Скелетоны вместо спиннеров** на списках — вместе с кэшем (G‑17) их почти
  не будет видно.
- **Форма товара на телефоне:** фото — кнопка «📷 Снять» 64px рядом с
  названием; метрики «Закупка / Маржа / Порог / Остаток» — сетка 2×2; у цены
  подпись «Цена продажи».
- **Карточка товара витрины на телефоне:** панель «Итого · В корзину»
  (`MobileDock`) стоит над нижней навигацией, а не под ней (релиз 1.0).

## 8. Метрики

Главная (North Star): **активные магазины недели** — магазины, где продажи
были минимум в 3 разных дня за последние 7. Считается по уже имеющимся
данным (`last_sale_at` / продажи по дням в админке).

| Метрика | Как считаем | Цель к 31.12.2026 | Цель к 31.03.2027 |
|---|---|---|---|
| Внедрённых магазинов | админка | 20 | 50 |
| Активных через месяц после внедрения | health в админке | ≥ 70% (README §12) | ≥ 75% |
| Медиана «открыл продажу → продал» | G‑11 | ≤ 15 с | ≤ 10 с |
| Доля позиций, добавленных сканом или плиткой | G‑11 | ≥ 50% | ≥ 65% |
| Поиск без результата в продаже | G‑11 | ≤ 8% | ≤ 5% |
| Заявки витрины, брошенные на шаге входа покупателя | G‑11 | ≤ 25% | ≤ 15% |
| Отправлено выписок / напоминаний по долгам в неделю | G‑11 | база | ×2 от базы |
| Аптайм прода | мониторинг G‑08 | ≥ 99,5% | ≥ 99,8% |
| Время восстановления из бэкапа | ежемесячный прогон | ≤ 1 ч | ≤ 30 мин |
| Доход с услуг | учёт вручную | 30–50 тыс. ₽/мес (README §12) | 60+ тыс. ₽/мес |

Цели по магазинам и доходу — ориентиры из README, поправь под реальные
возможности визитов.

| P‑41: заявка только с аккаунтом, регистрация покупателя подтверждается в Telegram | Оставлено как есть (решение 22.09), но с метрикой отвала на шаге входа | Если метрика покажет потери — вернуться к заявке без аккаунта |
| P‑34 (инсайты без LLM) — «ПОТОМ» | G‑24, декабрь | Дёшево, и работает на главную метрику: сводка — ежедневный повод открыть продукт |
| «В меню — не больше 7 пунктов» | На телефоне — не больше 5 | Material 3 и реальная ширина экрана 360–390px |
| Ежедневный xlsx в Telegram | Раз в неделю или по кнопке | Файлы через Telegram сейчас доставляются плохо; нужен ли файл каждый день — спросить у пилота |
| Своя система справочников `CatalogContext`, «без новых зависимостей» | TanStack Query (~15 КБ gzip) | Одна проверенная зависимость заменяет ручной кэш и сотни `useEffect`, даёт оптимистичные обновления и офлайн‑кэш. Это прямо про скорость |
| Прод на LS | Уже на VPS (22.09); LS — dev | Остаётся проверить DNS без прокси Cloudflare |

**Не меняю и поддерживаю:** маркетплейс выключен; витрина — магазин по
ссылке; wikkeo‑уровень — только исправления багов; AI‑описания товаров
убраны; этикетки / IMEI / прокат — по запросу конкретного магазина.

Нативные приложения (PWA хватает, и оно ставится после G‑05) · онлайн‑оплата
и эквайринг · SSR / Next.js · микросервисы и Kubernetes · Redux и другие
тяжёлые стейт‑менеджеры · LLM‑советы в сводке · маркетплейс · любая фича, у
которой нет ответа на вопрос «какие шаги она убирает».
