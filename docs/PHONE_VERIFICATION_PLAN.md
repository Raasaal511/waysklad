# Записка: что делать с подтверждением номера — уточнение задачи

Записано 2026-09-21 (v3 — переоценка задачи после проверки фактов). **Код не
реализован, флаг `phone_verified` не добавлен.** Предыдущие версии этого
файла (v1: rate-limit, v2: хард-стоп на заказ при "входе без подтверждения")
спроектировали решение для проблемы, которая при проверке фактов оказалась
не той, что нужно решать. Ниже — по существу.

## Что выяснено про корзину/избранное (факт, проверено по коду)

**На backend корзины и избранного не существует вообще** —
`grep -rln "cart\|Cart\|favorite\|Favorite" app/domain` не находит ничего.
Это чисто фронтенд-понятия (localStorage), backend о них не знает.

**Просмотр витрины не требует входа.** В
`app/presentation/storefront/router.py` у `GET /{slug}`,
`GET /{slug}/products/{id}`, `GET /{slug}/profile` и других read-эндпоинтов
нет зависимости `CurrentCustomerDep` — каталог, карточка товара, профиль
магазина открыты без авторизации. Значит "смотреть и складывать в корзину
без входа" уже работает сегодня, без каких-либо изменений — это
подтверждает первую гипотезу пользователя.

**Только оформление заказа требует входа.** `POST /{slug}/requests`
(`create_storefront_request`, router.py:190-202) — единственный
write-эндпоинт с `customer: CurrentCustomerDep`. А `CurrentCustomerDep`
достаётся только из JWT, который выпускает
`ConfirmCustomerLoginLinkUseCase` — то есть **только после подтверждения
через Telegram-бота**. Отзыв и чат заявки тоже завязаны на существование
`StorefrontRequest`, то есть на тот же вход.

## Вывод: какую боль лечим

Правильная формулировка (после проверки): **сейчас оформить заказ можно
только через Telegram — нет вообще никакого альтернативного пути.** Вопрос
не в "заставляем ли мы входить, чтобы смотреть" (не заставляем, уже так) —
а в "что делать покупателю без Telegram, который дошёл до оформления
заказа и упёрся в стену".

Раньше (v2) я спроектировал "вход без подтверждения, но с блокировкой
заказа" — это НЕ решает проблему покупателя без Telegram, оно просто
переносит стену на шаг позже (кнопка «Оформить» вместо кнопки «Войти»,
результат тот же: заказ так и нельзя оформить). Реального решения
"обойтись без Telegram" такая модель не даёт — она даёт только более
поздний UX для той же невозможности. Значит вопрос по существу — нужна ли
вообще альтернатива Telegram-подтверждению для заказа, и если да, то какая.

## Варианты для альтернативы подтверждению (если решим, что она нужна)

### Вариант А — оставить как есть, без альтернативы

Не делать ничего. Telegram — единственный путь к заказу.

- **Цена:** 0.
- **Риск:** покупатели без Telegram (или не желающие его ставить/давать
  боту доступ) не могут оформить заказ вообще, уходят. Неизвестная доля
  аудитории региона (СКФО, по `docs/CUSTOMER_FEATURES_SKFO.md`, если там
  есть данные про проникновение Telegram — не проверял, стоит свериться
  перед решением).
- **Риск ложных заявок:** нулевой — подтверждение уже есть у каждого
  заказа.

### Вариант B — SMS-код (платный)

Подтверждение кодом на любой номер через SMS-провайдера (SMS.ru/SMSC.ru
и т.п., см. обсуждение раньше в сессии — бесплатных нет).

- **Цена:** ~1.5-3₽ за SMS плюс абонплата/минимальное пополнение у
  большинства провайдеров. При пилотных объёмах (единицы-десятки заказов в
  день на первых порах) — копейки, но это первая постоянная денежная
  статья на стороне владельца платформы (ВайСклад), а не магазина —
  нужно решить, кто платит и как включать в тарификацию.
- **Риск:** технический — нужен реальный SMS-шлюз, обработка недоставки,
  ретраи, лимит попыток (защита от накрутки чужого баланса перебором
  номеров).
- **Плюс:** закрывает и просмотр статистики использования Telegram —
  не зависит от того, установлен ли у покупателя мессенджер вообще.

### Вариант C — ручное подтверждение магазином (без кода вообще)

Покупатель указывает номер без всякого автоматического подтверждения;
владелец магазина видит в заявке бейдж «номер не подтверждён» и сам
решает: позвонить и уточнить, или просто обработать как есть (это уже
частично то же самое, что было в v2, но БЕЗ блокировки заказа — просто
информационный сигнал, не стена).

- **Цена:** 0 разработки сверх бейджа + поля `phone_verified`.
- **Риск ложных заявок:** реальный. Любой может ввести чужой номер и
  оформить заказ на него — если оплата при получении (судя по
  `PaymentMethod`/`Оплата при получении`, это основной сценарий у
  пилотных магазинов, см. project_reviews_rating память), ложная заявка —
  это потраченное время владельца на сборку/подготовку товара, который
  никто не заберёт, и человек, чей номер использовали без спроса, может
  получить неожиданный звонок/сообщение от незнакомого магазина. Это
  довольно ощутимая цена для маленького пилотного магазина, где каждая
  заявка на счету.
- **Смягчение:** можно ограничить это конкретным сценарием — например,
  разрешить неподтверждённые заявки только с самовывозом (без предоплаты,
  без обязательства курьера ехать), но это усложняет модель и требует
  отдельного решения про самовывоз/доставку, которого сейчас нет как
  явного различения на этом уровне — не проверял, различает ли текущий
  `StorefrontRequest` способ получения на этом этапе.

### Вариант D — звонок с кодом (voice call)

Как SMS, но робот-звонок с озвученным кодом вместо SMS.

- **Цена:** обычно дешевле SMS в РФ, но всё ещё платно, тот же класс
  провайдеров.
- Не рассматривал детально — упоминаю как менее очевидную альтернативу B,
  не более.
