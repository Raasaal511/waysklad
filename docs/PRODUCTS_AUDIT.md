# Аудит вкладки «Товары» — backend vs frontend

Дата среза: 2026-08-11, обновлено 2026-08-12. Разовый аудит после переделки страницы
«Товары» (плитки, `ProductDetailCard`, импорт/экспорт xlsx/csv/pdf, фото WebP
thumb+full, история изменений). Задача: свести, что из backend-функциональности
модуля `products` не используется или используется не полностью во фронтенде,
и что стоит доделать.

Формат находок — как в `docs/sessions/NEXT_STAGES_PROMPT.md`: `⚠️` значит backend
готов и протестирован, доделка чисто фронтовая.

**Статус на 2026-08-12: находки №1–5 закрыты** (пагинация с серверной фильтрацией/
сортировкой, поиск по штрихкоду в общем списке, форма создания единицы измерения,
рекурсивное дерево категорий). №6–9 остаются открытыми — см. раздел 4.

## 2. Поля моделей vs UI

| Модель | Поле | Backend | UI |
|---|---|---|---|
| `Product` | все основные поля | ✅ | ✅ читаются и редактируются |
| `ProductVariant.barcode` | штрихкод варианта | ✅ полностью (валидация уникальности, сохранение) | **Ввод убран сознательно** — в прошлой сессии по фидбеку «зачем тут 2 штрихкода» поле удалили из формы варианта, оставив только штрихкод товара. В карточке штрихкод варианта — read-only. Компромисс: для одежды со сканированием размера/цвета на кассе это может понадобиться обратно — см. находку №4 |
| `Category.parent_id` | иерархия категорий | ✅ не ограничивает глубину | ✅ (с 2026-08-12) `categoryOptions()` строит дерево рекурсивно, произвольная глубина — находка №5 |
| `ProductModel.is_active` | soft-delete флаг | Есть в БД и фильтруется в `search()`, но **никогда не устанавливается в `False`** ни одним use case | Нет ни в UI, ни в API — заготовка без реализации архивации/удаления товара |

## 3. Права — сверка гранулярности

`backend/app/domain/identity/permissions.py`:

| Право | Роли | Проверяется реально |
|---|---|---|
| `PRODUCTS_MANAGE` | manager, owner | ✅ во всех write use case (`create_product.py:38`, `update_product.py:41`, `create_category.py:20`, `create_unit.py:22`, `import_excel.py:46`, `set_product_photo.py:23`) |
| `PRODUCTS_VIEW` | все роли | ⚠️ **нигде не enforced** — ни один GET в `products/router.py` не проверяет это право (роутер без `dependencies=[require_permission(...)]`). Сейчас безопасно (у всех ролей есть), но `docs/API_ROUTES.md` заявляет это право как требование — несоответствие документации коду |
| `PURCHASE_PRICES_VIEW` | storekeeper, analyst, manager, owner (у seller нет) | ✅ корректно — сервер физически не отдаёт `purchase_price`/`margin`, если права нет (`ShowPurchaseDep`, `schemas.py:177-178`) |

Фронт (`canManage = user?.role === 'owner' || 'manager'`, `ProductsPage.tsx:104`) 1:1
совпадает с бэкендовым `PRODUCTS_MANAGE`. Расхождений в гранулярности нет.

## 4. Находки

### Критично

**№1 — ✅ ЗАКРЫТО (2026-08-12) — лимит 50 товаров без пагинации.**
Было: `search()` всегда `.limit(50)`, без `offset`/курсора. Стало:
`IProductRepository.search(query, limit, offset, category_id, sort)` возвращает
`tuple[list[Product], int]` (список страницы + общее количество, честный
`SELECT count(*)` тем же фильтром), `search_all()` — отдельный метод без лимита
для экспорта (`_load_export_data` теперь зовёт его, а не `search("")`).
`GET /products` принимает `limit`/`offset`/`category_id`/`sort`, отдаёт
`X-Total-Count`. Фронт (`ProductsPage.tsx`) грузит страницами по 50 с кнопкой
«Показать ещё», категория и сортировка (кроме «по остатку») теперь считаются
на сервере по всему каталогу. Тесты: `test_products_pagination_via_api`,
`test_products_category_and_sort_via_api` (`backend/tests/test_api.py`).

**№2 — ✅ ЗАКРЫТО (2026-08-12) — поиск по штрихкоду не работал в общем списке.**
`search()`/`search_all()` теперь ищут и по `barcode ILIKE`, не только по
name/sku (`catalog.py` `_search_filter`). Отдельный поход на фронт к
`getByBarcode` не понадобился — работает через тот же общий поиск. Тест:
`test_products_search_by_barcode_via_api`.

### Полезно

**№3 — ✅ ЗАКРЫТО (2026-08-12) — нет UI для создания единицы измерения.**
Добавлен `QuickNewUnitForm` (по аналогии с `QuickNewCategoryForm`) — код,
название, флаг «допускает дробное количество», кнопка «+» рядом с Select
единицы измерения в `ProductForm`.

**№4 — штрихкод варианта не редактируется через UI (см. п.2 таблицы полей).**
Не трогали в этом заходе — сознательное решение прошлой сессии, а не забытый
пробел. Если для одежды понадобится сканировать конкретный размер/цвет на
кассе отдельно от штрихкода товара, потребуется вернуть поле в форму варианта.

**№5 — ✅ ЗАКРЫТО (2026-08-12) — категории только 2 уровня в UI.**
`categoryOptions()` переписан на рекурсивный обход произвольной глубины
(с защитой от циклов через `visited`), отступ `— ` умножается на глубину.

**№6 — нет агрегированного индикатора низкого остатка на уровне страницы.**
Есть только пометка на отдельной плитке (`product-tile-stock-low`). Счётчика
«N товаров с низким остатком» в шапке списка нет (аналитика по мёртвому
остатку — отдельно и правильно, в `AnalyticsPage`, дублировать не нужно).

**№7 — `GET /products/{id}` не используется отдельно.**
`ProductDetailCard` берёт товар из уже загруженного списка (пропом), не делает
собственный запрос. Открытая надолго карточка не увидит изменения, внесённые
в другой вкладке/другим сотрудником, без полной перезагрузки списка.

### Опционально

**№8 — валидация формата штрихкода только на бэкенде.**
Regex `^[A-Z0-9\-]{4,32}$` (`domain/catalog/barcode.py:7`) не продублирован на
фронте — ошибка формата видна только после отправки формы.

**№9 — `docs/API_ROUTES.md` устарел для модуля Products.**
Указано 9 путей, реально — 15 (нет `categories` GET/POST, `{id}/history`,
трёх export-путей). Указанный доступ `PRODUCTS_VIEW` на GET не подтверждается
кодом (см. находку в разделе 3). Стоит поправить при следующем ревью документации.

варианты/история), расширенная `ProductForm` (категория/фото/варианты),

фильтры/сортировка (№1)**, **поиск по штрихкоду (№2)**, **форма единицы
измерения (№3)**, **рекурсивное дерево категорий (№5)**.

Осталось (не входило в объём этого захода — пункты 1–4 исходного списка,
№6–9 сознательно отложены):

1. Опционально: счётчик низкого остатка в шапке списка; `GET /products/{id}`
   для точечного обновления одной карточки без перезагрузки всего списка;
   решить, возвращать ли штрихкод варианта в форму (№4).
2. Обновить `docs/API_ROUTES.md` под актуальный список products-роутов (№9).
3. Валидация формата штрихкода на фронте до отправки формы (№8).

### Побочные изменения при реализации №1

- `entities/product/api.ts`: `listProducts()` сменил сигнатуру на объект
  параметров и возвращает `{ items, total }` вместо `Product[]` — ломающее
  изменение. Добавлена `listAllProducts(query)` (весь каталог без пагинации,
  `limit=1000`) для экранов, которым нужен полный список для выбора товара:
  `SalePage.tsx` (продажа), `OrdersPage.tsx` (заказ), `StockPage.tsx`/
  `WarehouseDetailPage.tsx` (приёмка/списание/перемещение) — все переведены
  на неё, иначе они бы так же уткнулись в лимит 50 при большом каталоге.
- `shared/api/client.ts`: добавлена `api.getWithTotal()` — читает заголовок
  `X-Total-Count`, не трогая обычный `api.get()`.
- Фильтр «Только в наличии» и сортировка «По остатку» остаются клиентскими
  (работают только над уже загруженной страницей) — осознанный компромисс,
  чтобы не тащить `stock_items` (модуль inventory) в catalog-репозиторий и
  не нарушать границы Clean Architecture. Категория и сортировка по
  названию/цене/марже — на сервере, работают по всему каталогу.
- Заодно: заглушка для карточек без фото на плитках (`ProductPhoto` в
  `shared/ui/`, переиспользована в `ProductsPage.tsx` и `SalePage.tsx`),
  логика «низкий остаток» вынесена в `isLowStock()` (`shared/lib/format.ts`)
  и исправлена — нулевой остаток подсвечивается всегда, не только когда
  задан `min_stock`.
