# Клиентские фичи по вкладкам — разбор рынка СКФО и рекомендации

**Дата:** 2026-08-12
**Задача:** не «что добавить в товарный учёт вообще», а что добавить **конкретно клиенту магазина**
(не владельцу) в каждой вкладке ВайСклада, чтобы продукт ощущался «удобным для покупателя», а не
только «удобным для бухгалтерии владельца». Второй слой — специфика рынка СКФО (Чечня, Дагестан,
Ингушетия, Кабардино-Балкария, Северная Осетия, Ставрополье): наличность и переводы вместо карт,
рассрочка без процентов как норма, WhatsApp/Instagram* как основной канал продаж, тейповая/тухумная
и соседская репутация как главный маркетинговый актив, недоверие к обезличенным сервисам.

Формат по каждой вкладке: **что делают конкуренты для конечного клиента → в чём разрыв с СКФО →
конкретная фича → сложность/вес.** В конце — сводная таблица приоритетов.

Документ — только план/идеи, без кода, по аналогии с `docs/COMPETITOR_MOYSKLAD_ANALYSIS.md`.

---

## 0. Почему это отдельный слой, а не то же самое, что анализ МойСклад

`COMPETITOR_MOYSKLAD_ANALYSIS.md` разбирает фичи **для владельца/продавца** — учёт, аналитика,
разграничение прав. Это внутренняя сторона прилавка. Здесь — **фичи для человека по ту сторону
прилавка**: покупателя, который получает квитанцию в WhatsApp, стоит в долговой книге, ждёт заказ
из Instagram*. МойСклад в принципе не решает эту сторону — у них нет клиентского интерфейса вообще,
их продукт целиком про учёт. Значит, конкурентов на эту фичу нужно искать не в товароучётных
системах, а там, где клиент реально что-то видит: маркетплейсы, CRM-боты, программы лояльности,
локальные сервисы доставки.

Ключевое ограничение, унаследованное из README §5.3: ВайСклад **не двигает деньги** — не касса, не
эквайринг. Значит, любая клиентская фича должна быть **информационной или коммуникационной**, а не
платёжной: клиент может *видеть* свой долг, *получить* квитанцию, *записаться* на статус заказа — но
не может провести оплату картой через приложение. Это единственная жёсткая граница, применённая
ниже ко всем разделам.

## 1. Вкладка «Продажи» (`/`)

### Что делают конкуренты для клиента
- Маркетплейсы (Wildberries, Ozon) — электронный чек, статус заказа push-уведомлением, история
  покупок в личном кабинете.
- Кассовые системы среднего бизнеса (Эвотор, Poster) — SMS/email с чеком и накопленными баллами.
- Локальные точки в СКФО в массе своей **не дают клиенту вообще ничего на руки**, кроме
  устной суммы и рукопожатия — чек на бумаге редкость даже там, где есть касса, потому что касса
  часто пробивает по минимуму «для галочки», а не для клиента.

### Разрыв в СКФО
У ВайСклада уже есть квитанция-PDF в WhatsApp (README §5.1) — это уже впереди среднего локального
магазина. Но она разовая и безымянная: отправил — забыл, второй раз для того же клиента считать
заново. Нет ощущения «у меня есть история покупок в этом магазине», которое создаёт лояльность.

### Фича: привязка продажи к клиенту как опция в один тап
Сейчас продажа может быть анонимной (просто сумма) или в долг (обязательно привязана к клиенту).
Добавить: **необязательную** привязку к клиенту и для обычной (не долговой) продажи — тот же
`Select` клиента, что уже есть в форме долга, но без обязательности. Это не новая сущность, просто
снятие ограничения "клиент обязателен только если оплата = долг" на уровне формы, если он уже
выбран из справочника (карточка клиента уже существует — см. §5). Даёт владельцу нового вида
данные почти бесплатно: «Айна — постоянный клиент, 8 покупок за 3 месяца» — то, чем локальный
магазин может козырнуть перед клиентом лично («О, вы у нас уже 5-й раз!»), что в культуре СКФО,
где личное отношение решает больше рекламы, работает сильнее любой формальной программы лояльности.

**Сложность:** низкая — поле уже есть в форме долга, нужно вынести его в общую форму продажи и
снять условие обязательности.

## 2. Вкладка «Товары» (`/products`)

### Что делают конкуренты для клиента
- У всех крупных ритейлеров и маркетплейсов — публичный каталог с ценами, доступный до похода в
  магазин, с фото и остатком «в наличии/нет».
- Локальные Instagram*-магазины в СКФО (одежда, парфюмерия, кондитерка) сейчас держат каталог
  **вручную дублированным**: карточка товара делается один раз в тетради/голове хозяина, а на
  витрину в Instagram* фото и цена выкладываются отдельно, вручную, с рассинхроном (товар давно
  продан, а пост в директе всё ещё висит).

### Разрыв в СКФО
Ровно то, что уже зафиксировано в README §5.2 как «вторая очередь» — **публичная витрина-каталог
с остатками** — не абстрактная идея, а прямое попадание в самую массовую боль региона: магазины
одежды/парфюмерии/кондитерки в ЧР, Дагестане, Ингушетии торгуют **в первую очередь через
Instagram* и WhatsApp**, и у них систематически нет единого источника правды «что сейчас есть в
наличии», кроме головы продавца.

### Фича: публичная ссылка на витрину товара (уже запланировано, поднять приоритет)
Минимальная версия — не полноценный интернет-магазин с оформлением заказа, а **read-only страница**
по прямой ссылке (`waysklad.ru/s/<tenant>/p/<product_id>` или на весь каталог `.../s/<tenant>`):
фото, название, цена, «в наличии»/«нет в наличии» (без точного числа — чтобы не палить объём
поставщику-конкуренту), кнопка «Написать в WhatsApp» с уже подставленным текстом («Здравствуйте,
интересует [товар]»). Владелец вставляет одну ссылку в шапку Instagram* вместо ежедневного ручного
дублирования постов. Технически — это уже существующие данные (`Product`, `photo`, остаток),
просто новый публичный (без авторизации) read-only эндпоинт и одна статическая страница; не
требует корзины, оплаты или личного кабинета клиента — остаётся в рамках «не двигаем деньги».

**Сложность:** средняя — новый публичный роут без токена (внимательно с tenant-изоляцией и
rate-limit, это первая полностью открытая наружу поверхность), простая статическая страница на
фронте. Прямое попадание в нишу «Одежда/Instagram*-магазины» из README §4 — уже топ-1 по важности
в этой нише.

### Фича: QR/ссылка на бирке товара → карточка с составом/уходом (для одежды и продуктов)
Более лёгкий вариант той же идеи specifically под нишу одежды и кондитерки: на бирке/стикере —
QR на карточку **одного** товара с составом ткани/сроком годности/инструкцией по уходу. Дешевле в
реализации, чем полноценная витрина (не нужен список/поиск, только один товар по id), но не
самостоятельная замена ей — это скорее дополнение поверх той же публичной страницы товара.

**Сложность:** низкая, если делать поверх публичной страницы товара выше (переиспользует тот же
эндпоинт); отдельно от неё — не имеет смысла делать.

## 3. Вкладка «Остатки» (`/stock`)

### Что делают конкуренты для клиента
Складской модуль в принципе не клиентский раздел ни у одного конкурента — это исключительно
внутренний инструмент. Wildberries/Ozon показывают клиенту только «осталось 2 шт» на карточке
товара как приём подгонки к покупке.

### Разрыв в СКФО
Разрыва в смысле «клиент хочет видеть остатки склада» нет и не должно быть — это осознанно
внутренний раздел. Единственная клиентская проекция остатков — та же публичная витрина из §2
(«в наличии / нет в наличии»), это не отдельная фича вкладки «Остатки», а прямое следствие
того, что уже предложено там.

### Вывод
**Ничего отдельного не делать.** Специально фиксируем это, чтобы не пытаться придумать
клиентскую фичу там, где её не должно быть — сама вкладка и её данные полностью закрыты от
клиента и должны такими оставаться (закупочные объёмы — чувствительная для локального рынка
информация, конкуренты не должны её видеть).

## 4. Вкладка «Заказы» (`/orders`)

### Что делают конкуренты для клиента
- Маркетплейсы и службы доставки (Ozon, СДЭК, Яндекс.Доставка) — статус заказа виден клиенту в
  реальном времени: «принят → собран → в пути → доставлен», без звонков менеджеру.
- Локальные Instagram*-магазины и кондитерские в СКФО сейчас закрывают этот же вопрос **звонками
  и голосовыми в WhatsApp**: «а мой заказ готов?» — постоянный поток отвлекающих сообщений
  продавцу, особенно у кондитерских (README: «Сладкий дом» — торты на заказ) и швейных цехов, где
  цикл выполнения заказа занимает дни, а не минуты.

### Разрыв в СКФО
Прямое попадание: `OrderStatus` (new → in_progress → ready → issued) уже есть в модели данных —
это ровно то состояние, которое клиент маркетплейса видит на каждом шагу, а клиент локального
кондитерского цеха/швейной мастерской/магазина одежды не видит вообще, потому что статус меняется
только во внутреннем интерфейсе продавца.

### Фича: статус заказа клиенту одной кнопкой в WhatsApp
Не push-уведомления и не личный кабинет (это уже уровень отдельного мобильного приложения) — а
минимальный паттерн, уже освоенный в квитанциях: кнопка «Сообщить клиенту статус» рядом с каждым
переходом статуса в `OrdersPage`, которая формирует `wa.me`-ссылку с готовым текстом («Ваш заказ
№42 готов, можно забирать») на телефон клиента, уже привязанного к заказу. Это не автоматическая
рассылка (сервер не хранит и не использует WhatsApp Business API — остаётся тем же ручным
паттерном, что уже работает для квитанций), просто убирает продавцу необходимость печатать текст
руками при каждой смене статуса.

**Сложность:** очень низкая — переиспользует уже существующий `wa.me`-паттерн квитанций, только с
другим шаблоном текста и другой точкой вызова (кнопка в `OrdersPage.tsx` рядом с кнопкой смены
статуса).

### Фича (опционально, вторая очередь): страница статуса заказа по ссылке — без звонка
Более развитая версия той же идеи: `wa.me`-ссылка ведёт не просто на сообщение, а на короткую
read-only страницу «Заказ №42 — Готов, можно забирать до 18:00» (публичная, без авторизации, по
непредсказуемому id/токену в URL, аналогично билетам на мероприятия). Клиент добавляет её в
закладки и обновляет сам, без сообщения продавцу. Оправдана только если пилот покажет, что
кондитерским/ателье регулярно пишут «а что там с заказом» несмотря на первую фичу.

**Сложность:** средняя — тот же публичный слой без авторизации, что и витрина товара в §2, можно
переиспользовать инфраструктуру (публичный роут, rate-limit, отсутствие чувствительных данных).

## 5. Вкладка «Долги» (`/debts`)

### Что делают конкуренты для клиента
- Микрофинансовые/банковские приложения — заёмщик видит график платежей, остаток долга, дату
  следующего платежа в личном кабинете.
- «Долговые тетради» в локальных магазинах СКФО — по определению видны **только продавцу**;
  клиент узнаёт свою сумму долга только когда переспросит лично, что при частичных погашениях в
  течение месяцев регулярно приводит к спорам («я же уже отдавал часть!»).

### Разрыв в СКФО — это самый большой разрыв во всём документе
Долговая книга — киллер-фича №1 продукта (README §5.1) именно потому, что беспроцентная
рассрочка/отпуск в долг — норма делового оборота в регионе (стройматериалы бригадам, продукты
соседям, одежда постоянным клиентам). Но сейчас это **односторонняя** прозрачность: видит только
владелец. Ровно та точка, где спор «я же отдавал!» возникает чаще всего — и ровно то место, где
локальная культура (пересчитывать при свидетелях, не доверять словам без бумаги/записи) требует
не бухгалтерской точности, а **предъявляемого клиенту доказательства**.

### Фича: «Показать историю долга» — ссылка клиенту с историей начислений/погашений
По аналогии со статусом заказа: кнопка в карточке долга «Отправить клиенту» → `wa.me`-ссылка с
текстом-выпиской («Ваш долг в [магазин]: было 5000₽, оплачено 2000₽ 14.07, оплачено 1500₽ 02.08,
остаток 1500₽») — формируется из уже существующей истории частичных погашений (`Debt` +
операции), просто рендерится в текст сообщения. Это прямое закрытие самого частого бытового спора
в долговой торговле региона, и что критично — это **укрепляет доверие к владельцу магазина**, а
не только к продукту: он выглядит организованным и честным перед клиентом, что в культуре, где
репутация продавца среди соседей/тухума решает больше рекламы, стоит больше, чем кажется на
первый взгляд по объёму кода.

**Сложность:** низкая — тот же `wa.me`-паттерн, данные уже есть (`Debt`, история погашений уже
хранится и уже показывается владельцу в UI), нужно только собрать текстовый шаблон и кнопку.

### Фича (опционально): публичная страница «Мой долг» по ссылке
Аналогично статусу заказа — read-only страница по токену вместо разового текстового сообщения,
обновляется сама при следующем погашении, клиент может открыть в любой момент без нового
сообщения продавцу. Та же публичная инфраструктура, что и §2/§4 — имеет смысл делать все три
публичные read-only страницы (товар/заказ/долг) одним слоем, а не тремя отдельными.

**Сложность:** средняя, при уже построенной инфраструктуре публичных страниц — низкая (переиспользование).

## 6. Вкладка «Клиенты» (`/clients`)

### Что делают конкуренты для клиента
- Программы лояльности сетевого ритейла — бонусные баллы, скидка постоянного клиента, видимая
  клиенту через карту/приложение.
- У локального магазина в СКФО «постоянный клиент» — статус, который **знает продавец лично**, но
  никак не отражён в системе и не поощряется формально, кроме личного жеста («сделаю скидку, ты
  свой»).

### Разрыв в СКФО
Полноценная программа лояльности (баллы, накопительные скидки, автоматическое применение) — это
уже шаг в сторону кассовой/платёжной механики, которую продукт осознанно не делает (§5.3: не
двигаем деньги, скидка — не автоматическое списание бонусов, а решение продавца в моменте). Но
**видимость** статуса клиента — это чисто информационная фича, не платёжная, и она уже почти
готова из данных, которые собирает §1.

### Фича: бейдж «Постоянный клиент» на карточке — видимый продавцу, не клиенту
Не «клиентская» фича в смысле «клиент это видит», а фича **для клиента через продавца**: в
карточке клиента (после реализации §9.2 из `COMPETITOR_MOYSKLAD_ANALYSIS.md` — единой истории
покупок/долгов/заказов) — простой подсчёт «8 покупок за 3 месяца, средний чек 1200₽» и бейдж
«Постоянный клиент» при превышении порога (например, 5+ покупок). Продавец видит это при
следующей продаже и может лично предложить скидку/бонус — то есть технология лишь **подсвечивает
повод для персонального жеста**, который в культуре региона работает сильнее автоматической
скидки. Прямая зависимость от §9.2 «единая карточка истории клиента» из анализа МойСклад — имеет
смысл делать вместе.

**Сложность:** низкая при уже сделанной единой карточке клиента (§9.2 предыдущего документа) —
это просто счётчик и условный бейдж поверх уже агрегированных данных.

## 7. Вкладка «Аналитика» (`/analytics`)

### Что делают конкуренты для клиента
Аналитика по определению внутренний инструмент владельца — ни один конкурент (МойСклад,
маркетплейсы) не показывает аналитику покупателю. Здесь конкурентов на «клиентскую фичу» просто
не существует по построению раздела.

### Вывод
**Ничего клиентского здесь не делать** — так же как и с «Остатками» (§3), это осознанно закрытый
от клиента раздел, и попытка притянуть сюда клиентскую фичу была бы искусственной. Единственное
касание клиента через аналитику — косвенное, через «постоянного клиента» в §6, которое уже
отнесено туда, а не сюда.

## 8. Вкладка «Сотрудники» (`/employees`) и профиль

здесь нет и не должно быть точки соприкосновения. Не рассматриваем.

## 9. Сквозная идея, не привязанная к одной вкладке: единый номер бренда в WhatsApp

Отдельно от разбора по вкладкам — наблюдение, которое всплывает в каждом разделе (продажи,
заказы, долги): весь клиентский контакт идёт через `wa.me`-ссылку на **личный номер продавца**,
который менялся бы при уходе сотрудника. Это не фича экрана, а вопрос конфигурации: в профиле
магазина (`ShopContext`) уже должен быть контакт для приёма звонков — стоит убедиться, что все
`wa.me`-ссылки (существующая в квитанциях + три новые из §1/§4/§5 выше) берут номер из **профиля
магазина**, а не из личного номера текущего залогиненного продавца, если это ещё не так. Это не
новая фича, а требование к уже спланированным — чтобы уходящий продавец не забирал с собой канал
связи с постоянными клиентами магазина.

**Действие:** проверить при реализации §1/§4/§5, откуда берётся номер для `wa.me`-ссылки — если
из `user.phone` текущего сотрудника, а не из `shop.contact_phone`, поправить до того, как фичи
разъедутся по трём местам кода.

### Как читать таблицу
Три фичи с высоким приоритетом и низкой сложностью (долг в WhatsApp, статус заказа в WhatsApp,
привязка клиента к продаже) — это одна волна работы: все три расширяют уже существующий
`wa.me`-паттерн новыми текстовыми шаблонами поверх данных, которые уже хранятся. Разумно делать
их вместе, одной сессией, вместе с проверкой источника номера (иначе три новых кнопки унаследуют
один и тот же баг). Публичная витрина товара — отдельная, более весомая работа (первая открытая
наружу поверхность в проекте), но она уже согласована как направление в README §5.2 и здесь
получает независимое подтверждение: это единственная фича из всего разбора, которая закрывает
буквально самую массовую операционную боль ниши «Instagram*-магазины» (§4 README) — ручной
рассинхрон каталога и переписки.
