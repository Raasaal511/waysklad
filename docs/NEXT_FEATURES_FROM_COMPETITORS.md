## 1. Описание товара + автогенерация через ИИ — AI-часть УБРАНА (2026-09-16)

`Product.description` осталось обычным текстовым полем (владелец заполняет
руками) — это часть живёт нормально, задел под витрину/отзывы. Но сама
AI-генерация (`POST /products/{id}/description/generate`, Anthropic Claude)
удалена из кода 2026-09-16 по решению пользователя: «рано». Если понадобится
вернуть — вся конструкция описана ниже в исходном плане, код просто удалён
(`IDescriptionGenerator`, `GenerateProductDescriptionUseCase`,
`AnthropicDescriptionGenerator`, `ANTHROPIC_API_KEY`/`ANTHROPIC_MODEL` в
конфиге, пакет `anthropic` в requirements.txt) — писать заново по этому же
плану, не с нуля придумывать архитектуру.

Пользователь подтвердил (исходно): у `Product` сейчас нет поля `description` вообще
(только `name`, `sku`, `min_stock` и т.д. — см. `app/domain/catalog/entities.py:51`).
Решено:

- Добавить `Product.description: str = ""` — обычное текстовое поле, владелец
  может заполнить/поправить руками как любое другое поле товара.
- Отдельная кнопка/эндпоинт **«сгенерировать через ИИ»** — не сохраняет
  автоматически, а только возвращает предложенный текст для предпросмотра;
  сохранение — обычным `PUT /products/{id}` с уже отредактированным текстом.
- **Провайдер: Anthropic Claude.** Для короткой генерации (1-3 предложения по
  названию+категории) — модель `claude-haiku-4-5` (самая дешёвая: $1/$5 за 1M
  токенов, более чем достаточно для такой простой задачи; не обязательно
  Opus). Пакет `anthropic` для Python, пока не установлен в проекте.
- **Начать только с текста** (название + категория), без фото — vision-вызов
  дороже, можно добавить отдельным шагом позже, если текстового результата
  окажется недостаточно.
- Новая конфигурация потребуется: `ANTHROPIC_API_KEY` в `Settings`
  (`app/infrastructure/config.py`, по тому же паттерну, что
  `telegram_bot_token`) — до сих пор в проекте не было ни одной LLM-интеграции.
- Архитектурно: домен-порт `IDescriptionGenerator` (Protocol, аналог
  `INotifier`) + инфраструктурная реализация через Anthropic SDK + отдельный
  use case (`GenerateProductDescriptionUseCase`), который только читает и
  возвращает текст, не трогает `uow.commit()`.

## 2. Аналитика: «упущенные продажи» (из WB "Inventory History")

Пользователь: **пункт 5 из списка, «можно сделать, дополнив от нашего»**.

Идея WB: отчёт показывает, сколько заказов клиенты могли бы сделать, если бы
товар был в наличии — считается по факту нулевого/недостаточного остатка при
наличии спроса. Прямая противоположность нашему текущему
"Рекомендации к дозаказу" (`app/application/analytics/restock_recommendations.py`)
— тот ловит "заканчивается, пока ещё есть", это — "уже кончилось, теряем
продажи".

**Как дополнить под наш масштаб** (не решено окончательно, обсудить перед
реализацией):
- Источник данных: заявки на витрине (`StorefrontRequest`), где товара не
  хватило на складе на момент заявки — уже частично есть флаг
  `insufficient_stock_at_request` (см. `2026-09-07_storefront_request_reservation_flags.py`)
  — вероятно, можно агрегировать из него, не заводя новую сущность.
- Для обычных продаж (не через витрину) "упущенная продажа" не наблюдаема
  напрямую — покупатель, которому продавец сказал "закончилось", нигде не
  фиксируется, если только это не заявка. Обсудить, ограничиваемся ли только
  витриной, или это неприменимо к офлайн-продажам вовсе.

## 5. Отзывы и рейтинг (из wikkeo) — РЕАЛИЗОВАНО (2026-09-16)

См. `frontend/api_docs/reviews.md` и `docs/sessions/session-31-reviews-and-rating.md`
для полного описания реализации. Ниже — исходный план для истории.

Пользователь подтвердил к реализации — самая крупная фича из всего списка,
новый домен, не просто поле.

**Модель доступа — предложение, не решено окончательно:** привязать отзыв к
`StorefrontRequest` в статусе `ACCEPTED` (сделка подтверждена владельцем),
доступ на отправку — тем же `access_token`, что уже используется для чата по
заявке (`app/domain/storefront/entities.py:41-44` — тот же непредсказуемый
токен, покупатель уже хранит его в localStorage после создания заявки). Это
автоматически защищает от анонимного спама без отдельной модерационной
очереди на старте: оставить отзыв может только тот, у кого есть токен принятой
заявки.

**Новая сущность (черновой набросок, уточнить перед реализацией):**
```
Review:
  id, tenant_id, product_id, storefront_request_id,
  rating: int (1-5), text: str, photo: str | None,
  author_name: str,       # из StorefrontRequest.customer_name, не отдельный логин
  created_at
```

**Публичные эндпоинты (черновой набросок):**
- `POST /storefront/requests/{request_id}/reviews` (по `access_token`,
  аналогично `POST /requests/chat`) — создать отзыв, только если заявка
  `ACCEPTED` и отзыва по ней ещё не было (один отзыв на заявку).
- `GET /storefront/{slug}/products/{product_id}/reviews` — список + агрегат
  (средний рейтинг, гистограмма по 5 звёздам — как у wikkeo) для карточки
  товара на витрине.

**Не решено, обсудить перед реализацией:**
- Нужна ли модерация владельцем перед публикацией (скрыть/удалить неудачный
  отзыв) — вероятно да, хотя бы кнопка «скрыть».
- Ответ владельца на отзыв (как у wikkeo) — отдельная фича сверху, не в
  первой итерации.

**Дополнение по странице магазина `/store/onshop` (не только карточка товара):**
у wikkeo рейтинг существует на двух уровнях — по конкретному товару (в его
карточке) И по магазину в целом отдельной вкладкой «Отзывы» на странице
магазина, с отдельными агрегированными цифрами в шапке: рейтинг (5.0), число
подписчиков (2.4k), число заказов (13000+), **скорость отправки** («~2 часа»),
**% выполненных заказов** («95%», видимо доля принятых/не отменённых заявок).
У нас уже есть аналог «страницы магазина» — сама витрина `/{slug}`; агрегат
рейтинга по tenant'у в целом — это `avg(Review.rating)` по всем отзывам всех
товаров этого tenant'а, никакой новой сущности не требует поверх уже описанной
`Review`. «Скорость отправки»/«% выполненных» у нас можно было бы посчитать
из `StorefrontRequest` (время от `created_at` до `accept`/`reject`, доля
`ACCEPTED` от всех) — отдельно решить, интересно ли это владельцу вообще, не
факт что нужно.

## 6. Счётчики просмотров и продаж на карточке товара

Пользователь подтвердил к реализации.

- **`sold_count`** — не новое поле, агрегат по существующей истории продаж
  (`uow.sales`/`uow.analytics`) за всё время или за период, посчитанный внутри
  `GetStorefrontProductUseCase`/`GetStorefrontCatalogUseCase`. Дёшево, без
  новой таблицы.
- **`views_count`** — требует инкремента на каждый публичный `GET` карточки
  товара. Писать в Postgres на каждый просмотр — лишняя нагрузка на таблицу
  под высокий read-трафик; правильнее копить в Redis (тот же Redis, что уже
  используется для кеша витрины и rate-limit — `CACHE_REDIS_URL`) простым
  `INCR` по ключу `views:{tenant_id}:{product_id}`, точность до дня не нужна.
  Не решено: нужен ли период (просмотры «за 90 дней», как у wikkeo) —
  проще для старта показывать общий счётчик без оконного среза.
- **Публичность на самой витрине** (не только владельцу в аналитике) — под
  вопросом, тот же конкурентный риск, что с точными остатками. Предварительно:
  можно показывать `sold_count` публично (это то же самое, что бейдж
  «Продано: N» у wikkeo, не палит ничего чувствительного), а `views_count`
  оставить только владельцу в аналитике.

## 7. Фильтры каталога витрины (со страницы `/store/onshop`)

Новая находка, не обсуждалась раньше — **пока не подтверждена к реализации**,
только зафиксирована для следующего разбора. У wikkeo боковая панель фильтров
каталога магазина включает: формат товара (опт/дропшиппинг — неприменимо к
нам), скидка (по размеру/по сумме), местонахождение товара (по городу),
категория, способ оплаты, **«товары от N звёзд и выше»** (фильтр по минимальному
рейтингу — требует пункта 5 выше), **«бесплатная доставка»**, **«ликвидация»**
(распродажа/уценка — булев чекбокс).

Из этого набора применимо к нашей витрине уже сейчас, без новых сущностей:
- Фильтр по категории — уже есть.
- Фильтр «местонахождение» ≈ наш существующий `?warehouse_id=` — уже есть,
  просто не оформлен как фильтр в боковой панели на фронте (backend уже
  поддерживает).
- **Фильтр по минимальному рейтингу — РЕАЛИЗОВАНО (2026-09-16).**
  `?min_rating=1..5` добавлен и в `GET /storefront/{slug}` (каталог одного
  магазина), и в `GET /marketplace/products` (общий каталог платформы) —
  фильтрация на уровне SQL (correlated subquery со средним рейтингом,
  `app/infrastructure/db/filtering/product_filter.py` и
  `app/infrastructure/db/repositories/marketplace.py`), не постфактум в
  Python — иначе пагинация/`total` были бы неверными. Товар без единого
  отзыва не проходит фильтр даже при `min_rating=1` (NULL не удовлетворяет
  `>=` в SQL — осознанно, «нет отзывов» ≠ «плохой рейтинг»). Контракт для
  фронта обновлён в `storefront_extras.md`/`marketplace.md`.

Требует новых данных (не решено, обсуждать отдельно):
- «Скидка» как отдельный признак товара (у нас цена одна, `retail_price`, без
  понятия «старая цена/скидка от неё») — если вводить, это новое поле
  `Product` (`sale_price`? `discount_percent`?) и логика зачёркнутой цены.
- «Бесплатная доставка», «ликвидация» — булевы флаги, которых сейчас у
  `Product`/`Warehouse` нет.

## Дизайн/фронтенд — важное ограничение

Пользователь попросил «взять дизайн и бек у них» — но текущий режим работы
(с 2026-09-02) строго backend-only: фронтенд ведёт свой отдельный
разработчик, я не трогаю UI/вёрстку/дизайн-систему. Все пункты выше —
исключительно backend-контракты (данные, эндпоинты). Визуальная реализация
карточки товара, галереи отзывов, счётчиков и т.п. — задача фронтенд-команды;
с моей стороны это фиксируется как контракт для фронта (см. соответствующий
файл в `frontend/api_docs/`), не как дизайн-макет.
