**Дата:** 2026-08-12

**Статус: рекомендации реализованы (сессия 21, тот же день).** Итоговая реализация
использует список складов (`warehouse_assignments`, многие-ко-многим) вместо
одиночного `warehouse_id`, автоматически назначает единственный склад без
показа выбора в форме сотрудника, и добавляет `UpdateEmployeeUseCase` — то
есть пункты 1–4 рекомендации из раздела 5 учтены. См.
`docs/sessions/session-21-roles-warehouses-mvp-gaps.md`. Текст ниже оставлен
как есть — это снимок анализа на момент, когда функционала ещё не было в коде.

**Контекст.** Задача — оценить, насколько удобна модель «роль + обязательная привязка сотрудника к одному складу» для типичного случая целевой аудитории ВайСклад: «Магазин платьев Айна» с рынка Беркат — одна точка 4–6 кв.м, витрина = склад = касса, 1–3 человека персонала, часто сам владелец же и продавец.

**Важная оговорка по методу.** По условиям задачи предполагалось, что параллельно уже ведётся работа над обязательной привязкой сотрудника к одному складу (`warehouse_id` на `User`) и над сужением меню по ролям. Я прочитал фактическое состояние кода в текущей рабочей копии (`develop`, коммит `00c93fb`) и в обоих открытых git worktree (`agent-a0582fb0ae573a95c`, `agent-aed9783a478a0ddb8`) — оба чистые и совпадают с `develop`, никакой незакоммиченной работы над ролями/складами в них нет. Значит, ничего из описанного функционала («обязательный `warehouse_id` у сотрудника», «сужение меню по ролям под конкретный склад») **в код ещё не попало** — это само по себе первая находка, см. раздел 0. Весь дальнейший анализ построен на том, что есть в коде сейчас, с пометками, где придётся достраивать логику, а не просто её тюнинговать.

## 0. Фактическое состояние: обязательной привязки «сотрудник → один склад» пока нет

- `User` в `backend/app/domain/identity/entities.py:41-51` не имеет поля `warehouse_id`. Единственная связь склад↔пользователь — `Warehouse.assigned_user_ids: list[int]` (`entities.py:37`), то есть **многие-ко-многим**, и означает она не «сотрудник работает на складе», а «кладовщику разрешено проводить складские операции по этому складу» (докстринг там же: «owner/manager имеют доступ ко всем складам вне зависимости от списка»).
- Форма создания сотрудника (`frontend/src/pages/employees/EmployeesPage.tsx:109-167`, компонент `NewEmployeeForm`) содержит только Имя/Телефон/Пароль/Роль. Поля выбора склада нет вообще ни на фронте, ни в `CreateEmployeeCommand` (`backend/app/application/auth/create_employee.py:14-19`).
- Продавец на экране продажи (`frontend/src/pages/sales/SalePage.tsx`) сам выбирает склад из выпадающего списка (`warehouseId`, строка 546), по умолчанию берётся первый склад из списка (`SalePage.tsx:592`). Никакого ограничения «этому продавцу доступен только его склад» не применяется.
- Единственное место, где связь пользователь↔склад вообще на что-то влияет — кладовщик (`Role.STOREKEEPER`): в `backend/app/presentation/inventory/router.py:49-56` и `:59-70` для роли storekeeper список складов и остатков фильтруется через `list_for_user`/`assigned_user_ids`. Для owner/manager/seller фильтрации нет.
- `RegisterShopUseCase` (`backend/app/application/auth/register_shop.py:54`) при регистрации магазина сам создаёт один склад «Основной склад» — это уже готовый, работающий кусок «нулевого трения»: владельцу ничего выбирать не надо, склад появляется автоматически.

Вывод: пункты 1–4 ниже я разбираю как **риски будущей реализации**, а не как разбор существующего UX (существующего в этой части просто нет). Даю рекомендации на входе в проектирование, а не пост-фактум критику готового экрана.

## 1. Сценарий «один склад = один магазин»: нужна ли обязательная привязка вообще

Факты:
- Регистрация магазина уже даёт владельцу ровно один склад бесплатно, без единого клика (`register_shop.py:54`). Это ровно то, что нужно «Айне»: она регистрируется и у неё уже есть «Основной склад».
- Если добавить обязательный `warehouse_id` в форму сотрудника (как описано в задаче), при **первом** сотруднике выбор тривиален — склад один, дропдаун с одним пунктом. Трения почти нет технически, но по ощущениям — лишний вопрос в форме, ответ на который всегда предопределён и неинформативен для пользователя («а зачем вы спрашиваете, у меня же один склад»).
- Реальное трение появляется не при первом сотруднике, а концептуально: форма показывает выбор там, где для 90%+ ЦА (по README, сегмент — 1 точка, будущий рост скорее через второй похожий магазин, чем через мультискладовую розницу) выбирать не из чего. Каждое лишнее поле в форме — это README-философия «проще калькулятора», которая явно нарушается, если поле всегда с одним и тем же ответом.

Вывод: обязательная привязка **сама по себе не создаёт многошаговый онбординг** (склад уже существует к моменту создания сотрудника — не нужно «сначала создать склад, потом сотрудника», это уже так по коду), но создаёт **бесполезный УФ-шаг** в самом частом случае (один склад). Правильная реализация — сделать поле складом условно видимым: если складов больше одного — показывать выбор; если один — привязывать автоматически и не показывать вообще (проверка `warehouses.length <= 1` уже используется в похожем месте фронта, например `SalePage.tsx:353` — `{warehouses.length > 1 && (...)}` для фильтра по складу в продажах, то есть паттерн «скрывать выбор при одном складе» уже есть в кодовой базе и его стоит просто повторно применить к форме сотрудника).

## 2. Сценарий «хозяин = сам продавец»

Факты:
- `Role.OWNER` имеет все права (`permissions.py:94`, `frozenset(Permission)`), включая `Permission.SALES_CREATE` — то есть owner физически может открыть экран продаж и продавать, отдельная роль seller ему для этого не нужна. `require(actor, Permission.SALES_CREATE)` в `create_sale.py:49` пройдёт для owner.
- `Sale.seller_id = actor.id` (`create_sale.py:76`) — значит, если продажу оформляет owner, она физически привяжется к owner как к продавцу. Это корректно с точки зрения данных.
- Проблема — с аналитикой «продажи по сотруднику»: я проверил весь `backend/app/application/analytics/` (`dashboard.py`, `top_products.py`, `dead_stock.py`) — **разреза по продавцу нет вообще**. `dashboard.py:9-33` отдаёт только периодные тоталы (`today/week/month`), без группировки по `seller_id`. `top_products.py` и `dead_stock.py` — про товары, не про людей. Значит, вопрос «имеет ли смысл заводить owner ещё и как seller ради отчёта по продавцу» пока снят сам собой: такого отчёта, ради которого стоило бы городить fake-сотрудника, просто нет в системе.
- Специфика ЦА («хозяин часто сам сидит за прилавком») в этом смысле уже обслужена лучше, чем можно было ожидать: owner — универсальная роль, включающая продавца, не требует второй учётки.

Вывод: сейчас никакого трения нет — owner может продавать под своей же учёткой. Риск появится только если в будущем добавят аналитику «продажи по сотруднику» и **не включат туда явно и owner** (например, если разрез будет фильтроваться по `role == seller`, а не по факту `seller_id` в проданных документах) — тогда владелец рискует «выпасть» из собственной отчётности. Рекомендация на будущее: если/когда появится разрез по продавцам, строить его от `Sale.seller_id` (кто фактически провёл продажу), а не от роли пользователя — тогда owner, торгующий за прилавком, попадёт в отчёт автоматически, без фейковой учётки.

## 3. Сценарий «родственник помогает то на одной точке, то на другой»

Факты:
- Модель `User` — один пользователь принадлежит одному `tenant_id` (`entities.py:50`, докстринг: «identity — единственный контекст, знающий о tenant»), и (по условиям задачи, ещё не реализовано) должен принадлежать одному `warehouse_id`. Это жёсткая модель 1 человек = 1 склад одномоментно.
- Текущий паттерн для похожей проблемы уже есть в коде — `Warehouse.assigned_user_ids: list[int]` (многие-ко-многим) для кладовщиков: один кладовщик может быть назначен на несколько складов одновременно (`set_warehouse_assignments` меняет список целиком, `IWarehouseRepository.set_assignments` в `repository.py:32-34`). Это ровно тот механизм, который решает сценарий «продавец подменяет на двух точках» — только он сейчас применяется исключительно к роли storekeeper, а не к seller.
- Если для seller/storekeeper ввести **обязательный одиночный** `warehouse_id` (как в постановке задачи), а не список назначений (как уже сделано для storekeeper), то сценарий «продавец периодически работает на двух точках» потребует либо (а) заводить второй аккаунт на того же человека под второй склад — что плодит дубликаты телефонов/паролей и путаницу в audit log (кто есть кто), либо (б) владельцу постоянно вручную переключать `warehouse_id` туда-сюда через редактирование сотрудника — неудобно и не отражает факт «работает на обеих точках».

Вывод: жёсткая модель «1 сотрудник = 1 склад» тесна именно для этого сценария, и это не гипотетический край — в README прямо описан рост через открытие второй точки тем же составом семьи. У кодовой базы уже есть подходящий паттерн (`assigned_user_ids`, список), не хватает только применить его единообразно к seller, а не только к storekeeper. Рекомендация: не делать привязку сотрудника к складу как одиночный FK; использовать (или ввести) список «домашних» складов для любой роли, с одним из них помеченным как склад по умолчанию (для дефолта в форме продажи и в меню), а не как единственно возможный.

## 4. Сценарий смены роли/склада: сохранность истории продаж

Факты:
- **Ключевой и самый важный факт: `warehouse_id` продажи не выводится из сотрудника, а передаётся явно в команде создания продажи.** `CreateSaleCommand.warehouse_id: int` (`create_sale.py:26`), заполняется из ручного выбора кассира на экране (`SalePage.tsx`, стейт `warehouseId`, строка 546) и попадает в `Sale(..., warehouse_id=cmd.warehouse_id, seller_id=actor.id, ...)` (`create_sale.py:73-76`). То есть warehouse_id продажи — это склад **документа**, зафиксированный в момент продажи, полностью независимый от текущего значения `warehouse_id` у пользователя-продавца.
- Прямое следствие: если в будущем у `User` появится `warehouse_id`, и владелец переназначит продавца на другую точку, **исторические продажи не «телепортируются»** — они уже сохранены с конкретным `warehouse_id` в БД (`sale.warehouse_id`, отдельное поле сущности, не производное). Проблема, которой опасается постановка задачи, структурно исключена архитектурой — это хорошая новость, ничего чинить не нужно.
- UI редактирования сотрудника (смена роли/склада) на сегодня **не существует** — в `EmployeesPage.tsx` есть только создание (`createEmployee`) и список (`listEmployees`), никакого «Изменить»/PATCH-эндпоинта для сотрудника я не нашёл (искал по `application/auth/` — там `create_employee.py`, `change_password.py`, `login.py`, `connect_telegram.py`, `register_shop.py`, `update_shop.py`; последний — про сам магазин, не про сотрудника). Значит, если добавят обязательный `warehouse_id`, понадобится отдельный use case на редактирование сотрудника (смена роли и/или склада) — этого куска сейчас нет вообще, не только для warehouse.

Вывод: с точки зрения целостности данных о прошлых продажах — рисков нет, архитектура уже правильная (документ хранит свой склад, а не смотрит на текущее состояние сотрудника). Но нужно **не забыть добавить сам use case редактирования сотрудника** — это на сегодня отсутствующий кусок функциональности, а не доработка существующего.

## 5. Порог сложности vs польза

Аргументы за то, что для сегмента «1 точка, 1–3 человека» обязательная привязка — избыточна:
- Реальных дней, когда у «Айны» будет два склада, скорее всего не наступит вовсе (README прямо называет такие магазины «единица бизнеса» на 4–6 кв.м, а не сеть). Проектировать обязательный шаг под гипотетическое будущее — цена которого закладывается в форму сегодня, для каждого магазина, у которого это будущее не наступит.
- Единственный реальный сегодняшний пример многоскладовости в коде — кладовщик с несколькими назначенными складами (`assigned_user_ids`), и даже он не обязателен: кладовщика можно создать вообще без назначений (форма это разрешает, просто предупреждает «Нет доступных ответственных» только когда речь о выборе ответственного за **новый склад**, не наоборот).
- README философия («запуск за 15 минут», «проще калькулятора», раздел «Формула проекта») явно про минимизацию полей и решений на старте. Обязательный вопрос про склад при заведении первого продавца, когда склад физически один и по-другому быть не может — это ровно тот «визуальный шум», который стоит убирать заранее, а не после жалоб пилотов.

Аргументы за то, что модель ролей+складов — разумный минимум, а не оверинжиниринг:
- Сама многотенантность/роли (owner/manager/seller/storekeeper) не создают трения в одноточечном случае — они уже реализованы и работают прозрачно (не тратят лишние клики: роль выбирается один раз при создании сотрудника, это неизбежный и осмысленный вопрос — какие права дать человеку). Проблема не в ролях, а именно в **обязательности и одиночности склада**.
- Бизнес-модель ВайСклада прямо ориентирована на рост через «внедрение под ключ» и сарафанное радио (README, п.9) — то есть у части успешных клиентов вторая точка вполне реалистична через 1–2 года, и тогда наличие складской модели (пусть даже сейчас скрытой) экономит миграцию данных задним числом.

**Рекомендация (без реализации):**
1. Не делать `warehouse_id` у сотрудника обязательным одиночным полем. Использовать список назначений (по образцу уже существующего `Warehouse.assigned_user_ids`), единый для всех ролей, а не только для storekeeper.
2. В форме сотрудника и в UI выбора склада (продажи, остатки, аналитика) — **скрывать сам факт выбора, если склад в магазине один**: автоматически назначать единственный склад, без вопроса пользователю. Показывать выбор, только когда складов действительно больше одного. Паттерн `warehouses.length > 1 && (...)` для этого уже используется в `SalePage.tsx:353` — стоит просто применить его последовательно везде, где появится выбор склада у сотрудника.
3. Учитывая находку из раздела 4 (Sale.warehouse_id — свойство документа, не сотрудника): не пытаться «удобно» проставлять склад продажи автоматически от `user.warehouse_id` без возможности сменить его на экране продажи — если у сотрудника несколько складов (сценарий 3), кассиру нужно явно выбирать, на каком складе он сейчас находится, эта механика уже есть и её нужно только не сломать при добавлении привязки.
4. Добавить use case редактирования сотрудника (смена роли/списка складов) — сейчас его нет, а он понадобится сразу же, как только появится сама привязка (иначе смена продавца между точками потребует пересоздания учётки).
5. Если/когда появится аналитика «продажи по сотруднику» — строить её от фактического `seller_id` на документе продажи, а не от роли/текущей привязки пользователя, чтобы owner, торгующий за прилавком, автоматически попадал в отчёт без обходных путей.

Итого: текущая ролевая модель разумна и почти не мешает; риск не в ролях, а в дизайне будущей привязки к складу — если её сделать обязательной, единственной и жёстко видимой в UI даже при одном складе, это добавит трения именно в самом частом сценарии ЦА, ничего не выиграв взамен для этого же сценария.
