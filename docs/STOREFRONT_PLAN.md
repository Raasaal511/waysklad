# Публичная витрина-каталог (для конечных покупателей)

План. Соответствует README §5.2 ("Публичная витрина-каталог с остатками,
ссылка для клиентов в шапку Instagram"). Шаг 1 (публичный каталог без заявки)
реализован в коде 2026-09-03 — см. «Порядок реализации» ниже. Заявка и чат
(шаги 2–3) ещё не начаты.

## Статус решения

- **Без онлайн-оплаты.** README §5.3 сознательно отказывается от эквайринга и
  приёма платежей (юридические риски, фискализация, ответственность за деньги
  клиентов) — это решение не пересматривается витриной. Витрина — это заявка,
  не интернет-магазин с оплатой.
- Оплата за заказ с витрины — так же, как сейчас (наличными/переводом при
  выдаче, через существующий `Order` + `IssueOrderUseCase`).

## Что видит покупатель (публичная страница, без входа в систему)

- Список товаров: фото, название, цена, факт наличия ("в наличии"/"нет").
- **Не показываем:** закупочные цены, точные остатки в штуках (только факт
  наличия — не палить складские объёмы конкурентам), любые внутренние данные.
- Не все товары обязаны попадать на витрину — у товара должен быть флаг
  "показывать на витрине", **по умолчанию выключен** (решено) — новый товар
  не попадает на публичную страницу, пока владелец явно не включит показ.
  Осторожный дефолт: при первом включении витрины на уже заполненном каталоге
  ничего не "утечёт" наружу без явного решения владельца.
- Категории для навигации, если у магазина их много.

## Как покупатель оформляет заявку

- Корзина → оформление: имя, телефон, комментарий. Без оплаты на этом шаге.
- Заявка попадает в систему владельца как **`Order`** — переиспользуем
  существующую сущность (уже есть статусы new/in_progress/ready/issued,
  `source` с вариантами whatsapp/instagram/call/in_person). Добавить источник
  `storefront` (или похожий).
- Владелец обрабатывает заявку как обычный заказ — никакого нового интерфейса
  на стороне владельца для самого списка заказов не требуется.

## Внутренний чат (привязан к заявке)

- Не общий чат «на будущее», а переписка **под конкретным заказом** —
  открывается вместе с заявкой (уточнить размер/адрес/детали).
- Живёт вместе с заказом, не отдельная самостоятельная сущность.
- Нужно решить отдельно: real-time (WebSocket) или обычный поллинг/обновление
  по действию — вероятно, поллинг проще и достаточно для MVP этой фичи.
- Уведомление владельцу о новом сообщении — переиспользовать существующий
  механизм уведомлений (`domain/notifications/`), как уже сделано для задач.

## Технически (черновой набросок, backend)

- Публичный (без авторизации) эндпоинт по `Tenant.slug` — slug уже существует
  в системе (заведён сессией 06 именно под эту будущую задачу).
- Отдельный урезанный ответ каталога (без закупочных цен и точных остатков) —
  не переиспользовать существующий `ProductResponse` для владельца напрямую.
- Приём заявки → создание `Order` с `source=storefront`, без авторизации
  (в отличие от всех остальных мутирующих эндпоинтов сейчас).
- Чат по заказу: новая сущность сообщений, привязанная к `order_id`; доступ
  публичный со стороны покупателя (по ссылке на его заявку/номеру телефона —
  нужно продумать, как покупатель возвращается к своей переписке без логина)
  и авторизованный со стороны владельца/сотрудника.
- Флаг "показывать на витрине" — новое поле у `Product`.
- Настройка магазина: включить/выключить витрину целиком (не все захотят).

## Открытые вопросы

1. ~~Как покупатель без аккаунта возвращается к переписке по своей заявке
   позже?~~ **Решено:** токен на заявку (непредсказуемый, в URL) —
   единственный источник доступа на сервере; `localStorage` на стороне
   покупателя дублирует токен последних заявок этого браузера, чтобы не
   заставлять человека вручную хранить ссылку — вернулся на сайт и увидел
   свою заявку сам. Если localStorage пуст (другое устройство/браузер
   почищен) — доступа нет, это осознанный компромисс "без аккаунта".
2. Нужна ли отдельная модерация/уведомление, если покупатель пишет в чат по
   уже выданному/отменённому заказу?
3. ~~Флаг "показывать на витрине" — дефолт?~~ **Решено:** выключен по
   умолчанию.
4. У витрины будет отдельный URL по `slug` магазина — нужно проверить, что
   `Tenant.slug` действительно уникален и пригоден для публичной ссылки уже
   сейчас (заводился давно, не проверялся под эту нагрузку).

## Порядок реализации

1. ✅ **Публичный каталог без заявки** (2026-09-03) — `GET /api/storefront/{slug}`,
   `Tenant.storefront_enabled` (дефолт `false`) + `Product.show_on_storefront`
   (дефолт `false`) — оба условия обязательны разом. Урезанный ответ:
   `id/name/retail_price/photo/category_id/in_stock` — без закупочной цены,
   маржи, точного остатка. `in_stock` — булево по сумме `stock_items.quantity`
   по всем складам (переиспользует остаточную инфраструктуру, не новый расчёт).
   Rate limit `60/minute` на IP (`@limiter.limit`, тот же механизм, что и
   `/auth/register`/`/auth/login` — единственный прецедент публичных
   эндпоинтов в проекте). Тест `test_storefront_catalog_via_api`, отчёт в
   `frontend/api_docs/README.md`. Фронтенд (сама страница `/store/{slug}`,
   тумблеры в настройках/форме товара) не сделан — backend-only режим сессии.
1a. ✅ **Витрина одного склада** (2026-09-03) — тот же эндпоинт, опциональный
   `?warehouse_id=<id>`. Список товаров не сужается (это всё ещё общий каталог
   магазина, не отдельная сущность) — меняется только `in_stock`: без параметра
   суммарно по всем складам, с параметром — только по указанному. Решение
   пользователя явно: список НЕ фильтруется по складу (товар остаётся видимым
   даже без остатка на выбранном складе, просто `in_stock: false`) — так владелец
   видит полный ассортимент магазина через любую ссылку, просто с честной
   пометкой наличия относительно точки, которой делится. Несуществующий/чужой
   `warehouse_id` тихо игнорируется (не 404/400) — не даёт перебором узнавать
   id чужих складов. Тест `test_storefront_catalog_filtered_by_warehouse_via_api`.
   Фронтенд: кнопка «Поделиться витриной склада» на экране склада, формирующая
   `<домен>/store/{slug}?warehouse_id=<id>` — не сделана, backend-only.
2. ✅ **Заявка с витрины** (2026-09-03) — отличается от изначального черновика
   плана: заявка НЕ становится `Order` сразу (`due_date` неизвестен покупателю,
   а требование указать его сразу отсекает пустые/спам-заявки — решение
   пользователя). Новая лёгкая сущность `StorefrontRequest`
   (`app/domain/storefront/entities.py`) — имя (обязательно), телефон и
   комментарий (опционально), корзина товаров с количеством, без резерва
   остатка. `POST /api/storefront/{slug}/requests` (публично, `20/hour`
   rate limit), `GET /api/storefront/requests/new` (владелец, отдельный
   список — не смешивается с обычными заказами), `POST .../accept` (владелец
   указывает склад+дату — только тогда резервируется остаток и создаётся
   `Order` c `source=storefront`, цена берётся из АКТУАЛЬНОГО `retail_price`,
   не из момента заявки), `POST .../reject`. Клиент ищется по телефону
   (`IClientRepository.get_by_phone`, новый частичный уникальный индекс
   `clients(tenant_id, phone) WHERE phone != ''` — решение пользователя
   "сделай номер уникальным") — повторная заявка с тем же номером не плодит
   дубль в CRM. Тесты `test_storefront_request_full_flow_via_api`,
   `test_storefront_request_reject_via_api`. Побочно найдена находка №22
   в TECH_DEBT (`Order.number` не возвращается сразу после создания — не
   регрессия этой сессии, существовало и в обычном `POST /api/orders`).
   Фронтенд (корзина на витрине, экран «Заявки с витрины» у владельца) —
   не сделан, backend-only.
3. ✅ **Чат по заявке** (2026-09-03) — привязан к `StorefrontRequest`, не к
   `Order` (уточнение пользователя: покупатель должен мочь писать сразу
   после отправки заявки, ещё до принятия владельцем). Доступ покупателя —
   тот же `access_token`, что и был отложен как открытый вопрос при заявке:
   теперь реализован — `POST /requests` возвращает токен один раз в момент
   создания, дальше хранится в `localStorage` покупателя (аналог решения
   про localStorage из этого же плана, но не отдельный механизм — тот же
   токен обслуживает и доступ к заявке, и к чату). `StorefrontMessage`
   (`app/domain/storefront/entities.py`) — просто `author: customer|staff`
   + текст, живёт вместе с заявкой (не переносится в `Order` при принятии).
   REST: `GET/POST /api/storefront/requests/chat?token=` (покупатель, без
   авторизации), `GET/POST /api/storefront/requests/{id}/chat` (сотрудник,
   `ORDERS_VIEW`/`ORDERS_MANAGE` — те же права, что и у заявок, отдельного
   права не заводили). WS: `WS /api/storefront/requests/chat/ws?token=` —
   потребовало расширить `Broadcaster`/`ConnectionRegistry`
   (`app/infrastructure/ws_broadcast.py`) с адресации по `user_id: int` на
   произвольный строковый канал (`user:<id>` для уведомлений,
   `storefront_request:<id>` для чата) — один Redis pub/sub на оба сценария,
   обратная совместимость с уведомлениями сохранена. Новое сообщение
   покупателя создаёт `NotificationKind.STOREFRONT_MESSAGE` владельцу/
   менеджерам через существующий `notify_user` — отдельного алерта не
   городили. Тесты `test_storefront_chat_rest_via_api`,
   `test_storefront_chat_websocket_via_api` (последний — реальная доставка
   через `TestClient.websocket_connect`, как и WS-тесты уведомлений).
   Дополнительно проверено сквозным ручным сценарием (два независимых
   Python-процесса — WS-слушатель покупателя + REST-отправка владельцем)
   через живой Docker-контейнер. Фронтенд (экран заявки покупателя, блок
   переписки в карточке заявки владельца) — не сделан, backend-only.

Все три шага плана реализованы на backend. Фронтенд для витрины целиком
(публичная страница каталога, корзина, экран заявок и чата у владельца)
не начат — см. `frontend/api_docs/README.md` за полными контрактами.

## Доработки поверх плана (2026-09-03, после трёх шагов)

Пользователь запросил список идей "что ещё можно добавить" — выбрал 5 из
предложенных, все реализованы:

1. ✅ **Карточка одного товара** — `GET /{slug}/products/{id}`, урезанный
   ответ + `sku`/`variants` для полноты при шеринге ссылки на конкретный
   товар.
2. ✅ **Сортировка каталога** — `?sort=name|price_asc|price_desc|created_desc`
   на `GET /{slug}`. Только безопасное подмножество `ProductFilterFactory`
   (margin/stock исключены — внутренние данные).
3. ✅ **Категории со счётчиком** — `categories[].product_count` в ответе
   каталога, новый `IProductRepository.count_storefront_by_category()`;
   пустые категории (без видимых товаров) отфильтрованы.
4. ✅ **Статус заявки по токену** — `GET /requests/status?token=`, тот же
   `access_token`, что уже обслуживает чат; после `accepted` отдаёт
   `due_date`/`total`/`to_pay` принятого `Order`.
5. ✅ **Защита от спама заявками** — не более 5 необработанных заявок с
   одного телефона на один магазин одновременно (`IStorefrontRequestRepository.count_new_by_phone`);
   действует только когда телефон указан.

**Избранное** — явно НЕ backend-функциональность (решение пользователя):
localStorage на стороне покупателя, backend не участвует, API не менялся.
