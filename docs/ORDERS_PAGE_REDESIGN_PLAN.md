# План: доработка страницы «Заказы»

Зафиксировано перед реализацией по запросу пользователя.

**Статус: реализовано.** Отличия от плана при реализации:
- Домен `Order` получил `number`/`created_at` (тот же паттерн, что раньше был
  добавлен `StockDocument` для истории движения) — нужны для отображения номера
  заказа и сортировки завершённых по дате выдачи.
- Отдельный метод `list_completed()` (не параметр `?status=` у существующего
  эндпоинта) — симметрично `list_active()`, эндпоинт `GET /orders/completed`
  зарегистрирован в роутере ДО `GET /orders/{order_id}`, иначе FastAPI принял бы
  «completed» за id.
- Онбординг — `.onboarding-banner-dismissible` (новый модификатор существующего
  `.onboarding-banner`) с крестиком `IconButton`, флаг в
  `localStorage['orders_onboarding_dismissed']`.

## Контекст

«Заказы» — предзаказ клиента (обычно из переписки WhatsApp/Instagram): товара может
не быть в наличии, фиксируется дата готовности и опциональная предоплата, статус
идёт по циклу Новый → В работе → Готов → Выдан. Это осознанно отдельная сущность
от «Продажи» (см. `Order`/`OrderLine` в `backend/app/domain/orders/entities.py`) —
продажа списывает остаток и фиксирует факт оплаты сразу, заказ — обещание на будущее.

Сейчас страница — MVP-заготовка:
- форма создания принимает только один товар за заказ (бэкенд уже поддерживает
  список позиций, фронт им не пользуется);
- список показывает только активные заказы (`GET /orders` = `list_active`) — после
  перевода в статус `issued` заказ пропадает из вида навсегда, нет способа посмотреть
  завершённые;
- нет объяснения сути раздела для новичка — непонятно, «для себя» это или для клиента.

## 1. Корзина позиций в форме создания

Форма заказа переходит на паттерн Приёмки/Продажи: список позиций (`OrderLine[]`
на фронте) вместо одного товара — добавление/удаление строк, каждая строка —
товар/количество/цена. Бэкенд уже принимает `items: OrderItemRequest[]`, менять
не требуется.

## 2. История завершённых заказов

Вкладки «Активные / Завершённые» на той же странице `OrdersPage.tsx` (как
period-фильтры в Продажах/Остатках) — не отдельная страница.

- Backend: `IOrderRepository.list_all()` рядом с существующим `list_active()`
  (или `list_completed()` — выбрать по факту при реализации то, что проще
  фильтровать на фронте: скорее всего один метод `list_all()`, а активные/
  завершённые — просто фильтр по `status` на клиенте, т.к. заказов у одного
  магазина немного и постранично их точно не нужно).
- Роутер: либо расширить `GET /orders` необязательным параметром (`?status=all`),
  либо отдельный `GET /orders/all` — решить при реализации, глядя на то, как
  сейчас fetch вызывается на фронте (`listActiveOrders()` уже используется в
  одном месте, расширить сигнатуру не проблема).
- Frontend: вкладки-переключатели, при «Завершённые» показываем `issued` заказы
  с датой выдачи и итогом — ничего не удаляется, это просто фильтр отображения.

## 3. Онбординг для новичка

Закрываемая карточка-подсказка сверху страницы, между заголовком и списком.
Текст объясняет: «Заказ — это то, что клиент попросил заранее (из переписки), до
того как забрал и оплатил — в отличие от Продажи, которая фиксирует уже
свершившуюся сделку». Крестик «Понятно» — прячет насовсем через `localStorage`
(паттерн: булев флаг под ключом вида `orders_onboarding_dismissed`), аналогично
уже существующему подходу с черновиком продажи в `SalePage.tsx`
(`localStorage.getItem/setItem(DRAFT_KEY)`), но здесь — не данные, а факт
«показывали/закрыли».

Использовать существующий класс `.onboarding-banner` (см. `SalePage.tsx:447`,
`index.css`) как основу стиля, но с крестиком закрытия (новый элемент — сам
класс `.onboarding-banner` сейчас не подразумевает dismiss).

## Порядок реализации

1. Backend: `list_all()`/эндпоинт для истории заказов (если понадобится —
   зависит от финального решения по способу фильтрации).
2. Frontend: `entities/order/api.ts` — при необходимости новая функция для
   получения всех заказов.
3. Frontend: форма создания — корзина позиций вместо одного товара.
4. Frontend: вкладки Активные/Завершённые на `OrdersPage.tsx`.
5. Frontend: закрываемая карточка-подсказка (localStorage dismiss).
6. Проверка: backend pytest (если бэкенд менялся), tsc, vite build, ручная
   проверка в Docker.
