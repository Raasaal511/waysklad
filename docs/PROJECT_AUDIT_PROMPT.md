# Промпт: полная сверка проекта с изначальными целями

Задача — не написать код, а честно проверить, где ВайСклад находится
относительно того, что задумывалось в `README.md`, и не потерялся ли план.

Промпт один и большой. Давайте его в отдельной сессии ассистента, когда у
него есть доступ и к бэкенду, и к фронтенду, и к `docs/`.

---

## Промпт A — аудит состояния проекта (вставить целиком)

```text
Проект ВайСклад (WaySklad): FastAPI + Postgres + Redis (backend/),
React 19 + Vite + TypeScript (frontend/), документация в docs/ и
frontend/api_docs/.

ЗАДАЧА: провести полный аудит состояния проекта относительно изначальных
целей и написать один отчёт. Код НЕ МЕНЯТЬ вообще — ни строчки, включая
документацию, кроме единственного нового файла docs/PROJECT_STATE_AUDIT.md.

ГЛАВНОЕ ПРАВИЛО: документам не верить. Любая строка отчёта опирается на
проверку в коде, в тестах, в конфигах или в git — с указанием файла и
строки. Формулировки «реализовано», «закрыто», «готово» из docs/ и
frontend/api_docs/ — это гипотезы, которые нужно подтвердить или
опровергнуть. Если утверждение из документа не подтвердилось — это
отдельная находка.

ЧТО ПРОЧИТАТЬ СНАЧАЛА (это источники целей, не отчётности):
  README.md — разделы 1 (суть), 4 (для кого), 5.1 (MVP), 5.2 (вторая
    очередь), 5.3 (что сознательно не делаем), 6.4 (демо-данные),
    8 (план 12 недель), 9 (модель заработка), 12 (метрики успеха),
    13 (риски)
  docs/ROADMAP.md — пять направлений и очередь «до пилота / во время /
    после»
  docs/NEXT_PLAN.md — приоритеты backend перед пилотом
  frontend/api_docs/PRIORITY.md — что на фронте считается срочным
  frontend/api_docs/README.md — журнал изменений API (новые записи сверху)
  docs/sessions/ — журнал сессий, от последних к ранним
  docs/NEXT_FEATURES_FROM_COMPETITORS.md, docs/COMPETITOR_WIKKEO_ANALYSIS.md
  docs/PRODUCT_PAGE_PROMPTS.md, docs/MARKETPLACE_HOME_PROMPTS.md,
  docs/ILLUSTRATIONS_PROMPTS.md — текущие рабочие задания
  git log --date=short --pretty='%ad %s' за последние 60 дней

КАК ПРОВЕРЯТЬ (примеры приёмов, не ограничивайся ими):
  - фича есть на бэкенде: роут в app/presentation, use case в
    app/application, модель и миграция, тесты в backend/tests
  - фича есть на фронте: вызов эндпоинта в src/entities/*/api.ts И
    использование в src/pages/** (вызов без экрана = фичи нет)
  - тесты: запусти pytest (кратко, -q) и назови число и результат; если
    запустить нельзя — скажи почему, не выдумывай цифру
  - миграции: alembic heads — одна голова или несколько
  - сборка фронта: npm run build и npm run lint
  - прод-конфиг: docker-compose.prod.yml, deploy/, frontend/nginx.conf,
    backend/app/infrastructure/config.py
  - «мёртвый код»: экраны и эндпоинты, на которые никто не ссылается

ОТЧЁТ пиши в docs/PROJECT_STATE_AUDIT.md, по-русски, со следующими
разделами. Везде, где утверждаешь факт, ставь ссылку вида `путь:строка`.

1. КРАТКО ДЛЯ ВЛАДЕЛЬЦА (10–15 строк, без терминов): где проект
   находится, что мешает начать пилот, что делать в ближайшие две недели.

2. MVP ПО README §5.1 — таблица по каждому пункту:
   пункт | backend (есть/частично/нет + ссылка) | frontend (то же) |
   проверено тестом или руками | комментарий.
   Обязательно раздельно backend и frontend: у проекта уже был случай,
   когда контракт готов, а экрана нет.

3. ПЛАН 12 НЕДЕЛЬ (README §8) — таблица: неделя | результат по плану |
   фактически сделано | статус (сделано / частично / не начато) |
   чем подтверждается. Отдельно ответь: на какой неделе плана проект
   находится ФАКТИЧЕСКИ и сколько календарного времени прошло с начала
   (первый коммит в git).

4. БЛОКЕРЫ ПИЛОТА — список того, что обещано в README §6.5, §13 и
   docs/ROADMAP.md §1 и до сих пор не сделано. По каждому: почему это
   блокер, где именно проверено, оценка в часах. Проверь как минимум:
   внешний (offsite) бэкап, CORS, небезопасные дефолты secret_key и
   пароля БД, ревокация и срок жизни токена, health-check бэкенда в
   docker-compose.prod.yml и содержательность GET /api/health,
   логирование ошибок и алерты, согласие на обработку персональных
   данных при регистрации (152-ФЗ), индексы на FK, пагинация списков
   продаж и долгов. Каждый пункт — подтверди или сними: часть из них
   могла быть закрыта позже, чем написан ROADMAP.

5. РАСХОЖДЕНИЕ БЭКЕНД ↔ ФРОНТЕНД — таблица по каждому контракту из
   frontend/api_docs/: эндпоинт или поле | есть на бэкенде | используется
   на фронте | где должно использоваться. В конце — оценка: сколько
   фронтовых задач накопилось и в каком порядке их закрывать.
   Отдельно отметь случаи, когда фронт использует старое поле, а бэкенд
   уже отдаёт новое (риск тихой поломки).

6. ЛИШНЕЕ И РАСПОЛЗАНИЕ ЗАДАЧ — что сделано сверх README §5.1 и §5.2.
   По каждому пункту: что это, когда сделано, сколько сессий или
   коммитов заняло, работает ли это на цель «пилот в 5–10 магазинах»
   или уводит от неё. Не оценивай морально — просто покажи цену.
   Отдельно проверь §5.3 («что сознательно не делаем»): не появилось ли
   в коде чего-то из запрещённого списка (кассы, эквайринг, интеграции,
   ЭДО, бухгалтерия) хотя бы в виде заготовок.

7. ПОТЕРЯННОЕ — что было запланировано и тихо выпало: пункты из
   ROADMAP.md, NEXT_PLAN.md, PRIORITY.md и из «Что дальше» в конце
   файлов docs/sessions/*.md, которые не сделаны и не упомянуты нигде
   позже. Для каждого: где предложено, почему, похоже, выпало.

8. КАЧЕСТВО И ТЕХДОЛГ — покрытие тестами по модулям (что вообще не
   покрыто), число TODO и FIXME в коде с разбивкой по областям,
   несколько alembic-голов, мёртвые файлы, дубли (например, две разные
   карточки товара), размер самых больших файлов фронта. Без вкусовщины:
   только то, что мешает менять код.

9. ГОТОВНОСТЬ К МЕТРИКАМ (README §12) — сможем ли мы вообще измерить
   20+ магазинов, retention 70%, 5000+ продаж, NPS? Что для этого уже
   есть (админ-панель, аналитика), чего не хватает. Это должно быть
   готово ДО пилота, иначе пилот не даст данных.

10. ДОКУМЕНТАЦИЯ — таблица по каждому файлу docs/ и frontend/api_docs/:
    файл | дата последнего изменения | актуален / устарел / противоречит
    другому файлу | что делать (оставить, обновить, объединить, в архив).
    Отдельным списком — найденные противоречия между документами.

11. ПЛАН НА БЛИЖАЙШИЕ 5 СЕССИЙ — по одной строке на сессию: цель,
    почему именно она, что считается выполнением. Правило приоритета
    берётся из README §8: «если неделя поплыла — режем функциональность
    второй очереди, но не сдвигаем пилот». Из этого и исходи.

12. ВОПРОСЫ ВЛАДЕЛЬЦУ — не больше пяти, только те, без ответа на
    которые нельзя выбрать приоритет. Каждый — с вариантами ответа.

ТОН: без похвалы и без драматизации. Если что-то сделано хорошо — одна
строка. Если плохо — факт, ссылка, последствие. Не предлагай
переписывать архитектуру.

В КОНЦЕ ответа в чат (не в файл) дай 15 строк выжимки: три главных
вывода, три ближайших действия, три вопроса.
```

## Как пользоваться результатом

1. Прочитать раздел 1 отчёта и ответить на вопросы из раздела 12.
2. Раздел 4 (блокеры пилота) превратить в ближайшие сессии — это прямые
   обещания из README, а не украшения.
3. Разделы 5 и 7 (фронт отстал, потерянные задачи) — держать как
   единый бэклог, чтобы он больше не расползался по разным файлам.
4. Промпт B запускать раз в неделю: он дешёвый и не даёт курсу
   уплыть незаметно.
